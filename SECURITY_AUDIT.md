# Security and implementation audit

Review date: 2026-09-02. Scope: supplied baseline, modular source, build pipeline, generated WASM, the Bitcoin/Ethereum/Dash Wallet Key Derivation Tool, the connected Wallet Activity Viewer, and the mnemonic-based scan-only Wallet Discovery Scanner. The source is deliberately modular so additional coins and result types can be added without rewriting the generic UI/export layers. This is an engineering review, not a third-party security audit or formal cryptographic proof.

## Historical Bitcoin-only baseline

The supplied `Taproot_Key_Deriver.html` was a 102,545-byte single-file Bitcoin Taproot application. It bundled minified Noble/Scure-family code with MIT license markers, used standard BIP39/BIP32 and secp256k1 primitives, and correctly performed BIP341 key-path derivation: even-Y internal-key normalization, tagged `TapTweak`, output point addition, tweaked secret calculation, Bech32m, and P2TR scriptPubKey. Its CSP blocked connections and it did not use persistent storage or runtime network APIs.

That description applies only to the historical input prototype, not to the current suite. The current Wallet Key Derivation Tool supports Bitcoin Legacy/Nested SegWit/Native SegWit/Taproot, Ethereum EOA, Dash Core, Dash Platform, and Dash Orchard; the connected Wallet Activity Viewer and Wallet Discovery Scanner cover the documented Dash read-only workflows.

The main security weakness was secret duplication in DOM `data-copy` attributes. It also rendered large HTML fragments with `innerHTML`, did not generate BIP39 phrases, and had no automated vector suite, bulk selection, dependency lock, or modular source. Dependency versions were not reliably recoverable from the minified artifact.

The refactor preserves the visual/security model but replaces value-bearing data attributes with opaque field locators, constructs output using DOM nodes and `textContent`, retrieves copy values from in-memory typed result objects, and adds pinned dependencies and verification.

## Controls present

- The Wallet Key Derivation Tool CSP disables all default sources and runtime connections; frames, objects, form destinations, fonts, and base-URI changes are disabled. `worker-src blob:` permits only the disposable derivation worker constructed from JavaScript already embedded in the same HTML; remote or sibling workers remain blocked.
- The Wallet Key Derivation Tool has no fetch, XMLHttpRequest, WebSocket, EventSource, remote import, analytics, telemetry, CDN, external font, remote image, or automatic-update code. Connected-tool exceptions are described under their explicit boundaries below.
- No localStorage, sessionStorage, IndexedDB, or cookie access is present.
- Entropy generation requires `crypto.getRandomValues`; the verifier rejects `Math.random`.
- All user-derived HTML content is assigned with `textContent`. No result value is inserted through HTML parsing.
- Secret copy buttons and secret-bearing bulk exports remain disabled until reveal.
- Mnemonic copy is disabled until inputs are revealed. Privacy-sensitive watch-only exports are also reveal-gated even though they cannot spend.
- Export is selected-row-only and mode-aware; basic mode cannot include advanced fields.
- Numeric bounds are enforced both by UI adapter metadata and derivation modules. BIP32 leaves remain non-hardened; Shielded diversifier indices remain uint32.
- Expected-address verification is local, bounded to at most 5,000 requested indices, batched through adapter limits, and clears each temporary result before continuing.
- Async results carry a revision token; a batch is scrubbed and discarded if inputs or adapters change while derivation is pending. User totals are split into bounded internal batches inside a disposable Web Worker, with a transferred seed copy per batch. Optional receive/change generation stores each branch in an independent result, selection and paging slot so equal child indices cannot overwrite or cross-select one another. Termination stops the active worker immediately. Only a bounded window of rows is present in the DOM, and download exports are encoded in row-sized stream chunks.
- Offline totals of 10,000 or more require an explicit second confirmation that includes internal batch count and an estimated memory range. A changed adapter/control value invalidates that confirmation, and totals above the 20-row automatic default never start implicitly on tab changes. This is an availability guard; the protocol index space remains the only hard total limit.
- In `Wallet_Key_Derivation_Tool.html` the main-thread registry contains metadata only: runtime coin adapters, cryptographic derivation, address search, and the Orchard module are worker-only. Activity Viewer derivation/scanning remains in its document realm. The Discovery Scanner instead runs its mnemonic-bearing application inside an opaque-origin, network-denied Secret Vault and places Evo SDK/network transport in a separate outer Worker. Artifact verification byte-compares the generated WASM and requires exactly one embedded copy; in the offline artifact it also requires exactly one BIP39 English wordlist.
- BIP39 seed arrays, the WASM boundary seed copy, child/root key byte copies, hashes, address component buffers, HD private nodes and result objects receive best-effort zeroing/clearing where they are mutable. The generated-WASM test asserts that the caller seed is copied back as zeroes after derivation. Text controls/nodes are emptied and references released, but no claim is made that immutable JavaScript strings are overwritten.
- Sensitive offline inputs and result text automatically return to the concealed state when the document becomes hidden or the browser window loses focus.
- The WASM glue has no asynchronous loader or fetch path. The module is embedded and instantiated synchronously.
- Build verification scans every final artifact, confirms exact reviewed CSPs rather than only searching for fragments, confirms embedded WASM/wordlist counts, and validates recorded SHA-256 digests. Recovery additionally computes SHA-256 CSP authorization for both immutable inline scripts and checks the resulting shell hash byte for byte.
- Canonical release builds run in a Linux/amd64 Docker image whose Ubuntu 24.04-based base is pinned by immutable digest. Node/rustup installers are checksum-verified; pnpm, Rust/Cargo and wasm-bindgen versions are fixed; the final complete `pnpm verify` layer has no network access. Rebuilt Orchard WASM/glue must match the committed reviewed bytes before artifacts are exported. This prevents host-distribution linker differences from silently changing release identities; it does not make Docker or its daemon a cryptographic trust oracle.
- Build verification also rejects duplicate IDs within each document and guards against template-inlining corruption. Recovery verifies its two-document structure separately because the standalone shell embeds the complete vault document as inert `srcdoc` source.
- Recovery's mnemonic, passphrase, BIP39 seed, HD derivation and Orchard FVK remain in a sandboxed `srcdoc` Secret Vault without `allow-same-origin` or `allow-downloads`; its CSP sets `connect-src 'none'` and `worker-src 'none'`. The outer shell cannot read the vault DOM. Evo SDK plus every direct `fetch` lives in a separate Network Worker, which cannot access either DOM and has no BIP39/seed/private/viewing-key imports.
- Vault and Network Worker communicate through one transferred `MessagePort` with ten fixed read operations for Core status/tip/address data, Platform address/identity proofs and history, and Orchard pages. The protocol accepts no URL, generic body, SDK method name or callback. Core and Platform addresses must pass full checksum, network, payload-length, and P2PKH-type decoding inside the Worker. `RecoveryNetworkGateway` runs a registered-secret tripwire before each public RPC payload crosses the port, and scanner-specific parsers validate every response before it changes balances. The build fails if Evo/network-service modules enter the vault graph or secret-derivation/guard modules enter the network graph.
- Recovery can process one through five batch phrases, sequentially by default. Each wallet owns isolated seed/accounting state and a fixed result slot; completed reports are rendered/exported in original input order. The Network Worker shares only public Evo connection/quorum state and separates SDK instances by network and purpose. A shared abort-aware semaphore caps aggregate RPC/DAPI work at five, and Identity proof results are committed in increasing index order. Proof calls use a 10-second SDK timeout, disable nested retries, and permit at most two explicit fresh-connection retries with bounded backoff; invalid arguments fail immediately and exhaustion never becomes a zero result. Batch Orchard downloads each page once, applies it to every local FVK, wipes its byte arrays, and only then requests the next page. DAPI cursors stay aligned to 2,048-action chunks, two proof-verified empty reads establish completion, and a 4,096-page ceiling yields `partial`; the full pool is never cached. Cancellation removes queued work and becomes a barrier before final secret cleanup. Address-count controls have no artificial HTML maximum; Core/Platform totals are minimums and automatically extend to 20 addresses after every used index within the actual non-hardened BIP32 index space.
- Recovery renders completed batch wallets as source-ordered tabs so one wallet does not create an unbounded vertical report. CSV/JSON always exports every completed tab. General audit/recovery notices are displayed once; section-specific partial/failure warnings remain beside the affected result.
- Recovery CSV/JSON is projected from public findings rather than raw scan state. Internal re-derivation locators and every phrase/seed/private/spending/viewing key are omitted; exact integers become decimal strings and CSV cells are protected from formula execution. The vault cannot initiate a download: report text crosses a separate fixed export message and the trusted shell selects the local filename/MIME and creates the Blob.

## Cryptographic review results

No custom key-derivation, curve, hash, address, or encryption primitive was introduced. Noble/Scure provide hashes, HMAC/PBKDF2 through BIP39, secp256k1, BIP32, Base58Check, Bech32/Bech32m, Keccak, and Schnorr utilities. The non-secret BIP380 descriptor checksum is implemented directly from the deployed BIP/Bitcoin Core reference algorithm and checked against its official fixed vector.

Taproot matches the complete official BIP86 vector including internal key, exact TapTweak, output key, scriptPubKey, address, and the next address. The implementation treats the BIP32 child WIF and the BIP341-tweaked output secret as different values and explains the descriptor/import limitation. All four Bitcoin modes export a ranged, checksummed watch-only output descriptor with the account xpub and correct master fingerprint/origin path.

Ethereum uses uncompressed `0x04 || X || Y`, hashes only `X || Y` with Keccak-256, takes the final 20 bytes, and applies EIP-55. It is cross-checked against ethers.

Dash Core constants match current Dash Core chain parameters and outputs are cross-checked with DashHD plus a published SLIP vector. Platform matches all current DIP17 key vectors and DIP18 P2PKH address vectors. DIP13 Identity authentication keys now have fixed mainnet and testnet path/private/public/HASH160 vectors reproduced independently through `dashhd` during verification. The basic Platform secret is raw 32-byte hex because DIP17 defines raw child-key bytes and does not define a Platform-specific WIF; a Dash-compatible WIF is retained only as an explicitly qualified advanced transport encoding.

Shielded math is provided by Dash's official Orchard fork. Native Rust tests cover an upstream Orchard component vector, a fixed ZIP32 seed pin, display encoding, invalid bounds, and network domain separation. The generated browser WASM is instantiated separately and rechecked against the fixed vector.

The connected Wallet Activity Viewer and Wallet Discovery Scanner use the official Evo SDK 4.1.1 trusted/proof path for encrypted-note and Platform-address-state queries. Their Rust/WASM scanner mirrors the official Platform wallet's incoming decryption, OVK output recovery, and FVK-only owned-note nullifier derivation. In addition to locally generated round-trip coverage, scanner compatibility is pinned by a fixed full-wire note generated outside this repository through the official stable `dashpay/platform` v4.1.1 wallet builder at commit `69b85c81af8e000e8506edaa13406d1f6274af5a`. It verifies the complete `cmx || action nullifier || cv_net || encrypted_note` input and independently checks both FVK incoming and OVK outgoing recovery against the wallet's expected value, raw address, and Dash memo; exact provenance is stored beside the fixture. Other tests exercise a fresh encrypted Dash-memo note with FVK, IVK, and OVK capabilities, foreign-key rejection, malformed fixed-width inputs, key-buffer zeroing, spent reconstruction, and self/change classification. Live smoke tests fetch the current mainnet/testnet Orchard stream using required 2,048-action-aligned cursors without sending a viewing key. Orchard raw-value units are additionally pinned to official `dashpay/platform` commit `1c128acaf92e68a147086f9b87810dae5cc21993`: its SDK documents `1 DASH = 1e11` credits and its wallet test passes `value_credits` directly into `NoteValue::from_raw`. Dash Core public-address mode uses the Dash-specific DashScan Mainnet/Testnet API. It fails closed unless DashScan reports a synchronized index, reports the indexed Core height/time, parses monetary totals as exact integer duffs, and is tested with mocked synchronization, totals, pagination, and transaction-flow fixtures. The Wallet Discovery Scanner additionally has a live Mainnet/Testnet adapter smoke using a public BIP39 vector; it covers Core receive/change, Platform addresses, and identity public-key-hash proofs without using a user wallet.

## Connected artifact boundaries

- `Wallet_Key_Derivation_Tool.html` remains strictly offline with `connect-src 'none'`; no Evo SDK or network code is bundled into it.
- `Wallet_Activity_Viewer.html` is visibly marked ONLINE and has `connect-src https:` for Dash Platform DAPI/quorum connectivity, the DashScan Core-address index, and the Dash Platform Explorer history index. `wss:` was removed: neither connected artifact contains a WebSocket, EventSource or WebTransport reference, so the directive only widened the policy. Its exact reviewed CSP permits `worker-src blob:` because the pinned Evo SDK constructs a same-document Blob Worker from embedded code; external worker URLs remain blocked.
- `Wallet_Discovery_Scanner.html` is visibly marked network-enabled, but its CSP is split. Only the outer shell/Network Worker has `connect-src https:` and `worker-src blob:`; the nested opaque-origin Secret Vault has `connect-src 'none'`, `worker-src 'none'`, and no download sandbox permission. Host trust remains critical despite this structural separation.
- The viewer has no mnemonic or passphrase input. It accepts the offline tool's versioned FVK bundle, or a canonical 96-byte FVK or 64-byte IVK automatically. A bundle is rejected when its embedded network differs from the selected network. Fixed-width 32-byte OVKs require explicit advanced selection because their encoding length cannot be distinguished from a spending key; the UI warns against substituting spending authority. Each scanner exposes only the capability that the selected viewing key cryptographically provides.
- The FVK is passed only to local embedded Orchard WASM. Network methods receive public `(start_position, count)` ranges.
- Viewer query controls start disabled and fail closed until the embedded Orchard runtime passes fixed public derivation, canonical-FVK, invalid-FVK and empty scanner-boundary checks. Recovery reports the same runtime check in its full Release passport in addition to its derivation vector suite.
- Viewer executes a same-document Blob Worker handshake during startup. Recovery verifies opaque-origin parent-DOM denial, its inner `connect-src 'none'` and `worker-src 'none'` directives, and the outer Network Worker RPC identity. The shell revokes the Worker Blob URL only after its explicit ready message. Failure of any check keeps queries/scanning disabled.
- Evo SDK 4.1.1 exposes one combined browser facade and no package-exported read-only subpath. Viewer invokes only proof/read methods. Recovery confines that combined facade to the secret-free Network Worker, exposes only fixed read RPC operations, and retains static rejection of known write calls.
- Release WASM compilation remaps the workspace, Cargo and Rustup roots. Both the build and generated-WASM verifier reject private Unix/macOS/Windows user-profile paths before distribution.
- None of the three artifacts uses browser persistence. Wallet Activity Viewer and Wallet Discovery Scanner results are constructed with DOM nodes and `textContent`.
- Viewer tab changes clear the previous input, rendered results, diagnostics, and export state. Core is the default tab; Platform and Orchard must be selected explicitly.
- Viewer CSV/JSON downloads are generated locally from the current loaded snapshot. They never include an Orchard viewing key. CSV text is hardened against spreadsheet formula injection, and JSON converts arbitrary-size integers to exact decimal strings instead of lossy JavaScript numbers.
- The Wallet Activity Viewer clears its copied boundary buffer, concatenated note buffers, and scan-local key string where practical. As with the Wallet Key Derivation Tool, garbage-collected strings and WASM-derived key structures cannot be guaranteed erased.
- Recovery retains visible phrase/passphrase controls by default so an explicitly changed scan configuration can be run again; an opt-in clears those controls at scan start and then requires re-entry. No hidden reusable phrase cache is retained. Mutable seed/input objects are scrubbed after each wallet attempt and the secret-guard registry is cleared on every exit. Immutable JavaScript strings and engine-internal copies cannot be guaranteed erased.
- Recovery sends exact locally derived Core P2PKH addresses over fixed RPC in batches of 50, exact Platform P2PKH addresses to the Worker's proof-verified DAPI client in batches of 100, and identity public-key hashes to proof-verified DAPI. Core uses DashScan only, after synchronization and indexed-tip checks; the UI labels it as a single-source result. Orchard RPC requests contain only aligned `(start_position, count)` ranges; the locally derived FVK never leaves the vault and is never an SDK argument.
- Recovery does not construct, derive signing authority for, sign, prove, or broadcast a spend transaction. It reports public recovery metadata for restoration with a standard wallet.
- Public Core and Platform addresses are sent to their respective network services. They cannot spend funds, but the address, IP address, timing, and query pattern are linkable privacy metadata. Enabling historical empty Core rows adds one summary request per such address; CoinJoin wallets can make this both slow and especially distinctive.
- DashScan is a replaceable external index, not a consensus proof. Its `/status` and latest-block checks detect a reported lag or unavailable index. Recovery deliberately uses DashScan alone so an optional comparison provider cannot throttle or fail the entire scan. This improves availability but does not independently prove zero balances; every funded address and path must be checked in a standard Dash wallet before recovery.
- Platform address history is likewise supplied by the replaceable Dash Platform Explorer index after its status reports `synced`. Current balance and nonce are obtained independently through Evo SDK `getWithProof`; the viewer compares both sources, visibly warns on disagreement, and treats the verified DAPI state as authoritative. The Explorer API currently supplies lifetime aggregate amounts but not an address-attributable amount for each individual transition, so no per-transition amount is inferred from raw transition bytes.

## Residual risks and limitations

1. **Host compromise is out of scope.** A malicious OS, browser, extension, firmware, keylogger, or screen capture can steal revealed material. CSP does not protect against already-compromised local code.
2. **JavaScript erasure is not guaranteed.** Strings are immutable and garbage-collected; engines may copy values. DOM controls, clipboard managers, swap, crash dumps, and browser process memory may retain data after clearing.
3. **Concealment is visual only.** Blurring protects against casual observation. Sensitive values still exist in process memory and, once derived, text nodes.
4. **Clipboard is external state.** The app cannot reliably clear all OS clipboard histories. Users must clear the clipboard after sensitive copies.
5. **Standalone integrity depends on verification.** An altered HTML file can bypass its own CSP. Verify the SHA-256 value through a trusted external tool.
6. **DIP17/DIP18 are currently marked Proposed.** They are the official current Platform payment specifications and v4.1.1 behavior, but a later standard/release may require a migration. Do not assume future compatibility without re-review.
7. **Viewer privacy leakage.** A DAPI/quorum operator can observe the user's IP address and full-pool scan timing/volume. The FVK is not transmitted, but network metadata can still be identifying.
8. **Viewer history granularity.** Encrypted-note queries do not expose an exact transition hash or creation timestamp per note. The viewer reports canonical pool order and amounts, not invented transaction IDs/dates; fees and transition types are not reconstructed.
9. **Complete scan requirement.** Spent state and balance are authoritative only after scanning from position zero through the pool end. Cancelled/failed scans are marked partial.
10. **Large operations can exhaust resources or expose query patterns.** The artificial 50-result derivation limit and any convenience recovery-address limit are removed. Offline Worker execution, bounded derivation DOM windows, streamed recovery batches, and a bounded live-finding DOM reduce stalls, but result objects remain in memory for final display/export. A request such as 100,000 addresses is valid yet can consume substantial CPU, memory, bandwidth, provider quota, and time; its sequence is observable by the provider.
11. **Watch-only is not privacy-free.** Bitcoin account descriptors/xpubs expose the address graph, and the directly displayed Dash FVK exposes shielded wallet activity. The reveal gate is intentional; these values should not be published.
12. **Activity Viewer and Discovery Scanner exports preserve activity metadata.** CSV/JSON files can expose queried public addresses, transaction history, recovered shielded addresses, memos, note commitments, nullifiers, and wallet derivation paths. They cannot spend funds, but must be stored and shared as privacy-sensitive wallet records.
13. **Mnemonic entry into a connected browser remains high risk.** Opaque-origin/CSP/Worker separation prevents the honest network stack from sharing a realm with secrets; it cannot protect against a malicious browser or extension, altered artifact, compromised vault dependency, OS, firmware, keylogger, screen capture or process-memory inspection. Prefer a clean dedicated device and move any found funds to a new phrase.
14. **Provider completeness differs from proof validity.** Platform address/identity state and encrypted-note pages are proof-verified. Recovery deliberately uses only the synchronized DashScan index for Dash Core so an optional comparison provider cannot throttle or fail the scan; this is single-provider index trust, not a consensus proof. Viewer and scanner Platform Explorer history likewise remains replaceable index data: the scanner accepts it only after synchronization/network/resource validation and an exact balance cross-check, while proof-verified Platform state stays authoritative.

15. **Orchard history is note-level, not transaction-level.** Recovery can reconstruct received, sent and self/change note totals, spend state, and action/spend pool positions from the FVK and proof-verified encrypted stream. The feed does not supply a transaction hash, fee, block time or calendar timestamp per action, so the UI and export do not infer transaction counts or dates from pool positions.
15. **No external audit.** Dependency reputation, fixed vectors, random self-checks, and cross-implementation tests reduce risk but do not establish absence of implementation or supply-chain vulnerabilities.
16. **Isolation does not prove remote truth or parser correctness.** The Network Worker can return only structured-clone public data, but a compromised provider or defect can still produce hostile/malformed public responses. Vault-side size/shape/exact-integer validators and proof verification fail closed where available; DashScan completeness still requires provider trust.
17. **Embedding protection depends on delivery mode.** CSP `frame-ancestors` is ignored in a `<meta>` policy and has no applicable HTTP response when the artifact is opened through `file://`. Any web host must send `Content-Security-Policy: frame-ancestors 'none'` (preferably with `X-Frame-Options: DENY`) as an HTTP response header.
18. **The guard matches encodings, not meaning.** Registered material is compared verbatim, percent-decoded, base64-decoded, and with separators removed. A different encoding, compression, encryption, or a value split across fields still passes. It is intentionally only a tripwire; security does not depend on it because the secret-holding vault has no network capability and the SDK Worker has no access to vault memory.
19. **A checksum sidecar is not authenticity.** Each `.sha256` file is produced by the same build run as its HTML and travels beside it, so it detects transfer corruption only. GitHub artifact attestations bind CI-built bytes to the tagged repository, workflow and commit. An optional detached OpenPGP signature over the flat release `SHA256SUMS` can additionally record approval by its signing-key owner. Neither mechanism proves that the implementation is safe or cryptographically correct.

## Verification status

The canonical container verification runs TypeScript checks, deterministic JS vectors and independent comparisons (including separate `dashhd` DIP13 mainnet/testnet reproduction), fail-closed startup checks spanning both networks, a maximum child index and cross-protocol master/account extended-key integrity, native Rust tests, a pinned release WASM build and exact committed-byte comparison, generated-WASM derivation/scanner boundary tests, byte-for-byte comparison of two consecutive builds of all three artifacts, and artifact/CSP/storage/checksum scans. Recovery-specific gates assert the opaque sandbox flags; inner network/worker-denied and outer HTTPS CSPs; absence of `allow-downloads`; SHA-256-only inline-script authorization; a fixed no-URL RPC allowlist; semantic RPC address validation; absence of Evo/fetch/direct-download code in the vault graph and BIP39/secret derivation in the Worker graph; an exact two-module shell dependency graph; per-wallet RPC and scan-end export secret-tripwire behavior; ordered bounded scans/gap extension; response validation; funded/spendable filtering; concurrency/order; aligned two-empty Orchard termination with a hard page ceiling; canonical Platform Map keys; exact-integer exports; and both constructor and plain-call dynamic-code surfaces. Separate live tests exercise the same `DirectRecoveryNetworkService` implementation bundled into the Worker with a documented public BIP39 vector on Mainnet/Testnet. Heights are intentionally not fixed because live chain tips advance.

The prior Recovery artifact was visually exercised through a local-only HTTP server in the Codex in-app browser at desktop size and 390×844; it had no horizontal page overflow and completed a public-vector Testnet run through the actual vault RPC channel. The current source increases the expected startup count to 18 by adding two DIP13 vectors and removing the now-forbidden redundant vault Blob Worker check; deterministic artifact verification covers that exact marker set. The in-app browser disallows `file://` navigation, so direct-file startup, clipboard fallback, and shell-brokered CSV/JSON on current Chrome, Firefox, and Safari remain explicit manual release steps rather than falsely claimed automation.

## Release checklist

- Run `./tooling/build-reproducible.sh` from a clean checkout and compare its release checksums with CI. Use native `pnpm verify` for development, not as the byte-level release authority.
- Verify the GitHub build-provenance attestation and independently recompute each artifact's SHA-256 against `SHA256SUMS`. If a release also provides an optional detached OpenPGP signature, verify it as an additional publisher-approval signal. The per-file `.sha256` sidecar is a transfer-corruption check only.
- Copy only `Wallet_Key_Derivation_Tool.html` to the offline device and open it through `file://` while physically disconnected. Open the Wallet Activity Viewer and Wallet Discovery Scanner on a clean connected device because their documented read-only workflows require network access.
- Exercise generate/import, debounced automatic 20-row derivation after mnemonic/passphrase/coin/tab changes, Bitcoin/Dash Core receive-plus-change generation, independent branch selection/paging/export state, a change-branch known-address match, a multi-batch request and cancellation, all eight adapters, Basic table/Advanced cards, the single reveal-all gate, branch-specific Bitcoin watch-only copy/download, individual copy, selection inversion, and Clear Everything.
- Compare one result per protocol with a second trusted offline implementation before using valuable funds.
- Exercise all three viewer modes: a known Dash Core L1 address, a known Platform `dash1k…`/`tdash1k…` address, and a viewing bundle (or raw FVK). Confirm that Core/Platform diagnostics report synchronized indexes and current heights. For Shielded, let the scan reach the pool end and treat any partial scan as non-authoritative; IVK/OVK results remain intentionally limited even after a complete scan.
- Exercise Recovery Single and Batch modes on nonvaluable/public vectors at concurrency 1, 2, and 5; verify stable report order, visible per-section progress, one bounded-memory Orchard page stream per run, a multi-batch Core/Platform range, automatic post-use gap extension, funded/spendable-only versus historical/spent export, a second scan after toggling that option, identity gap stopping, cancellation with queued requests, a complete Orchard scan, and shell-brokered CSV/JSON. Confirm that entering `100000` is accepted and estimated rather than artificially capped. Inspect browser developer tools to confirm only validated public addresses, 20-byte identity public-key hashes, and pool ranges cross the network boundary. Open the final file directly with current Chrome, Firefox, and Safari where available; verify iframe startup, clipboard fallback, and CSV/JSON because the automated in-app browser cannot navigate to `file://`.
- For any real recovery, independently verify each found public address/path and restore with a standard Dash wallet on a clean device. Do not treat this engineering review as a cryptography audit or use the Wallet Discovery Scanner's results as the sole authority for valuable funds.
