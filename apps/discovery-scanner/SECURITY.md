# Wallet Discovery Scanner security boundary

- This application accepts a mnemonic while online and therefore has the highest host-risk profile in the suite. Prefer a clean dedicated device and move recovered funds to a new phrase.
- The mnemonic UI, BIP39/HD derivation and Orchard FVK scanner run inside a sandboxed `srcdoc` Secret Vault with an opaque origin (no `allow-same-origin`), no `allow-downloads`, `connect-src 'none'`, and `worker-src 'none'`. That realm has no Evo SDK, `fetch`, XMLHttpRequest, WebSocket, direct Blob-URL, or download code.
- Evo SDK and every network primitive run in a separate Network Worker created by the outer shell. The worker never receives a mnemonic, passphrase, seed, private/spending/viewing key or derivation callback. A transferred `MessagePort` exposes only ten fixed read operations for Core status/tip/address data, Platform address/identity proofs and history, and Orchard pool pages; no arbitrary URL or SDK method can cross it. Core/Platform address payloads must pass full checksum, network, payload-length, and P2PKH-type validation inside the Worker.
- Phrase, passphrase, seed and derived Orchard FVK are also registered with a last-boundary egress guard. It checks the public RPC payload before it crosses the port, but is deliberately treated as a secondary tripwire rather than the security boundary.
- The guard cannot protect against a malicious browser, extension, modified HTML, compromised OS, screen capture or memory inspection.
- Each phrase owns independent seed, guard, accounting and result state. Batch phrases run sequentially by default; optional two-to-five phrase concurrency preserves ordered result slots but can increase DAPI tail latency. A shared abort-aware semaphore caps aggregate network work at five. Only public trusted Evo connection/quorum state exists in the Network Worker, with separate SDK instances for Platform addresses, identities, and Orchard. Batch Orchard uses a single page stream: each page is applied to every phrase-specific FVK and its byte arrays are wiped before the next page. No full-pool cache, seed, or FVK crosses the RPC channel.
- DAPI operations use a 10-second SDK timeout, disable nested SDK retries, and allow at most two explicit retries through fresh purpose-specific SDK connections with a short bounded backoff. Invalid-argument failures are not retried. Retry exhaustion is represented as a failed, non-authoritative section; it is never converted into a zero balance. A progress heartbeat makes a pending proof/retry distinguishable from a stalled UI.
- Wallet-wide totals are supplied by the Dash adapter with explicit Duff/credit conversion. Fixed mainnet/testnet DIP13 vectors pin the identity path, private key, compressed public key, and HASH160; an independent `dashhd` implementation reproduces them during release verification.
- The outer shell CSP permits HTTPS and Blob workers because its isolated Network Worker and pinned Evo SDK require them. The Network Worker Blob URL is retained until an explicit ready message and then revoked. The inner vault denies all connections and workers. Both immutable inline scripts are authorized by build-time SHA-256 CSP hashes rather than `unsafe-inline`; `'unsafe-eval'` remains forbidden. The SDK has no separate read-only browser entry point, so the release verifier uses the TypeScript compiler AST to reject known transfer, withdrawal, identity-write, or broadcast calls through property access, literal/computed element access, optional chains, and simple aliases. It also rejects Evo wallet API imports and reviewed mnemonic/seed method calls in the connected graph. This remains a defense-in-depth check over known sensitive surfaces, not a type-level proof over future SDK APIs.
- The pinned Evo/wasm-bindgen Worker bundle contains exactly two known dynamic-code constructors in generic or Node-only glue. The browser CSP does not grant `'unsafe-eval'`, active Recovery read paths do not require them, and the build fails if their reviewed count changes or if any appears in the Secret Vault or shell.
- The build graph is a security gate: it rejects Evo/network-service inputs in the vault bundle and secret derivation/guard inputs in the Network Worker bundle. Artifact verification rechecks sandbox flags, both CSPs, the fixed RPC allowlist, response-boundary assumptions and the absence of arbitrary-URL RPC fields. Startup fails closed unless parent-DOM isolation, the vault CSP and the worker handshake are observed at runtime.
- The Orchard WASM build remaps private machine paths; release verification rejects common Unix and Windows user-profile path prefixes in the binary.
- A trapped Orchard WASM scan fails closed and cannot produce an export. The release profile uses `panic=abort`, so Rust destructors do not run after an internal panic and secret-derived bytes may remain in that module's linear memory until the instance is discarded. JavaScript callers still clear mutable viewing-key references in `finally`; adding destructor-only zeroization would not remove this residual panic path.
- Dash Core always scans both receive `/0` and change `/1` branches. Each branch has independent discovery/gap state and extends through 20 addresses following its own last used address; the optional change-display setting in the offline derivation application has no effect on recovery. Platform counts follow their documented key-class model. No convenience maximum is imposed; very large scans can exhaust resources and reveal a distinctive query pattern.
- Historical zero-balance Core/Platform rows and spent/outgoing Orchard activity are off by default. Orchard spent records are still processed internally to reconstruct nullifier state and the exact spendable balance. Enabling history can be extremely slow and privacy-revealing for CoinJoin-heavy wallets.
- Orchard lifetime figures are locally reconstructed note/output aggregates. They distinguish external received, external sent and self/change values and expose proof-verified pool positions, but must not be interpreted as transaction counts, transaction fees, block times or transaction timestamps.
- Platform payment-address and identity balances remain proof-verified through DAPI. Lifetime totals, event counts and first/last-seen timestamps are auxiliary Platform Explorer metadata: the Network Worker requires a synchronized network-matching index, validates the response shape and resource identifier, and the vault rejects the metadata unless its balance exactly equals the DAPI-proof-verified balance. History failure never becomes a zero balance and does not invalidate an otherwise authoritative discovery result.
- Phrase fields remain visible-but-concealed by default so a changed configuration can be scanned again. Optional clear-on-start removes those controls and deliberately requires re-entry; there is no hidden phrase cache for a later scan.
- CSV/JSON is a one-way public-data projection and excludes phrase, passphrase, seed and private/spending/viewing keys. At scan end the scanner serializes both report formats, rejects either if its final text contains a registered raw, hexadecimal, Base64, percent-encoded or split secret representation, caches only the approved public strings, and immediately clears the secret-pattern guard. The vault later sends only a prevalidated report plus `csv`/`json` to a fixed shell export broker; it cannot supply a URL, filename, or MIME type, and the shell creates only a local Blob download.
- The identity lookup field is necessarily a 20-byte opaque HASH160. A compromised vault could misuse successive valid-looking identity hashes as a low-bandwidth covert channel; the isolation protects against a compromised network side, not arbitrary malicious code already executing inside the secret-bearing vault. Verify the artifact hash and use a clean browser/OS.
- Core balances come only from DashScan after its synchronization check and indexed-tip query. This avoids an optional provider making recovery unavailable or throttling a large scan, but DashScan remains an external index rather than a consensus proof. The section always discloses its single-source status, and every funded address/path must be verified with a standard Dash wallet before funds are moved.
- The application does not sign or broadcast transactions. Use a standard Dash wallet for the actual recovery.
- A `<meta>` CSP cannot enforce `frame-ancestors`. Direct `file://` use has no hosting response to configure; if this artifact is served over HTTP, the server must add `Content-Security-Policy: frame-ancestors 'none'` (and preferably `X-Frame-Options: DENY`) to prevent clickjacking.
