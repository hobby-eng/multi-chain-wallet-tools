# Wallet Discovery Scanner

Network-enabled standalone scanner with a protocol-neutral extension boundary. The current Multi-Chain build provides Dash recovery while remaining ready for additional coin adapters; Dash Community is Dash-only. It derives selected Dash Core receive/change addresses, optional Dash mobile/CoinJoin/funding/provider P2PKH recovery families, Platform payment addresses, Platform identities and an Orchard account locally from one or several BIP39 phrases. Dash Core, Platform addresses, Platform identities and Orchard are four independently selectable top-level components. Additional Core path families appear and run only when Dash Core is selected. Build outputs: `dist/discovery-scanner/Wallet_Discovery_Scanner.html` and `dist/dash-community/discovery-scanner/Dash_Community_Discovery_Scanner.html`.

When selected, Dash Core recovery scans both BIP44 branches—receive `/0` and change `/1`—with independent post-use gap tracking. This is not controlled by the optional change-display checkbox in the separate offline Wallet Key Derivation Tool: the Scanner covers both branches so it does not miss spendable change.

Additional opt-in Core-chain families cover known mnemonic-derived Dash P2PKH balance paths beyond standard desktop BIP44. Legacy mobile Core scans `m/0'/{0,1}/i`: Dash Wallet for Android used it by default through v5.17, changed the default to BIP44 in v5.18 (May 2018), and retained the old path for backward-compatible recovery. Mobile CoinJoin/DIP9 scans `m/9'/coin_type'/4'/0'/{0,1}/i`. It is a current, deliberately separate mobile path rather than a retired legacy path: isolating high-activity CoinJoin keys permits independent discovery/gap limits and pruning of used keys from mobile BIP37 bloom filters. Dash Core desktop CoinJoin instead uses ordinary BIP44 receive/change chains. Identity asset-lock funding scans registration `5'/1'/i`, unbound top-up `5'/2'/i`, identity-bound top-up `5'/2'/registration_index'/i`, invitation `5'/3'/i'`, Platform-address top-up `5'/4'/i'`, and shielded-address top-up `5'/5'/i'` below `m/9'/coin_type'`. These are ordinary L1 staging addresses used to fund Platform credits, not Identity IDs or Identity authentication keys, so unconsumed DASH can remain on them. Masternode holdings scans `m/9'/coin_type'/3'/0'/i`, the masternode collateral holding path that DashSync (iOS, `DSMasternodeHoldingsDerivationPath`, reference `ProviderFunds`) and dashj (Android, `DerivationPathFactory.masternodeHoldingsDerivationPath()`, key chain `MASTERNODE_HOLDINGS`, commented "1000 DASH for masternode") both implement with a non-hardened leaf. DashSync's `DSLocalMasternode` pays the 1000 DASH ProRegTx collateral output to this path when a masternode is registered without an external collateral UTXO, and later reclaims it from there. Dash Core and the consumer Dash Wallet apps (`dash-wallet`, `dashwallet-ios`) never fund it, and the DIP9 assignments table lists `3'/0'` as reserved, so it matters only for masternodes registered through DashSync-based software. Provider owner/voting/operator/platform-node paths are signing credentials and are not balance-scanned. Mainnet uses coin type `5'`; testnet uses `1'`. Contact-payment paths require identity/contact metadata and cannot be bounded from a mnemonic alone.

Path definitions are checked against immutable upstream sources: [DIP9](https://github.com/dashpay/dips/blob/be4f7c130e30eaed2d910bb54554b608b52701b1/dip-0009.md), [DIP9 assignments](https://github.com/dashpay/dips/blob/22aae1d43fe46f87084fa6fab73c83eb96961452/dip-0009/assignments.md), and the current [rust-dashcore key-wallet account types](https://github.com/dashpay/rust-dashcore/blob/7e315af582bc6ec9c088447a7699099b5fbf0f96/key-wallet/src/account/account_type.rs). Numeric `DSDerivationPathReference` enum values are classifications, not HD child numbers; the unsupported `12'`/`13'` fallback paths are intentionally not scanned.

The single HTML contains two browser security realms. The visible application runs in a sandboxed `srcdoc` **Secret Vault** without `allow-same-origin` or `allow-downloads`; its CSP sets both `connect-src 'none'` and `worker-src 'none'`, so the realm that receives the mnemonic, passphrase, seed and FVK cannot open a network connection, create a worker, or initiate a download. A separate outer **Network Worker** embeds Evo SDK and owns every `fetch`/DAPI operation. The vault can reach it only through a transferred `MessagePort` whose typed protocol exposes ten fixed read operations; it accepts no arbitrary URL, request body, SDK method name or executable callback. Core RPC input is decoded as network-bound Base58Check P2PKH; Platform input is decoded as network-bound Bech32m DIP18 P2PKH. Identity queries remain a deliberate 20-byte HASH160 channel because those values are the actual public lookup keys. Scanner-specific validators check every structured-clone response before it affects balances. The existing `SecretEgressGuard` remains as a second tripwire before public RPC arguments leave the vault, but browser-realm/CSP separation—not pattern matching—is the primary boundary.

This independent scanner integrates the official open-source Dash Platform Evo/WASM SDK, specifications and Dash Orchard fork without claiming upstream authorship or endorsement. See the repository [attribution](../../ATTRIBUTION.md) and [third-party notices](../../THIRD_PARTY_NOTICES.md).

The Dash coin adapter is split into focused scanners under `src/coins/dash`. Within every seed phrase, enabled Core-chain, Platform payment, identity and Orchard sections run concurrently while one shared FIFO semaphore caps all network work at five. Batch seed phrases are sequential by default; explicit concurrency from two through five remains available, but can increase DAPI tail latency. Trusted Evo SDK connection/quorum state is isolated by network and purpose (Platform addresses, identities, or Orchard), so one slow subsystem cannot monopolize another subsystem's SDK instance. Each proof call uses a 10-second SDK deadline, no hidden SDK retries, and at most two explicit fresh-connection retries with a short bounded backoff; deterministic invalid requests are not retried. Exhaustion fails the section and is never interpreted as a zero balance. In batch mode, each proof-verified encrypted Orchard page is downloaded once, applied to every local FVK, wiped, and discarded before the next page is requested. DAPI requires 2,048-action-aligned cursors, so a short page advances to the next aligned chunk rather than by its returned item count. Completion requires two proof-verified empty reads at the terminal cursor, and a 4,096-page safety ceiling produces `partial` rather than an unbounded scan. Per-seed progress rows show all active section stages without changing source-line result order.

The app-level registry, progress UI, per-seed result tabs and CSV/JSON export are protocol-neutral so Bitcoin and Ethereum can be added as separate adapters later. Export always covers all completed seed-phrase tabs and contains public recovery metadata only. JSON retains every displayed finding field and section metric. CSV derives its schema from non-skipped scan components: a Core-only report has no empty Platform, Identity or Orchard columns, while a mixed scan contains the union required by its sections. Applicable columns cover derivation path, branch/index, operation and incoming/outgoing event counts, numeric DASH balance and lifetime received/sent/fee values, first/last-seen timestamps, public-key hash, Orchard note value/direction/spend positions, and numeric Orchard section aggregates; other protocol-specific fields remain in metadata. Current-balance mode shows only funded Core/Platform resources and spendable incoming Orchard notes. Funded Core and Platform resources are always enriched with available lifetime totals and first/last-seen timestamps; the history switch additionally exposes zero-balance, spent and outgoing activity. Platform current balances and identity discovery remain DAPI-proof-verified. Historical Platform metadata comes from a synchronized Platform Explorer index and is accepted only when its current balance exactly matches DAPI, so unavailable or inconsistent history produces a warning without discarding the authoritative balance result. Orchard statistics distinguish external received/sent notes from self/change, count spendable/spent/memo-bearing notes, and record first/last activity and spend positions. These are proof-verified pool-action positions rather than transaction counts or calendar timestamps because the encrypted page feed does not expose per-action transaction metadata. Re-running after changing the history switch creates a fresh run and replaces the prior report. Each wallet begins with a unit-safe aggregate overview, and zero-result messages explicitly name their section. Identity results include logical proof count, wall time, and DAPI average/maximum latency; Evo SDK 4.1.1 requires roughly two proof calls per empty identity candidate.

DashScan is the sole Core index in this build. The scanner requires its synchronization status to be `ok`, records the indexed Core height, and parses exact integer duff balances and transaction counts. When DashScan retains a `firstSeenTx` but reports a null first-block timestamp (observed for some special-transaction outputs), the isolated network service resolves that public transaction through DashScan and uses its validated timestamp as `First seen`. This removes optional-provider outages, throttling, and disagreements from the recovery path, but it also means the Core result is single-source and not a consensus proof. The UI marks that limitation and instructs the user to verify every funded address in a standard Dash wallet before recovery.

```bash
pnpm build:discovery-scanner
node apps/discovery-scanner/scripts/verify-discovery-scanner-artifact.mjs
```

The build fails if the vault bundle contains Evo SDK, the network service, or the direct browser-download helper, or if the Network Worker imports mnemonic/BIP39/derivation/guard modules. CSV/JSON report text crosses a separate fixed export message; the trusted shell chooses the filename/MIME and creates a local Blob, while the vault receives only success/failure. Artifact verification independently checks the opaque sandbox flags, both CSPs, SHA-256-authorized inline scripts, fixed RPC operation set, absence of direct network/download primitives in vault source, absence of arbitrary-URL RPC input, exactly one pinned Orchard WASM, forbidden signing/broadcast calls, and the HTML checksum. Startup keeps scanning disabled until it proves that the vault cannot read its parent DOM, sees its own network- and worker-denied CSP, completes cryptographic tests including fixed DIP13 vectors, and receives the expected Network Worker handshake.

The scanner does not construct, sign or broadcast recovery transactions. Restore found funds with a standard wallet after independently verifying the public address/path. Read [SECURITY.md](SECURITY.md) before entering any phrase into this connected application.
