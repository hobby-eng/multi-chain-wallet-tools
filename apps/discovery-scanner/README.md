# Wallet Discovery Scanner

Network-enabled standalone scanner with a protocol-neutral extension boundary. The Multi-Chain build supports Bitcoin, Ethereum and Dash; the Dash Community build is physically and visually Dash-only. Bitcoin recovery scans BIP44, BIP49, BIP84 and BIP86 receive/change chains through a 20-address post-use gap. Mainnet uses Blockchain.com's lightweight balance endpoint for validated batches of up to 100 addresses, then falls back to BlockCypher's independently operated 100-address batch endpoint and Blockchain.com's separate multi-address endpoint; both networks retain bounded, rotating Blockstream.info/Mempool.space per-address requests as the final fallback after transport, timeout, HTTP, JSON, or schema failures. Validated public Bitcoin address states are retained in worker memory for five minutes so presentation-only reruns do not consume provider quota. Ethereum recovery scans native ETH and nonce state for three common EOA layouts through batches of up to 100 addresses (201 JSON-RPC calls for balance, nonce and one shared block height) using Ethereum PublicNode: Standard BIP44/MetaMask/Trezor `m/44'/60'/account'/0/index`, Ledger Live `m/44'/60'/(account + index)'/0/0`, and Legacy Ledger/MEW `m/44'/60'/0'/index`. Each layout has an independent 20-address post-use gap, while overlapping addresses are queried and counted once. Every coin adapter can declare an optional custom-path capability, so current and future coins can expose their own address formats without coin-specific controller code. Bitcoin currently offers P2PKH, P2SH-P2WPKH, P2WPKH and BIP86 P2TR; Ethereum offers EIP-55 EOAs; Dash offers Core P2PKH. A custom template must contain exactly one `{index}` or `{index}'` segment. ERC-20 tokens and contract wallets are intentionally outside Ethereum scope. Dash recovery derives selected Core receive/change addresses, optional mobile/CoinJoin/provider paths, Platform payment addresses, Platform identities and an Orchard account locally from one or several BIP39 phrases. Dash Core requests up to 100 P2PKH addresses from DashScan at once, while Platform address proofs already use the DAPI maximum of 100 addresses. Dash Core, Platform addresses, Platform identities and Orchard are four independently selectable top-level components. Additional Core path families appear and run only when Dash Core is selected. Build outputs: `dist/discovery-scanner/Wallet_Discovery_Scanner.html` and `dist/dash-community/discovery-scanner/Dash_Community_Discovery_Scanner.html`.

When selected, Dash Core recovery scans both BIP44 branches—receive `/0` and change `/1`—with independent post-use gap tracking. This is not controlled by the optional change-display checkbox in the separate offline Wallet Key Derivation Tool: the Scanner covers both branches so it does not miss spendable change.

Additional opt-in Core-chain families cover known mnemonic-derived Dash P2PKH balance paths beyond standard desktop BIP44. Legacy mobile Core scans `m/0'/{0,1}/i`: Dash Wallet for Android used it by default through v5.17, changed the default to BIP44 in v5.18 (May 2018), and retained the old path for backward-compatible recovery. Mobile CoinJoin/DIP9 scans `m/9'/coin_type'/4'/0'/{0,1}/i`. It is a current, deliberately separate mobile path rather than a retired legacy path: isolating high-activity CoinJoin keys permits independent discovery/gap limits and pruning of used keys from mobile BIP37 bloom filters. Dash Core desktop CoinJoin instead uses ordinary BIP44 receive/change chains. Identity registration funding is linked only after an Identity is found: the scanner loads the Identity's actual L1 asset-lock transaction, displays its ordinary BIP44 funding inputs, extracts the credit-key HASH160 from the special transaction payload, and matches it against `m/9'/coin_type'/5'/1'/i`. That payload credit key owns Platform credits; it is not an ordinary spendable L1 address or UTXO, and DashScan does not index it as one. This linkage does not reverse-discover orphaned or unconsumed asset locks when no Identity is known. Masternode holdings scans `m/9'/coin_type'/3'/0'/i`, the masternode collateral holding path that DashSync (iOS, `DSMasternodeHoldingsDerivationPath`, reference `ProviderFunds`) and dashj (Android, `DerivationPathFactory.masternodeHoldingsDerivationPath()`, key chain `MASTERNODE_HOLDINGS`, commented "1000 DASH for masternode") both implement with a non-hardened leaf. DashSync's `DSLocalMasternode` pays the 1000 DASH ProRegTx collateral output to this path when a masternode is registered without an external collateral UTXO, and later reclaims it from there. Dash Core and the consumer Dash Wallet apps (`dash-wallet`, `dashwallet-ios`) never fund it, and the DIP9 assignments table lists `3'/0'` as reserved, so it matters only for masternodes registered through DashSync-based software. Provider owner/voting/operator/platform-node paths are signing credentials and are not balance-scanned. Mainnet uses coin type `5'`; testnet uses `1'`. Contact-payment paths require identity/contact metadata and cannot be bounded from a mnemonic alone.

Path definitions are checked against immutable upstream sources: [DIP9](https://github.com/dashpay/dips/blob/be4f7c130e30eaed2d910bb54554b608b52701b1/dip-0009.md), [DIP9 assignments](https://github.com/dashpay/dips/blob/22aae1d43fe46f87084fa6fab73c83eb96961452/dip-0009/assignments.md), and the current [rust-dashcore key-wallet account types](https://github.com/dashpay/rust-dashcore/blob/7e315af582bc6ec9c088447a7699099b5fbf0f96/key-wallet/src/account/account_type.rs). Numeric `DSDerivationPathReference` enum values are classifications, not HD child numbers; the unsupported `12'`/`13'` fallback paths are intentionally not scanned.

The single HTML contains two browser security realms. The visible application runs in a sandboxed `srcdoc` **Secret Vault** without `allow-same-origin` or `allow-downloads`; its CSP sets both `connect-src 'none'` and `worker-src 'none'`, so the realm that receives the mnemonic, passphrase, seed and FVK cannot open a network connection, create a worker, or initiate a download. A separate outer **Network Worker** embeds Evo SDK and owns every `fetch`/DAPI operation. The vault can reach it only through a transferred `MessagePort` whose typed protocol exposes a fixed set of coin-specific read operations; it accepts no arbitrary URL, request body, SDK method name or executable callback. Bitcoin, Ethereum, Dash Core and Platform public inputs are strictly validated before their fixed provider operation runs. Identity queries remain a deliberate 20-byte HASH160 channel because those values are the actual public lookup keys. Scanner-specific validators check every structured-clone response before it affects balances. The existing `SecretEgressGuard` remains as a second tripwire before public RPC arguments leave the vault, but browser-realm/CSP separation—not pattern matching—is the primary boundary.

This independent scanner integrates the official open-source Dash Platform Evo/WASM SDK, specifications and Dash Orchard fork without claiming upstream authorship or endorsement. See the repository [attribution](../../ATTRIBUTION.md) and [third-party notices](../../THIRD_PARTY_NOTICES.md).

The Dash coin adapter is split into focused scanners under `src/coins/dash`. Within every seed phrase, enabled Core-chain, Platform payment, identity and Orchard sections run concurrently while one shared FIFO semaphore caps all network work at five. Batch seed phrases are sequential by default; explicit concurrency from two through five remains available, but can increase DAPI tail latency. Trusted Evo SDK connection/quorum state is isolated by network and purpose (Platform addresses, identities, or Orchard), so one slow subsystem cannot monopolize another subsystem's SDK instance. Identity discovery derives the official ECDSA_SECP256K1 authentication key, whose key type is globally unique in Platform state, and therefore performs one unique-key proof lookup per candidate rather than following every miss with an inapplicable non-unique-key lookup. At most two Identity lookups share the SDK connection concurrently, leaving network capacity for the other scan sections and avoiding five-request proof bursts. Each proof call uses a 10-second SDK deadline, no hidden SDK retries, and at most three explicit fresh-connection attempts with a short bounded backoff; deterministic invalid requests are not retried. Exhaustion fails the section and is never interpreted as a zero balance. In batch mode, each proof-verified encrypted Orchard page is downloaded once, applied to every local FVK, wiped, and discarded before the next page is requested. DAPI requires 2,048-action-aligned cursors, so a short page advances to the next aligned chunk rather than by its returned item count. Completion requires two proof-verified empty reads at the terminal cursor, and a 4,096-page safety ceiling produces `partial` rather than an unbounded scan. Per-seed progress rows show all active section stages without changing source-line result order.

The app-level registry, progress UI, per-seed result tabs and CSV/JSON export are protocol-neutral. Multi-Chain registers Bitcoin, Ethereum and Dash, while the Dash Community entry point registers only Dash and its generated HTML omits the coin selector. Inside every Dash seed-phrase result a second tab row splits the report by component — Dash Core · L1 (BIP44 plus every opt-in Core-compatible P2PKH family), Platform addresses, Platform identities and Orchard pool — so addresses and identities are never mixed in one list; the selected component persists while switching between batch seed phrases, and each tab shows its funded/listed count and state. Bitcoin and Ethereum results use their own single protocol section. Export always covers all completed seed-phrase tabs and contains public recovery metadata only. JSON retains every displayed finding field and section metric. CSV derives its schema from non-skipped scan components: a Core-only report has no empty Platform, Identity or Orchard columns, while a mixed scan contains the union required by its sections. Applicable columns cover derivation path, branch/index, operation and incoming/outgoing event counts, numeric balance and lifetime received/sent/fee values, first/last-seen timestamps, public-key hash, Orchard note value/direction/spend positions, and numeric Orchard section aggregates; other protocol-specific fields remain in metadata. Current-balance mode shows only funded Core/Platform resources and spendable incoming Orchard notes. Funded Core and Platform resources are always enriched with available lifetime totals and first/last-seen timestamps; the history switch additionally exposes zero-balance, spent and outgoing activity. Platform current balances and identity discovery remain DAPI-proof-verified. Historical Platform metadata comes from a synchronized Platform Explorer index and is accepted only when its current balance exactly matches DAPI, so unavailable or inconsistent history produces a warning without discarding the authoritative balance result. Orchard statistics distinguish external received/sent notes from self/change, count spendable/spent/memo-bearing notes, and record first/last activity and spend positions. These are proof-verified pool-action positions rather than transaction counts or calendar timestamps because the encrypted page feed does not expose per-action transaction metadata. Re-running after changing the history switch creates a fresh run and replaces the prior report. Each wallet begins with a unit-safe aggregate overview, and zero-result messages explicitly name their section. Identity results include logical proof count, wall time, and DAPI average/maximum latency; Evo SDK 4.1.1 performs one proof call per empty standard ECDSA identity candidate.

Dash Core L1 findings are designed as practical recovery records rather than bare address matches. Each result keeps the exact scan family, branch, derivation path, address index, current balance and public-key hash together with available lifetime received/sent totals and first/last activity. When an Identity is discovered, its actual asset-lock transaction and ordinary L1 funding inputs are linked without confusing them with the embedded Platform credit key.

DashScan is the sole Core index in this build. The scanner requires its synchronization status to be `ok`, records the indexed Core height, and parses exact integer duff balances and transaction counts. When DashScan retains a `firstSeenTx` but reports a null first-block timestamp (observed for some special-transaction outputs), the isolated network service resolves that public transaction through DashScan and uses its validated timestamp as `First seen`. This removes optional-provider outages, throttling, and disagreements from the recovery path, but it also means the Core result is single-source and not a consensus proof. The UI marks that limitation and instructs the user to verify every funded address in a standard Dash wallet before recovery.

```bash
pnpm build:discovery-scanner
node apps/discovery-scanner/scripts/verify-discovery-scanner-artifact.mjs
```

The build fails if the vault bundle contains Evo SDK, the network service, or the direct browser-download helper, or if the Network Worker imports mnemonic/BIP39/derivation/guard modules. CSV/JSON report text crosses a separate fixed export message; the trusted shell chooses the filename/MIME and creates a local Blob, while the vault receives only success/failure. Artifact verification independently checks the opaque sandbox flags, both CSPs, SHA-256-authorized inline scripts, fixed RPC operation set, absence of direct network/download primitives in vault source, absence of arbitrary-URL RPC input, exactly one pinned Orchard WASM, forbidden signing/broadcast calls, and the HTML checksum. Startup keeps scanning disabled until it proves that the vault cannot read its parent DOM, sees its own network- and worker-denied CSP, completes cryptographic tests including fixed DIP13 vectors, and receives the expected Network Worker handshake.

The scanner does not construct, sign or broadcast recovery transactions. Restore found funds with a standard wallet after independently verifying the public address/path. Read [SECURITY.md](SECURITY.md) before entering any phrase into this connected application.
