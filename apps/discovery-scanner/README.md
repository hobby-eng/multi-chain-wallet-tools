# Wallet Discovery Scanner

Network-enabled standalone scanner with a protocol-neutral extension boundary. The Multi-Chain build supports Bitcoin, Ethereum and Dash; the Dash Community build is physically and visually Dash-only. Bitcoin discovery scans BIP44, BIP49, BIP84 and BIP86 receive/change chains through a 20-address post-use gap. Mainnet uses Blockchain.com's lightweight balance endpoint for validated batches of up to 100 addresses, then falls back to BlockCypher's independently operated 100-address batch endpoint and Blockchain.com's separate multi-address endpoint; both networks retain bounded, rotating Blockstream.info/Mempool.space per-address requests as the final fallback after transport, timeout, HTTP, JSON, or schema failures. Every new scan requests fresh public state and index status; results are not cached between runs, and first-party HTTP requests bypass the browser cache. Duplicate addresses within one scan are still queried and counted once. Ethereum discovery scans native ETH and nonce state for three common EOA layouts through batches of up to 100 addresses (one head request followed by up to 200 balance/nonce calls pinned to that explicit block height; separate batches can observe different heights) using Ethereum PublicNode: Standard BIP44/MetaMask/Trezor `m/44'/60'/account'/0/index`, Ledger Live `m/44'/60'/(account + index)'/0/0`, and Legacy Ledger/MEW `m/44'/60'/0'/index`. Each layout has an independent 20-address post-use gap, while overlapping addresses are queried and counted once. Every coin adapter can declare an optional custom-path capability, so current and future coins can expose their own address formats without coin-specific controller code. Bitcoin currently offers P2PKH, P2SH-P2WPKH, P2WPKH and BIP86 P2TR; Ethereum offers EIP-55 EOAs; Dash offers Core P2PKH. A custom template must contain exactly one `{index}` or `{index}'` segment. ERC-20 tokens and contract wallets are intentionally outside Ethereum scope. Dash discovery derives selected Core receive/change addresses, optional mobile/CoinJoin/provider paths, Platform payment addresses, Platform identities and an Orchard account locally from one or several BIP39 phrases. Dash Core requests up to 100 P2PKH addresses from DashScan at once, while Platform address proofs already use the DAPI maximum of 100 addresses. Dash Core, Platform addresses, Platform identities and Orchard are four independently selectable top-level components. Additional Core path families appear and run only when Dash Core is selected. Build outputs: `dist/multi-chain-edition/discovery-scanner/Wallet_Discovery_Scanner.html` and `dist/dash-community-edition/discovery-scanner/Dash_Community_Discovery_Scanner.html`.

When selected, Dash Core recovery scans both BIP44 branches—receive `/0` and change `/1`—with independent post-use gap tracking. This is not controlled by the optional change-display checkbox in the separate offline Wallet Key Derivation Tool: the Scanner covers both branches so it does not miss spendable change.

Additional opt-in Core-chain families cover known mnemonic-derived Dash P2PKH balance paths beyond standard desktop BIP44. Legacy mobile Core scans `m/0'/{0,1}/i`: Dash Wallet for Android used it by default through v5.17, changed the default to BIP44 in v5.18 (May 2018), and retained the old path for backward-compatible recovery. Dash Mobile CoinJoin · DIP9 scans `m/9'/coin_type'/4'/account'/{0,1}/i`, with account zero as the default. It is a current, deliberately separate mobile path rather than a retired legacy path: isolating high-activity CoinJoin keys permits independent discovery/gap limits and pruning of used keys from mobile BIP37 bloom filters. Dash Core desktop CoinJoin instead uses ordinary BIP44 receive/change chains. Identity registration funding is linked only after an Identity is found: the scanner loads the Identity's actual L1 asset-lock transaction, displays its ordinary BIP44 funding inputs, extracts the credit-key HASH160 from the special transaction payload, and matches it against `m/9'/coin_type'/5'/1'/i`. That payload credit key owns Platform credits; it is not an ordinary spendable L1 address or UTXO, and DashScan does not index it as one. This linkage does not reverse-discover orphaned or unconsumed asset locks when no Identity is known. Masternode holdings scans `m/9'/coin_type'/3'/0'/i`, the masternode collateral holding path that DashSync (iOS, `DSMasternodeHoldingsDerivationPath`, reference `ProviderFunds`) and dashj (Android, `DerivationPathFactory.masternodeHoldingsDerivationPath()`, key chain `MASTERNODE_HOLDINGS`, commented "1000 DASH for masternode") both implement with a non-hardened leaf. DashSync's `DSLocalMasternode` pays the 1000 DASH ProRegTx collateral output to this path when a masternode is registered without an external collateral UTXO, and later reclaims it from there. Dash Core and the consumer Dash Wallet apps (`dash-wallet`, `dashwallet-ios`) never fund it, and the DIP9 assignments table lists `3'/0'` as reserved, so it matters only for masternodes registered through DashSync-based software. Provider owner/voting/operator/platform-node paths are signing credentials and are not balance-scanned. Mainnet uses coin type `5'`; testnet uses `1'`. Contact-payment paths require identity/contact metadata and cannot be bounded from a mnemonic alone.

Path definitions are checked against immutable upstream sources: [DIP9](https://github.com/dashpay/dips/blob/161637b85d735fa02b85d28d1214157a7e7bbe75/dip-0009.md), [DIP9 assignments](https://github.com/dashpay/dips/blob/a4d46dd2d1d53471fe68912ec1b18e17bad9b76c/dip-0009/assignments.md), and the current [rust-dashcore key-wallet account types](https://github.com/dashpay/rust-dashcore/blob/7e315af582bc6ec9c088447a7699099b5fbf0f96/key-wallet/src/account/account_type.rs). Numeric `DSDerivationPathReference` enum values are classifications, not HD child numbers; the unsupported `12'`/`13'` fallback paths are intentionally not scanned.

The single HTML contains two browser security realms. The visible application runs in a sandboxed `srcdoc` **Secret Vault** without `allow-same-origin` or `allow-downloads`; its CSP sets both `connect-src 'none'` and `worker-src 'none'`, so the realm that receives the mnemonic, passphrase, seed and FVK cannot open a network connection, create a worker, or initiate a download. A separate outer **Network Worker** embeds Evo SDK and owns every `fetch`/DAPI operation. The vault can reach it only through a transferred `MessagePort` whose typed protocol exposes a fixed set of coin-specific read operations; it accepts no arbitrary URL, request body, SDK method name or executable callback. Bitcoin, Ethereum, Dash Core and Platform public inputs are strictly validated before their fixed provider operation runs. Identity queries remain a deliberate 20-byte HASH160 channel because those values are the actual public lookup keys. Scanner-specific validators check every structured-clone response before it affects balances. The existing `SecretEgressGuard` remains as a second tripwire before public RPC arguments leave the vault, but browser-realm/CSP separation—not pattern matching—is the primary boundary.

This independent scanner integrates the official open-source Dash Platform Evo/WASM SDK, specifications and Dash Orchard fork without claiming upstream authorship or endorsement. See the repository [attribution](../../ATTRIBUTION.md) and [third-party notices](../../THIRD_PARTY_NOTICES.md).

Original project code is released under the repository's [MIT License](../../LICENSE); embedded dependencies retain their separately listed licenses.

The Dash coin adapter is split into focused scanners under `src/coins/dash`. Within every seed phrase, enabled Core-chain, Platform payment, identity and Orchard sections run concurrently while one shared FIFO semaphore caps all network work at five. Batch seed phrases are sequential by default; explicit concurrency from two through five remains available, but can increase DAPI tail latency. Trusted Evo SDK connection/quorum state is isolated by network and purpose (Platform addresses, identities, or Orchard), so one slow subsystem cannot monopolize another subsystem's SDK instance. Identity discovery derives the official ECDSA_SECP256K1 authentication key, whose key type is globally unique in Platform state, and therefore performs one unique-key proof lookup per candidate rather than following every miss with an inapplicable non-unique-key lookup. At most two Identity lookups share the SDK connection concurrently, leaving network capacity for the other scan sections and avoiding five-request proof bursts. Each proof call uses a 10-second SDK deadline, no hidden SDK retries, and at most three explicit fresh-connection attempts with a short bounded backoff; deterministic invalid requests are not retried. Exhaustion fails the section and is never interpreted as a zero balance. In batch mode, each proof-verified encrypted Orchard page is downloaded once, applied to every local FVK, wiped, and discarded before the next page is requested. DAPI requires 2,048-action-aligned cursors, so a short page advances to the next aligned chunk rather than by its returned item count. Completion requires two proof-verified empty reads at the terminal cursor, and a 4,096-page safety ceiling produces `partial` rather than an unbounded scan. Per-seed progress rows show all active section stages without changing source-line result order.

The app-level registry, progress UI, per-seed result tabs and CSV/JSON export are protocol-neutral. Multi-Chain registers Bitcoin, Ethereum and Dash, while the Dash Community entry point registers only Dash and its generated HTML omits the coin selector. Inside every Dash seed-phrase result a second tab row splits the report by component — Dash Core · L1 (BIP44 plus every opt-in Core-compatible P2PKH family), Platform addresses, Platform identities and Orchard pool — so addresses and identities are never mixed in one list; the selected component persists while switching between batch seed phrases, and each tab shows its funded/listed count and state. Bitcoin and Ethereum results use their own single protocol section. Export covers all available wallet reports, including explicitly marked partial sections and contains public discovery metadata only. JSON retains every displayed finding field and section metric. CSV derives its schema from non-skipped scan components: a Core-only report has no empty Platform, Identity or Orchard columns, while a mixed scan contains the union required by its sections. Applicable columns cover derivation path, branch/index, operation and incoming/outgoing event counts, numeric balance and lifetime received/sent/fee values, first/last-seen timestamps, public-key hash, Orchard note value/direction/spend positions, and numeric Orchard section aggregates; other protocol-specific fields remain in metadata. Current-balance mode shows only funded Core/Platform resources and incoming Orchard notes not known to be spent. An incomplete scan or incoming-only viewing key cannot establish their current spendability. Funded Core and Platform resources are always enriched with available lifetime totals and first/last-seen timestamps; the history switch additionally exposes zero-balance, spent and outgoing activity. Platform current balances and identity discovery remain DAPI-proof-verified. Historical Platform metadata comes from a synchronized Platform Explorer index and is accepted only when its current balance exactly matches DAPI, so unavailable or inconsistent history produces a warning without discarding the authoritative balance result. Orchard statistics distinguish external received/sent notes from self/change, count spendable/spent/memo-bearing notes, and record first/last activity and spend positions. These are proof-verified pool-action positions rather than transaction counts or calendar timestamps because the encrypted page feed does not expose per-action transaction metadata. Re-running after changing the history switch creates a fresh run and replaces the prior report. Each wallet begins with a unit-safe aggregate overview, and zero-result messages explicitly name their section. Identity results include logical proof count, wall time, and DAPI average/maximum latency; Evo SDK 4.1.1 performs one proof call per empty standard ECDSA identity candidate.

Dash Core L1 findings are designed as practical recovery records rather than bare address matches. Each result keeps the exact scan family, branch, derivation path, address index, current balance and public-key hash together with available lifetime received/sent totals and first/last activity. When an Identity is discovered, its actual asset-lock transaction and ordinary L1 funding inputs are linked without confusing them with the embedded Platform credit key.

DashScan is the sole Core index in this build. The scanner requires its synchronization status to be `ok`, records the indexed Core height, and parses exact integer duff balances and transaction counts. When DashScan retains a `firstSeenTx` but reports a null first-block timestamp (observed for some special-transaction outputs), the isolated network service resolves that public transaction through DashScan and uses its validated timestamp as `First seen`. This removes optional-provider outages, throttling, and disagreements from the recovery path, but it also means the Core result is single-source and not a consensus proof. The UI marks that limitation and instructs the user to verify every funded address in a standard Dash wallet before recovery.

```bash
pnpm build:discovery-scanner
node apps/discovery-scanner/scripts/verify-discovery-scanner-artifact.mjs
```

The build fails if the vault bundle contains Evo SDK, the network service, or the direct browser-download helper, or if the Network Worker imports mnemonic/BIP39/derivation/guard modules. CSV/JSON report text crosses a separate fixed export message; the trusted shell chooses the filename/MIME and creates a local Blob, while the vault receives only success/failure. Artifact verification independently checks the opaque sandbox flags, both CSPs, SHA-256-authorized inline scripts, fixed RPC operation set, absence of direct network/download primitives in vault source, absence of arbitrary-URL RPC input, exactly one pinned Orchard WASM, forbidden signing/broadcast calls, and the HTML checksum. Startup keeps scanning disabled until it proves that the vault cannot read its parent DOM, sees its own network- and worker-denied CSP, completes cryptographic tests including fixed DIP13 vectors, and receives the expected Network Worker handshake.

The scanner does not construct, sign or broadcast recovery transactions. Restore found funds with a standard wallet after independently verifying the public address/path. Read [SECURITY.md](SECURITY.md) before entering any phrase into this connected application.


## Public-key discovery

Choose **Seed phrase** or **Public keys**. Only the selected tab is used, even if the other tab still contains input. The seed tab supports one phrase or a batch with matching BIP39 passphrases. The public-key tab accepts one key, multiple keys (one per line), or one formatted Dash Orchard viewing bundle as JSON. Its Coin menu sits immediately left of Network. Auto-detect proceeds only when every input identifies exactly one coin; an ambiguous key requires an explicit coin selection before any network request. Pasting input only updates the local preview; press **Scan public keys** to start network discovery.

**Limited public-key coverage:** a public key only covers addresses reachable from that particular key: an account, branch or exact address encodings. It cannot traverse hardened derivation levels or search other wallet accounts. For the broadest search over the supported address families and selected account/range, use the original seed phrase and BIP39 passphrase, if any. Re-encoding a single xpub as Legacy, SegWit or Taproot does not derive the distinct hardened BIP44/49/84/86 accounts. Even seed discovery remains bounded by the selected settings and supported schemes. The same notice is displayed below the public-key field.

A bare SEC1 public key has no unique coin identifier. Multi-Chain requires the user to select the coin when detection is ambiguous; it scans only that coin. Dash Community checks Dash only. Shared account xpubs are likewise restricted to the selected coin, without claiming that depth or an empty response identifies the original wallet. Checksummed Bitcoin descriptors and explicit coin prefixes narrow the scan. Encoded xpub/tpub or viewing-bundle networks take precedence over the network selector; unencoded public keys and Ethereum xpubs use the selected network (Ethereum xpub versions do not distinguish mainnet from Sepolia). Root/master xpubs are rejected because the standard wallet account paths cross hardened derivation levels.

Supported inputs: compressed/uncompressed SEC1 public keys; account or branch xpub/tpub; single-signature SLIP-132 `ypub`/`zpub` and testnet `upub`/`vpub` keys; checksummed `pkh`, `sh(wpkh)`, `wpkh`, and `tr` descriptors; `bitcoin-xpub:`, `ethereum-xpub:`, `dash-core-xpub:`, `dash-coinjoin-xpub:`, `dash-platform-xpub:`, `identity:` (ECDSA key or HASH160); raw Orchard FVK/IVK, a Dash Orchard viewing bundle, or explicitly labeled `orchard-fvk:`, `orchard-ivk:`, `orchard-ovk:`. Dash Core accepts depth-3 account and depth-4 branch xpubs; Dash Mobile CoinJoin accepts depth-4 account and depth-5 branch xpubs; Dash Platform accepts a depth-5 DIP17 key-class xpub. A bare xpub does not encode its hardened family. With Dash selected, accepted depth-3/4 bare keys are interpreted as Core account/branch candidates; use the matching explicit prefix to identify Mobile CoinJoin or Platform key-class material. `ypub`/`upub` select Nested SegWit and `zpub`/`vpub` select Native SegWit; Taproot has no corresponding standardized SLIP-132 public version and requires a `tr(...)` descriptor for exact detection. A raw `xpub`/`tpub` does not encode its coin or hardened BIP44/49/84/86 purpose, so Auto-detect asks for a coin instead of scanning every compatible adapter. A raw 32-byte value is rejected as potentially private. Private keys and seed phrases are rejected in this field before any scan is started.

Only derived addresses, public-key hashes and pool queries cross the network boundary. Extended and viewing keys stay local and are excluded from exports. The minimum count applies per derivable branch; a single curve key is checked exactly at supported address encodings. Unavailable Dash Platform/Identity services do not discard successful Core results. Public-key mode does not launch scans of other coins. Reports and CSV/JSON warnings identify incomplete coverage. Core duffs and Platform credits are converted to a common unit before calculating the DASH total.


## History supplied by coin adapters

Both source modes use `RecoveryCoinAdapter.getHistory(finding, section, network, context)`. The common runner calls this optional capability for displayed resources, validates its `RecoveryHistory` result, and renders/exports the same fields for any registered coin. A future adapter implements this hook without adding coin switches to the UI or exporter. Missing capabilities are explicitly `unsupported`; provider errors are `unavailable` and never remove a discovered balance. Completed Dash seed history is reused rather than fetched twice.

`RecoveryCoinAdapter.amountUnit(section)` independently declares current-balance units. JSON `balanceUnit` and CSV balance-unit columns preserve those units even when historical queries fail. A history response with mismatching units is rejected.

The contract stores exact decimal strings in atomic units plus `asset`, `atomicUnit` and `decimals`. Bitcoin uses satoshis (8), ETH wei (18), Dash Core duffs (8), and Dash Platform credits (11). Null denotes unavailable information, not zero. JSON includes a structured `history` object; CSV adds coin-independent totals in atomic and display units, UTC dates, transaction counts, source, scope and coverage status. These per-address turnover totals must not be summed as net wallet payments: self-transfers/change can appear on both sides.

- Bitcoin: [Esplora address statistics and paginated confirmed history](https://github.com/Blockstream/esplora/blob/master/API.md), with Blockstream/Mempool fallback. Lifetime received/spent totals exclude pending transactions; pending count is separate. `First seen` and `Last seen` come from confirmation block times in UTC. Sent values include consumed address outputs, including change and fees, so an address-specific fee total is not inferred. Complete histories must match address summary totals/counts and an unchanged final summary. At 500 transactions or a 60-second resource deadline the scan is bounded; truncated dates are not presented as lifetime dates.
- Ethereum: [Blockscout transactions](https://docs.blockscout.com/api-reference/get-address-transactions) and [internal transfers](https://docs.blockscout.com/api-reference/get-address-internal-transactions) for Ethereum mainnet/Sepolia. The scope is confirmed native ETH, with sender gas fees separate; reverted transfers do not add value and root calls are not double-counted. `First seen` and `Last seen` come from provider-reported block times in UTC. Tokens, validator withdrawals and mining rewards are outside this scope. Each stream is limited to 1,000 entries and the resource to 60 seconds. Truncated history withholds lifetime sums/dates instead of reporting partial totals as complete.
- Dash Core: existing DashScan lifetime amounts and activity dates. Platform/Identity: synchronized Platform Explorer credit history, checked against the DAPI balance. The report presents only the summary `First seen` / `Last seen` pair rather than separate receipt/spend date ranges. Orchard exposes note values, direction, spend state and pool positions, not per-note calendar dates or lifetime address totals; complete scans provide lifetime section aggregates; partial scans label prefix totals as Observed and withhold current spendable balances.

`First seen` and `Last seen` mean earliest/latest activity within the stated scope; they are not aliases for first receipt/last spending. Provider outages and incomplete coverage are visible in each finding and both exports. The zero-balance-history checkbox still controls which resources are displayed, independently of historical detail enrichment.

The cross-utility monetary-unit review is recorded in [DASH_UNITS_AUDIT.md](../DASH_UNITS_AUDIT.md).

## Seed compatibility

Seed input uses BIP39. Native Electrum seed phrases use a different seed-version and seed-derivation scheme and are not supported. Electrum can also import BIP39 wallets; those require the original BIP39 phrase/passphrase and a supported path. Native Electrum support must be a separate explicit seed format if added later, rather than interpreting its words as BIP39. Legacy depth-1/2 extended keys are not covered by the supported account/branch xpub importer.

### Freshness and incomplete results

Every explicit run starts new balance/history requests and rechecks the Platform Explorer index. First-party HTTP calls use `cache: 'no-store'`. Per-run deduplication still prevents counting one resource twice; SDK connections and the currently displayed public report may stay in memory. No prior run's wallet balance or Explorer synchronization answer is reused. Remote providers can still lag; bypassing browser storage does not establish their freshness or consensus correctness.

Orchard spendability requires a full viewing key and a completed pool traversal. Partial results retain observed note values and known spends, but unconfirmed spendability uses `balanceAtomic: null` in JSON and an empty `balance_atomic`/`balance_dash` cell in CSV. The section has `balanceAvailable: false`; its prefix totals use `Observed`, not `Lifetime`. An incomplete section makes the wallet's combined balance unavailable. Completed components retain their own values. Seed and public-key runs both report incomplete status while allowing public reports to be exported.
