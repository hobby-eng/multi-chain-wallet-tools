# PSBT & Multisig Inspector

Bitcoin address rendering supports mainnet, testnet/signet, and local regtest (`bcrt`) while retaining testnet Base58 and extended-key versions for regtest. Dash exposes only mainnet and testnet. Dash Core v21+ fixed and ranged `sh(multi(...))`/`sh(sortedmulti(...))` policy descriptors use `importdescriptors`; an address-only descriptor fallback and explicitly labeled legacy-wallet `importmulti` command remain copyable. RPC JSON download is available, while executable `.sh` and console `.txt` downloads are intentionally omitted. Generated imports use `timestamp:"now"` and warn that historical recovery requires an earlier timestamp or `0`.

Offline standalone Bitcoin and Dash Core PSBT/Script inspection, multisig-policy construction, experimental watch-only multisig wallet construction, message verification, and BIP38 private-key decryption.

This fourth HTML utility is an early review build. Do not use it with real funds yet; test only with valueless examples or testnet funds until scripts, descriptors, import commands, wallet compatibility, and recovery procedures have been independently verified.

The current implementation decodes Bitcoin PSBT v0/v2 and Dash Core PSBT v0, displays all known and unknown key-value records, derives standard output addresses, reports input values, fees, and clearly labeled fee/current-unsigned-size ratios derived from supplied UTXOs (not verified against the blockchain), decodes Script hex and Bitcoin output descriptors/Miniscript, builds multisig scripts with optional absolute/relative locks or a separately delayed recovery key, verifies public message proofs, and derives deterministic watch-only multisig receive/change ranges from account public keys with explicit origin fingerprints. For PSBT v0 it also derives the unsigned transaction ID, serialized size, virtual size, weight, output Script ASM, and recognized redeem/witness-script policies. Every supplied non-witness UTXO can be expanded into its decoded previous transaction, including decoded previous-input scriptSig pushes, previous signatures and their sighash byte, outputs, chain-specific addresses, human-readable OP_RETURN payloads, scripts, special payload metadata, and the original raw bytes. The exact referenced previous output is highlighted separately and confirmed against the current input prevout. A per-input signing-commitment panel explains supplied signature state, requested or inferred sighash, protected inputs and outputs, opt-in Bitcoin RBF signaling, absolute locktime, and BIP68 relative locktime. Dash explicitly reports that Dash Core does not implement replace-by-fee. BIP32 key-origin values are split into their four-byte master fingerprint and human-readable derivation path.

Dash Purpose48 `m/48'/5'/account'/0'` (testnet `m/48'/1'/account'/0'`) remains an optional wallet-specific P2SH convention. Confirm support with every signer. Dash Core also supports its official signer workflow: obtain public `pkh(.../0/*)` descriptors with `listdescriptors` from dedicated signer wallets, then use their account xpubs in shared `sh(sortedmulti(.../0/*))` and `sh(sortedmulti(.../1/*))` descriptors. The builder accepts complete checksummed pkh descriptors or origin-tagged account xpubs. Never export private descriptors. Preserve the agreed derivation family and key origins; different paths produce different wallets.

For P2SH multisig, individual single-signer receive addresses are not used by the shared wallet. Each shared address is built from one child public key per cosigner at the same branch/index, wrapped into one redeemScript and then hashed into the P2SH address. A watch-only wallet therefore needs all cosigner xpubs plus origin paths; private keys are needed only by signers when spending.

For concrete multisig, derive one child public key from each cosigner at the same agreed branch/index. Both Purpose48 and the official Dash Core signer workflow are supported; do not mix their paths accidentally.

Dash Core descriptor documentation covers `pk()`, `pkh()`, `sh()`, `multi()`, `sortedmulti()`, `addr()`, `raw()`, and `combo()`. No newer Dash L1 P2PKH/P2SH address family was found for this scope. The test suite pins and exercises all four official Dash Core BIP67 `sh(sortedmulti(...))` P2SH vectors from `test/functional/data/rpc_bip67.json` (fixture SHA-256 `9087f6bee68d1cdbcf4d6940d665e1743b7b15c6b576211c40a343a1f433ecaf`). Dash PSBT parser conformance also runs every valid and invalid `decodepsbt` vector in Dash Core's `rpc_psbt.json`, pinned to `dashpay/dash` commit `728f5055836c6d29806412fc7223ac8fe05af991` and fixture SHA-256 `026112af3403edc0b02746352abbdd8d3ab727febdb1f88ae7d5746e023256aa`.

Advanced policy shapes are compiled locally by the pinned `@bitcoinerlab/miniscript` package. Its ASM is serialized into the redeem/witness script, from which the funding address and scriptPubKey are derived. The builder also displays the complete checksummed descriptor, Miniscript fragment, compiled ASM, and safety analysis. For custom Dash P2SH policies, Dash Core does not accept the Miniscript expression as descriptor grammar: the export is instead a valid but non-solvable `raw(scriptPubKey)` watch descriptor, while the complete redeemScript is displayed and must be preserved separately. Dash L1 executes CLTV/CSV, conditionals, and the four supported hashlock opcodes, but Core's wallet does not automatically satisfy these custom branches. Hashlock/preimage policies are contract-style scripts rather than normal multisig wallet recovery. OP_RETURN outputs are not spendable wallet outputs.

Nunchuk-style policy templates map only partly to the named presets. HODL/Zen HODL corresponds to M-of-N after a CLTV/CSV lock. The named flexible, decaying, expanding, and staged recovery presets cover common reviewable shapes; the Multi-Chain edition also accepts custom Bitcoin Miniscript when an exact policy tree is needed.

Bitcoin descriptor coverage is intentionally narrower than Bitcoin Core. The decoder summarizes common wallet descriptors (`pk`, `pkh`, `wpkh`, `sh`, `wsh`, `multi`, `sortedmulti`, `tr`, `rawtr`, `sp`, `multi_a`, `sortedmulti_a`, `addr`, `raw`) and explains Miniscript constants, key checks, CLTV/CSV locks, all four hashlocks, `andor`, `and_v`, `and_b`, `and_n`, `or_b`, `or_c`, `or_d`, `or_i`, `thresh`, `multi`, `multi_a`, and wrappers `a s c t d v j n l u`. Concrete `pk`, `pkh`, `wpkh`, `raw`, `rawtr`, bare `multi`/`sortedmulti`, and supported `sh`/`wsh` Miniscript inputs also show a normalized checksummed descriptor, derived keys, Script hex/ASM, scriptPubKey, output type, address when standard, witness program, and Script size. Two-way multipath xpub expressions expose an explicit branch selector and wildcard index. Recognized WSH and Tapscript fragments receive an additional BitcoinerLab Miniscript safety analysis. Raw Script is decoded operation by operation and only high-confidence templates are inferred because Script does not have a unique inverse Miniscript expression. For BIP-390 `musig(...)` keys inside `tr()`, `rawtr()`, or `sp()`, the selected wildcard index is derived locally, participant keys are sorted and aggregated with Scure BTC Signer's BIP-327 implementation, aggregate-level derivation uses the BIP-328 synthetic xpub construction, and MuSig key-path outputs show their concrete scriptPubKey and address. Plain `rawtr()` is a Bitcoin Core descriptor extension referenced by BIP-390, not a BIP-381 descriptor. Concrete `tr()` binary trees and MuSig2 script-path descriptors are expanded and compiled after selecting the branch/index, with context-checked keys and a maximum depth of 128. General `combo` and Dash `addr` remain analysis-only; Bitcoin `addr` is validated against the selected network and compiled to scriptPubKey; multipath support is limited to two choices, and private-key descriptors remain unsupported.

Hashlock fragments `sha256()`, `hash256()`, `ripemd160()`, and `hash160()` are validated for their exact digest width. Path cards show the Miniscript-required 32-byte preimage independently from signatures and CLTV/CSV locks, and identify HTLC-like policies that combine an immediate preimage branch with a timelocked fallback branch. Descriptor inspection needs only the hash commitment. The separate optional phrase-to-preimage calculator accepts a local secret phrase and displays its derived 32-byte preimage; it does not persist or transmit it.

The policy builder can create HTLC-like outputs and three-stage `or_d(...or_i(...))` recovery policies. Fixed public keys produce a concrete output directly. For staged recovery, origin-tagged ranged xpub expressions such as `/<0;1>/*` are also accepted: `@scure/bip32` derives the selected multipath branch and wildcard index, BitcoinerLab compiles the resulting concrete Miniscript, and the export retains the checksummed ranged descriptor. In the Multi-Chain edition, supported presets can be compiled as P2SH, P2WSH, or a single-leaf P2TR Tapscript output. Portable Bitcoin P2WSH/P2TR presets must pass the Miniscript sanity analysis; repeated keys across branches are rejected. The decaying/expanding shapes repeat keys by construction and require a separately reviewed advanced custom policy rather than a claimed Core-compatible preset. Advanced P2SH policies export a raw watch-only scriptPubKey descriptor and require preserving the separate redeemScript and a tested custom signer. P2SH/P2WSH use `multi()` and compressed keys; Tapscript converts validated compressed input keys to x-only keys and uses `multi_a()`. The Taproot script-path builder delegates output construction to Scure BTC Signer and uses its standard unspendable NUMS internal key, so no key-path signature can bypass the displayed policy. A separate P2TR MuSig2 option creates a BIP-327/BIP-390 cooperative N-of-N key-path output with no Tapscript leaf; it does not claim M-of-N semantics and still requires an external interactive MuSig2 signer. Custom Bitcoin Miniscript remains available as an advanced P2WSH/Tapscript mode. All Taproot and custom Miniscript construction is intentionally absent from the Dash Community edition.

The PSBT inspector names and structurally validates the BIP-373 MuSig2 participant-key, public-nonce, and partial-signature fields. It intentionally does not generate nonces, handle private keys, coordinate signers, or create/verify partial signatures: nonce reuse and interactive-round mistakes can reveal private keys, so signing requires a separately reviewed coordinator.

BIP-390 deliberately spells the descriptor key expression `musig(...)`; that expression selects the modern BIP-327 MuSig2 protocol. It is not legacy MuSig1, and there is no separate standard `musig2(...)` descriptor function to add.

The message verifier is public-data-only. Bitcoin verification uses pinned `btcutil-js` 0.4.1 and its btcd-derived Script engine to check BIP-322 legacy, simple (`smp`), full (`ful`), and proof-of-funds (`pof`) messages, including script-based and multisig challenges supported by BIP-322. Dash verification supports Dash Core compact P2PKH messages with the protocol-compatible Dash signed-message domain. The utility does not expose message signing.

The BIP38 decryptor is the only workflow that handles private-key material. It accepts up to 200 non-EC-multiplied `6P…` encrypted keys with one shared password, verifies every BIP38 address hash against the explicitly selected Bitcoin/Dash network, and progressively reveals each recovered WIF, hexadecimal private key, compression mode, and P2PKH address. A failed key does not stop the rest of the batch. Decryption is local, output secrets are masked by default and hidden again when the page loses visibility or focus, and Clear removes all references from the page controls. Prefer sweeping recovered WIFs into a new wallet.

It deliberately does not sign, finalize, create funded spending transactions, query UTXOs, or broadcast. Those capabilities require a separate reviewed signing boundary and chain-specific transaction tests.

Build:

```bash
pnpm build:psbt-inspector
```

Build outputs: `dist/multi-chain-edition/psbt-inspector/PSBT_Multisig_Inspector.html` and `dist/dash-community-edition/psbt-inspector/Dash_Community_PSBT_Multisig_Inspector.html`.

The historical [documentation/code follow-up](../../docs/audits/audit-06-2026-09-12.md) records descriptor defects and their original remediation. Current regressions validate original MuSig participant/aggregate paths before selecting either supported branch, including nested origins, and enforce centralised script/policy limits. Arbitrary-length multipath tuples remain unsupported.

## Validation boundaries

Implemented PSBT field checks cover required v2 fields and selected scope, version and key/value constraints. This is not complete validation of every registered field: hash-preimage fields 0x0a–0x0d now have exact-width and digest-commitment checks; some additional semantic relationships remain outside the implemented checks. Non-witness UTXOs must match the referenced transaction ID/output; conflicting witness and non-witness UTXOs are rejected. Unknown and proprietary fields remain inspectable. Structural acceptance does not prove that signatures are valid or a transaction can be spent/imported. MuSig2 nonce points and scalar ranges are checked, but partial signatures are not cryptographically verified and the utility does not run a signing or nonce lifecycle.

Custom Tapscript requires valid 32-byte x-only keys; compressed keys must not be pasted as literal Tapscript CHECKSIG keys. Normal descriptor keys are derived and converted in their specified context before compilation. Legacy compressed/uncompressed key rules are separate from SegWit/Tapscript rules. Funding/import compatibility still requires review in the intended wallet.

Bitcoin and Dash ranged import commands create a separate blank, private-keys-disabled descriptor wallet and import active receive/change descriptors without labels. Choose a unique wallet name and independently compare addresses with every cosigner before funding. `timestamp: "now"` is for a new wallet; existing wallets require their earliest possible use time and a historical rescan. P2SH accepts at most 15 compressed keys; Bitcoin P2WSH accepts up to 20. Fixed non-ranged imports remain inactive.

CLI exports select `-testnet` or `-regtest` when that network is selected and set `load_on_startup=true` for new ranged wallets. For Bitcoin signet, replace `-testnet` with `-signet`; signet shares address versions with testnet and cannot be inferred from an address or xpub. Each cosigner origin is preserved independently; different valid origin paths are allowed when all signers agree on the final descriptors.
