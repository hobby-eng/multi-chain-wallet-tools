SeedSigner SeedQR

            

          

          

            What is this?
            

              
SeedQR

              

                Converts a BIP39 recovery phrase into a QR payload for offline transfer or paper backup. Standard SeedQR
                stores four digits per word; CompactSeedQR stores the underlying entropy bytes. SeedSigner documents 12-
                and 24-word payloads; 15-, 18-, and 21-word payloads work here but may not be accepted by external
                readers.
              

              

                Open-source specifications and modules are used. Source code is available from
                SeedSigner SeedQR, uqr for QR
                encoding, and
                paulmillr/qr for
                QR decoding. Every build verifies locked dependency checksums. When GitHub is available, it also
                verifies the exact pinned upstream commits; a mismatch stops the build.
              

            

          

          

            Encode or decode 12-, 15-, 18-, 21-, or 24-word English BIP39 phrases. Check external-reader compatibility
            in “What is this?”.
          

          

            Secret QR. Anyone who scans this QR can recover the wallet. Do not photograph, upload, or
            display it near cameras.
          

          

            
            
          

          

            

              
              
            

            
            
            
            

              
              
            

            

          

          

            
            
            
            
            

              
              
            

            

          

        


        

          

            

              02
              
MHFE encrypted BIP39 backup

            

          

          

            What is this?
            

              
Memory-Hard Feistel Encryption

              

                MHFE is an experimental encryption construction designed by this project's author. It converts a
                checksum-valid 12-, 15-, 18-, 21-, or 24-word English BIP39 phrase into one checksum-valid 24-word BIP39
                container without storing a separate salt, nonce, or tag. It runs twelve 512 MiB Argon2id-backed Feistel
                rounds and can therefore take several minutes on slower computers.
              

              

                Short source phrases carry a recovery fingerprint whose first bits are their ordinary BIP39 checksum. A
                24-word source fills the whole state and cannot carry that fingerprint, so its recovered checksum does
                not prove that the password was correct.
              

              

                An optional 24-word mode can preserve the source's complete final word by repeatedly running the full
                encryption until that word matches. The word is then visible in the encrypted container. This search
                averages about 2,048 complete encryptions, can take many hours depending on the computer, and may finish
                much sooner or later. It is unnecessary for exact recovery and does not verify the password.
              

              

                Read the
                MHFE specification
                and inspect the
                reference implementation. This page embeds the verified v0.3.1 browser module.
              

            

          

          

            Experimental construction. MHFE has not received enough independent cryptographic review
            for protecting real funds. Losing the password or a deliberately selected non-zero PIM makes recovery
            impossible.
          

          

            
            
          

          

            

              
              
            

            
            

              

                

                  
                  
                

                
              

              

                

                  
                  
                

                
              

            

            
            
            

              With the checkbox off, PIM is 0 and does not need to be recorded. This browser module accepts printable
              ASCII passwords so its normalization is exact and reproducible.
            

            
            

              

                Keeps the original final word as a visible check word. It is not required to recover the original phrase.
              

              

                More details
                

                  
Why preserve the final word?

                  

                    A 24-word source uses the entire 256-bit plaintext state, leaving no room for the internal recovery
                    fingerprint carried by shorter sources. Its encrypted container still has a valid BIP39 checksum,
                    but its final word is normally unrelated to the source's final word.
                  

                  

                    This mode repeats the complete memory-hard encryption until the container has exactly the same final
                    word, including its checksum bits. It is useful only when you want that recognizable word to remain
                    visible in the container. Standard mode still recovers the original phrase exactly when the correct
                    password and recorded PIM, if any, are supplied.
                  

                  

                    The search averages about 2,048 attempts and can take many hours. Progress and a device-based
                    estimate appear below. Stop safely discards the unfinished search. Because every result from this
                    mode preserves the word, it does not confirm that the password is correct.
                  

                

              

            

            

              
              
            

            

            

          

          

            

              
              
            

            
            

              

                
                
              

              
            

            
            
            
            
            

              Auto checks the recovery fingerprints for 12, 15, 18, and 21 words; if none matches, it returns the
              24-word interpretation. Use an exact length only as an override. In the extremely unlikely event that
              several short lengths match, every matching phrase is shown. Select the final-word mode only when it was
              used during encryption; it forces 24 words and repeats the same potentially multi-hour search.
            

            

              
              
            

            

            

          

        


        

          

            

              02
              
SLIP-39 mnemonic shares

            

          

          

            What is this?
            

              
SLIP-39 mnemonic shares

              

                Splits secret entropy into standardized mnemonic shares with a threshold. In a 2-of-3 set, any two cards
                recover the secret while one card is insufficient. Each share uses the separate SLIP-39 wordlist.
              

              

                An open-source reference implementation and its official vectors are used. Source code is available from
                Trezor python-shamir-mnemonic. The browser port is maintained by this project. Every build verifies locked dependency checksums.
                When GitHub is available, it also verifies the exact pinned upstream commit; a mismatch stops the build.
              

            

          

          

            SLIP-39 shares have their own 1024-word list, metadata and checksum. They are not BIP39 seed phrases.
          

          

            
            
          

          

            

              
            

            
            

              

                
              

              

                
              

              

                
              

            

            
            
            

              Use the current extendable format for new backups. Select legacy only when compatibility with older
              SLIP-39 software requires it.
            

            

              Compatibility boundary. These shares preserve the entropy of the BIP39 phrase so this
              tool can reconstruct the same words. A wallet that treats them as a native SLIP-39 wallet may derive a
              different wallet.
            

            

              
            

            

          

          

            

              
              
            

            
            
            
            
            

          

        

        

          

            

              02
              
CKD Shamir

            

          

          

            What is this?
            

              
CKD Shamir

              

                Splits BIP39 entropy with Shamir Secret Sharing. Raw uses compact Base64URL records; Words encodes the
                same records with the BIP39 English list. Both are versioned custom CKD formats, not wallet mnemonics.
              

              

                An open-source module is used for GF(256) Shamir arithmetic. Source code is available from
                sharks. The
                versioned CKD envelope and both display encodings are maintained by this project. Every build verifies
                locked dependency checksums. When GitHub is available, it also verifies the exact pinned upstream
                commit; a mismatch stops the build.
              

            

          

          
Choose the representation independently when creating or restoring cards.

          

            
            
          

          

            

              
              
            

            
            

              
              
            

            

              

                
                
              

              

                
                
              

            

            

              Custom CKD format. Raw and Words represent custom CKD Shamir cards. They cannot be
              restored by SLIP-39, SSKR, Codex32, or ordinary wallet software. Preserve every selected card in full.
            

            

              
              
            

            

          

          

            

              
              
            

            

              
              
            

            
            
            

          

        

        

          

            

              02
              
SSKR · Blockchain Commons

            

          

          

            What is this?
            

              
SSKR

              

                Interoperable Sharded Secret Key Reconstruction with share thresholds inside groups and a threshold
                across groups. Encode and Decode support Compact UR and full Bytewords representations of the same
                standard SSKR share.
              

              

                SSKR splits a secret; it does not encrypt one. To protect mnemonic entropy together with its BIP39
                passphrase, use Seed Envelope with an SSKR permit.
              

              

                An open-source module is used for standard SSKR and Bytewords support. Source code is available from
                Blockchain Commons bc-sskr-rust. Every build verifies locked dependency checksums. When GitHub is available, it also verifies the
                exact pinned upstream commit; a mismatch stops the build.
              

            

          

          

            Splits BIP39 entropy with the Blockchain Commons SSKR format. It is separate from CKD Shamir and SLIP-39.
          

          

            
          

          

            
            

              
              
              
Both choices carry the same standard SSKR share data.

              02
              
Gordian Seed Envelope

            

          

          

            What is this?
            

              
Gordian Seed Envelope

              

                Stores BIP39 entropy in a typed Gordian Envelope. One encrypted container can be opened by a password,
                recipient private keys, or an SSKR quorum. Password permits use the pinned Blockchain Commons Argon2id
                profile: 19 MiB memory, 2 iterations, 1 lane, a random per-permit salt, and a 32-byte derived key.
              

              

                Open-source modules are used. Source code is available from
                bc-envelope-rust
                and
                bc-components-rust. Every build verifies locked dependency checksums. When GitHub is available, it also verifies the
                exact pinned upstream commits; a mismatch stops the build.
              

            

          

          

            Uses the Blockchain Commons Seed Envelope profile, deterministic CBOR and UR transport. Recipient keys use
            X25519.
          

          

            
          

          

            
            

              

              

              

                
              

              

                
              

              

                
              

              

                SSKR permit groups · optional
                

              

            

            

              Derive recipient key pair
              
              
              

                
                
              

              

                
                
                
                
                
              

              

                Uses the complete 64-byte BIP39 seed and the official Blockchain Commons X25519 derivation. A key
                derived from the protected wallet is convenient access control, but it is not an independent backup.
              

              
            

            

              
              

                
                
              

            

            

              
            

            

          

          

            
            
            

              
            

            

          

        


        

          

            

              02
              
Codex32 · BIP93

            

          

          

            What is this?
            

              
Codex32 · BIP93

              

                Encodes secret bytes in a checksummed, error-correcting Bech32-style string and can optionally split
                them with Codex32 native shares. This workspace supports BIP39 entropy and BIP32 master-seed modes.
              

              

                An open-source Rust module and its BIP93 vectors are used. Source code is available from
                apoelstra/rust-codex32. Every build verifies locked dependency checksums. When GitHub is available, it also verifies the
                exact pinned upstream commit; a mismatch stops the build.
              

            

          

          

            Encodes either recoverable BIP39 entropy or a passphrase-derived BIP32 master seed with the Codex32
            error-correcting checksum and optional native secret sharing.
          

          

            
            
          

          

            

              
              
            

            
            
            
            

            
            
            

              

                
                
                

                  Public label that keeps records from different sets together. Use four Bech32 characters; b, i, o, and
                  1 are unavailable. Examples: safe, fund, cash, 2026.
                

              

              

                
                
              

              

                
                
              

            

            
            
Disables the threshold and share-count fields.

            

            

              
              
            

            

          

          

            

              
              
            

            
            
            
            

              Codex32 records do not identify the semantic meaning of their bytes. Select the same content type that was
              used when the backup was created.
