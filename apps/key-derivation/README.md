# Wallet Key Derivation Tool

The derivation form displays the fixed purpose, coin type and selected scheme from the same adapter that defines the standard path. The path is read-only: account, address branch controls, start index and result count remain editable where supported. Receive/change generation retains its existing checkbox. Identity has no account control; Orchard labels its diversifier index explicitly. Legacy mobile paths do not display nonexistent purpose/coin levels. There is no arbitrary-path mode in this tool.

Offline, standalone BIP39/BIP32/ZIP-32 derivation. The local Seed Diagnostic reports word count, English-wordlist membership, checksum validity, NFKD normalization, entropy/checksum sizes, and the passphrase-sensitive BIP32 master fingerprint; unknown English words receive bounded nearest-word suggestions. Its reveal-gated construction view lists every word position, BIP39 index in decimal/hex, the corresponding 11-bit group, canonical entropy in hex/binary, and checksum bits; validation and entropy recovery use the pinned `@scure/bip39` implementation. The input validator and secure phrase generator support every standard English BIP39 length: 12, 15, 18, 21, and 24 words. The extensible Multi-Chain edition currently includes Bitcoin, Ethereum, and Dash (Core BIP44, legacy mobile Core, Platform payments, Platform Identity keys, Purpose48 and Dash Core pkh multisig cosigner keys, and Orchard). Dash Community is Dash-only and compiles those Dash adapters. Build outputs: `dist/multi-chain-edition/key-derivation/Wallet_Key_Derivation_Tool.html` and `dist/dash-community-edition/key-derivation/Dash_Community_Key_Derivation_Tool.html`.

A new phrase is a new wallet: Generate empties the BIP39 passphrase field, and only the MHFE wallet check mode keeps the passphrase its phrase is drawn for. Whenever a passphrase is in use, a line right above the address table says so. **Generate with a chosen word**, a checkbox under the Generate buttons, is not recommended: a phrase from the ordinary Generate buttons is the strongest, and the panel says so first. It makes the new phrase hold one chosen word, at a chosen position (the last word included) or anywhere, and not hold one word never to use: one of each at most, at every length, as in MHFE (owner's decisions, 2026-10-08). Every word must be in the English BIP39 list; a word that is not is marked and refused. The phrase is still drawn with `crypto.getRandomValues()`, evenly among all phrases that meet the wishes: the bits of a word at a position are set directly, everything else is drawn again until it fits, and the checksum is always calculated. The panel shows the random bits left for every length: a word at a position takes 11 bits, a word anywhere about 7, so a 12-word phrase keeps at least about 117. These are the worst case, for someone who knows the word: if nobody knows or can guess it, the phrase stays as strong as a random one. A chosen word also gives a phrase away: as MHFE warns, someone who learns or guesses it can rule out almost every wrong MHFE password and tell the wallet from a decoy, so the panel says so whenever a word is chosen; choose no word for a wallet you would protect with a decoy. Used the other way round, with a hidden wallet behind an honest disclosure, a word you are known to like, placed in the wallet you would disclose, is one more sign that this is your real wallet, while the hidden wallets are random phrases anyway; the wallet's own history remains the main evidence. The chosen word is part of the phrase, so the fields are hidden and shown together with it. A new Generate or Clear all cancels a search that has not started, and a wish that cannot be met is reported, never replaced by an ordinary phrase. At every start, in about 10 ms, the page self-test checks the generator's own steps at every position of all five lengths against an independent oracle: where a chosen word's bits go and that no neighbouring bit changes, how each word is read back with its checksum, and that a word never to use is refused wherever it stands. It then lets the search draw six known phrases from a fixed byte stream (a chosen word first, in the middle, across three bytes, anywhere and last), each computed by an independent whole-integer implementation. Unit tests check every word index at every position through the public generator and that 20,000 phrases of each kind keep their other bits and words uniform. The generator is `packages/crypto-core/src/bip39-chosen-words.ts`; MHFE's New wallet tab offers the same fields for its own draw.

**Generate with the MHFE wallet check** draws a 24-word phrase with MHFE's own wallet module (`MhfeWallet.drawPhrase`) so that it passes the experimental `MHFE-WALLET-CHECK-SEED-1` tagged check with the BIP39 passphrase entered in the main field, confirmed separately; it holds the chosen word of the panel below, if one is given. MHFE holds every rule: the check needs a passphrase (an empty one is refused, since anyone who sees the phrase could test it), the confirmation must match, and MHFE says before the draw what the check and the wishes keep of the phrase's 256 random bits (about 240 with the check alone, 229 with a fixed word; below 240 not recommended, below 218 refused). New generation preserves the main passphrase field verbatim; keep it for recovery and keep all funds under it. The check accepts `SHA-256(ASCII("MHFE-WALLET-CHECK-SEED-1") || BE32(256) || seed)` only when its first two bytes are zero; neither the entropy nor the seed is zeroed. A wrong password or passphrase passes about once in 65,536; an address or fingerprint still identifies the wallet. The check is not encryption. MHFE's workers draw roughly 65,536 candidates on average; progress contains counts only, and MHFE checks the phrase once more before it is shown. Cancel, Clear all and changed inputs stop the draw and discard late results. MHFE's quick check of its wallet module runs when the box is first ticked; a failure closes the mode and says why. A build without MHFE contains neither these controls nor their code.

The Release passport contains the self-test result, deterministic build identity, checksum sidecar name, and embedded dependency versions/licenses. The former duplicate expandable dependency footer has been removed.

The startup self-test checks known answers before any control opens: the health of the Web Crypto randomness, BIP39, every backup codec of the build but MHFE (SSKR with the published grouped vector of BCR-2020-011), every coin's derivation, and the optional features built in (BIP85's published vectors, Silent Payments, compact message signatures). **Run the full self-test** in the Release passport repeats these with the slower vectors (BIP38, BIP-322) and runs the self-tests of the backup methods, such as MnemoCode's. MHFE checks its classes when its panel is first opened, before any of its fields opens, since its WebAssembly is compiled only for MHFE; the full self-test runs MHFE's full checks too (a few seconds, up to 256 MiB). MHFE's published vectors take minutes and 2 GiB, so they run only in its Self-test tab. A failed check, at startup or in the full self-test, closes every control that derives, signs or encrypts from the phrase, BIP85 and Silent Payments included. Every check uses public test data.

The shared **Recover & Back Up** workspace is present in both editions. The original phrase or current BIP85 child phrase can be passed to a selected recovery workflow through an expiring in-memory reference, without clipboard or storage. The reveal-gated Mnemonic construction details also show BIP39 entropy; it never treats the separate passphrase as entropy. Wallet Matcher numbers seed phrases, their aligned passphrases, and known addresses as separate records; pasted line breaks inside a valid phrase are normalized only when its BIP39 checksum proves the boundary. It accepts aligned lists of BIP39 phrases and passphrases plus one or more known addresses, checks the selected coin’s supported profiles, optionally including change addresses; the all-coins option also includes change branches, and reports the matching seed number and full derivation path within explicit account/index bounds. SeedQR supports Standard numeric and Compact binary formats for every standard 12/15/18/21/24-word English BIP39 phrase. SeedSigner documents 12/24-word payloads; intermediate lengths round-trip inside this tool but may not be accepted by every external SeedQR implementation. MnemoCode 0.1.0 supports all five text representations plus Direct, checksum-valid Seedshift, exact legacy Seedshift, and legacy valid-final-word recovery; dates remain external to MNC1 records. Codes that a representation writes joined, such as Unicode code points, are also shown apart above the joined text in results, shares and restored backups, so that a person sees which code to mark with ?. Below its fields of words (the seed phrase, a phrase with a forgotten word, a word looked up in the word table, encoded codes or a record, a written backup checked again, and shares), MnemoCode's word hints appear while the text is shown, by the same rule as MHFE's: English codes and Bytewords get them, Unicode codes, numbers and colors do not. Its Forgotten tab searches forgotten words, a missing word and forgotten dates (a ? for a digit, a whole day, month or year, or a whole date, and values joined by |), and sends unreadable codes of an encoded seed phrase, and codes typed in place of words, to Decode, which finds the codes marked with ?; with SSKR in the build it also splits, restores and repairs Shamir shares, and a share typed or read into Decode goes to Restore as its first share. Wherever MnemoCode asks for the wallet, it takes the master fingerprint, a Bitcoin address or key, or an address of eleven other coins (the Dash Community Edition: the fingerprint or a Dash address), compared at its place among as many addresses as the person says, 20 by default. Printable share cards print shares written in colours or Unicode codes, one code to a card followed by random codes that belong to nothing, or one QR card per share; shares in word numbers, Bytewords or UR have no cards; a QR code printed on a sheet is offered as an image too. SLIP-39 uses the current Trezor-compatible mnemonic format. Codex32 follows draft BIP93 and its native GF(32) sharing scheme. Blockchain Commons SSKR adds interoperable grouped thresholds with standard `ur:sskr` records. Gordian Seed Envelope is the typed Seed profile inside Gordian Envelope; its encrypted form may carry password, X25519 recipient, and SSKR quorum permits over one content key. Each generated SeedQR, MnemoCode record, SLIP-39 share, Codex32 record, SSKR share, or Seed Envelope record is rendered as its own offline QR code with local PNG export. Every restore mode accepts local QR image files; CompactSeedQR import preserves raw bytes including NUL and line-break values.

SLIP-39 backs up the entropy of a valid English BIP39 phrase and restores those words. Codex32 can store either BIP39 entropy, which reconstructs the original English words, or the 64-byte BIP32 master seed produced from the phrase and its exact Unicode passphrase. Master-seed mode restores those seed bytes, but the PBKDF2 conversion is one-way and cannot recover the original words or passphrase. All share creation uses `crypto.getRandomValues`; Codex32 receives independent browser-generated random field-point payloads. No recovery method uses `Math.random`, network access, or browser storage.

MHFE embeds the MHFE 0.6.0 browser package (suites `MHFE-BIP39-256-EXPERIMENTAL-3` and `MHFE-BIP39-LP-EXPERIMENTAL-4`) and runs every operation in a disposable Worker. It provides 12/15/18/21/24-word encryption into a 24-word container, or on the user's choice into one as long as a 12- to 21-word phrase, which has no built-in check, with a check of every new container, automatic length detection with every candidate shown on the rare ambiguity, an explicit length override, PIM 0–1023, memory level 0 (2 GiB), stop/status controls, QR transfer, and recovery-verifier reporting. Its tabs offer every operation of the mhfe program: Encode, Decode, Check (a rehearsal that shows no phrase), New wallet (a phrase drawn in the browser, optionally with the phrase + passphrase check), Change password, Hidden wallets (a session that lists and counts nothing and closes itself after 10 minutes without use), Repair (repair words and the repair of a container phrase), Password (dice words, a check word or random characters) and Self-test (only on request). Where a container password is set (Encode, New wallet, Change password), it is the person's own, typed twice, or one MHFE makes: five dice words, five words and a check word, or sixteen random characters, shown once and typed back from the written copy; the result says how it was made, never the words. Every password is reviewed for a check word before long work, and the package's own list says what to keep. Where a container phrase is decrypted, checked, rekeyed or opened, a word typed as ? asks for its repair words at once; without them, MHFE asks what you know and searches for up to two missing words: by an address or fingerprint of the container's own wallet, with exactly the BIP39 passphrase you say is used with the container phrase and without the password (for two words by an address, among its first 20, 100, 500 or any number of receiving and change addresses, which takes minutes in a browser); or, for one missing word, by an address or fingerprint of your wallet, or in a 24-word container by the original seed phrase's passphrase or its built-in check, one full recovery a candidate, after saying how long that takes. A repaired or found container phrase is used only after Use it. Below every field of words (seed phrase, container phrase, repair words, chosen word) and every password field, MHFE's word hints appear as in the mhfe program while the text is shown: after one letter how many words begin with it, from two letters those words, and in a line of BIP39 words a warning when none fits; Tab completes the word in a line of BIP39 words. A hidden field shows no hint, and Ctrl+W, which deletes a word in the mhfe program, stays the browser's. Check lists every check a match passed, the original seed phrase's own checks included. Change password warns every user that funds at the old addresses of wallets other passwords open stay there until moved, and asks nothing about them. Encode asks nothing about a BIP39 passphrase, as the mhfe program asks nothing, and its list then names any BIP39 passphrase of the wallet; New wallet knows the answer itself. Change password asks, with no answer chosen in advance and saying why, whether the wallet has one, so that this list is complete; MHFE stores no passphrase. The panel says whether it runs in slow mode (a page opened as a file, one Argon2 thread) or fast mode. For fast mode, run the executable version of this tool, which carries the same page and serves it only to this computer (see [the executable version](#the-executable-version) below). See the [MHFE specification](https://github.com/hobby-eng/mhfe-spec) and [reference implementation](https://github.com/hobby-eng/mhfe).

Recovery-source visibility and derived-secret visibility use independent controls: revealing the mnemonic/passphrase does not reveal private result fields, and revealing result keys does not expose the recovery source. The BIP39 passphrase field accepts Unicode and preserves the entered case, spaces, line breaks, symbols, and other characters verbatim before the BIP39 library applies its required NFKD normalization. The mnemonic itself remains restricted to the English BIP39 wordlist.

The main UI loads protocol metadata only. All runtime key derivation and the Orchard WASM instance execute in a disposable Blob worker. The offline Recover & Back Up workspace uses separate embedded Codex32, SSKR, and Gordian Envelope WASM modules on the main thread because it does not share derivation-worker state. Message signing, BIP38 encryption, BIP85 child-secret derivation, and BIP352 scan/spend-key derivation use the same disposable-worker boundary. The final HTML has `connect-src 'none'`, no external assets, no storage APIs and no runtime install requirement.

Supported Bitcoin addresses expose local message signing: compact BIP137 for P2PKH and BIP322 for nested SegWit, native SegWit, and Taproot. Dash P2PKH uses Dash Core compact-message framing. BIP38 encryption is offered only for compressed Bitcoin and Dash P2PKH keys because BIP38 carries neither a script type nor a descriptor. It runs the standard scrypt and AES-256-ECB compatibility construction in the worker.

Both editions include coin-independent BIP85 child BIP39 derivation for all standard 12/15/18/21/24-word lengths. A child mnemonic opens as an in-memory wallet workspace with the edition’s supported coins, the normal result table, private-key reveal, clipboard controls, and account descriptor export; no URL, storage, popup, or network transport is used. Both editions additionally expose XPRV and hexadecimal BIP85 applications; WIF choices follow the edition (Dash only in Dash Community, Bitcoin and Dash in Multi-Chain). Multi-Chain also includes BIP352 Silent Payment address derivation. Silent Payments show the canonical scan and spend paths, base address, and reserved `m=0` change label. This offline utility does not scan chain history: detecting payments still requires eligible transaction input data and ordered outputs.

Bitcoin Legacy, Nested SegWit, Native SegWit and Taproot plus Dash Core can optionally derive the standard internal/change branch `/1` alongside the receive branch `/0`. Dash legacy mobile exposes the historical `m/account'/0/i` receive and `m/account'/1/i` change paths through the same two result tabs. Receive and Change have independent row selection, paging, copy/download state and branch-specific Bitcoin watch-only descriptors. Ethereum keeps its explicit address-branch selector; arbitrary custom paths are not offered by this Deriver; Dash Platform uses the same Receive/Change result tabs for DIP17's hardened receive class `0'` and optional internal/change class `1'`; Orchard diversifiers retain their own controls.

Every derived public payment address has an on-demand offline QR preview beside its copy action. Bitcoin, Ethereum, and Dash Core use their canonical address-only URI schemes; Platform and Orchard encode the exact address because no broader payment-URI mapping is assumed. Derivation rows do not offer QR actions for private/public keys, descriptors, viewing keys, Identity keys, paths, fingerprints, or metadata. Recover & Back Up separately offers explicitly labeled secret-record QR actions.

The **Also generate change addresses** checkbox appears only for adapters that explicitly declare receive/internal address selectors. It is off by default. When enabled, the same account, network, start index and result count are derived once for each selector: `/0` and `/1` for Core/BIP44, or hardened `0'` and `1'` classes for Dash Platform; the first tab remains **Receive addresses** and the second tab contains **Change addresses**. Automatic derivation, manual derivation, cancellation, known-address search, Basic/Advanced display, secret reveal, selection, copy and download all respect the active branch. Disabling the checkbox discards the change result rather than silently mixing it with receive rows.


For Dash Platform, leave **Also generate change addresses** off to derive receive addresses, or enable it for both receive and internal/change addresses. The advanced numeric Key class input is replaced by this standard choice; the underlying derivation library still accepts explicit classes. A receive-class xpub cannot derive the separate hardened internal class, so each result tab exposes its own xpub.

Legacy mobile Account selects the hardened root `m/account'`; zero remains the historical default. This matches [DashSync’s BIP32 account implementation](https://github.com/dashevo/dashsync-iOS/blob/master/DashSync/shared/Models/Derivation%20Paths/DSFundsDerivationPath.m). Discovery uses the selected account for both receive and change chains, on mainnet and testnet.

Legacy mobile results include **Copy public scan key** and a text-file export for the active branch. Paste the `dash-legacy-xpub:` export into Discovery Scanner; it covers that branch without revealing private keys.

### Dash multisig cosigner export

The Dash multisig section has two explicit cosigner derivation variants. Purpose48 derives wallet-specific legacy P2SH material at `m/48'/5'/account'/0'` on mainnet and `m/48'/1'/account'/0'` on testnet. Dash Core pkh signer uses the ordinary signer account at `m/44'/5'/account'` or testnet `m/44'/1'/account'`, matching Dash Core's default descriptor multisig workflow at account 0. Other accounts are explicitly custom BIP44 accounts and require the matching private signer descriptor/keys; an ordinary account-0 Core wallet will not infer them merely from the PSBT origin. Both variants show origin-tagged account xpubs and child compressed public keys; the Core variant also shows checksummed public `pkh(.../0/*)` and `pkh(.../1/*)` descriptors. It deliberately does not present the signer's P2PKH addresses as shared multisig addresses.

BIP48 itself specifies script types `1'` and `2'` for SegWit multisig; this tool’s Dash legacy `0'` convention must be checked against the intended wallet. A matching path does not prove import or signing compatibility.

Use the origin-tagged account xpub from the selected variant as one cosigner input in the PSBT & Multisig Inspector utility. The inspector also accepts the complete checksummed public Dash Core `pkh` signer descriptor and extracts its account xpub. It combines all cosigner xpubs to build the shared M-of-N P2SH address range. The signer's ordinary P2PKH addresses are not part of that shared wallet.

### Account descriptor export

The Key Derivation Tool exports public and **unencrypted private** account descriptors for all four Bitcoin address profiles and Dash Core P2PKH families (BIP44, legacy mobile and mobile DIP9 CoinJoin). The default export is a ready-to-paste Core console import command covering receive and change, with active account branches, Core-managed address pools and a full historical rescan. Raw checksummed descriptor lines remain available for Scanner and other wallets. Public export cannot spend; private export grants account spending access. Public export is available without revealing sensitive values; private export requires revealing them. The **Account export** button opens a dialog with public and private copy/download actions. Other accounts, other Bitcoin address profiles, Dash Platform, Identity and Orchard are not included. See [account descriptor instructions](../../docs/ACCOUNT_DESCRIPTORS.md) for scope and Core import requirements.

Only change the default scheme or account when you know the source wallet’s derivation path. A different account produces different keys and addresses; other wallets may not discover its funds automatically. Exports preserve the selected account, including a nonzero account number. The deriver supports the selected scheme’s account controls, not arbitrary custom path templates.

## Feature-selective standalone builds

Canonical builds include every feature allowed by their edition profile. Custom builds are written under `dist/custom-builds/<profile>/` and never replace release artifacts.

```bash
pnpm build:key-derivation -- --profile multi-chain --features derive,bip85,seedqr
pnpm build:key-derivation -- --profile dash-community --exclude mnemocode,slip39,codex32,sskr,gordian-envelope
pnpm build:key-derivation -- --profile multi-chain --features derive,bip85,seedqr,slip39 --exclude slip39
```

`--features` starts from the named allowlist; `--exclude` starts from the edition's complete set and removes names. When both are present, exclusions are applied after the allowlist. The base `derive` feature is required. Available names are `derive`, `bip85`, `silent-payments`, `bip38-encrypt`, `message-signing`, `wallet-matcher`, `seedqr`, `mnemocode`, `mnemocode-cards`, `mhfe`, `slip39`, `codex32`, `sskr`, and `gordian-envelope`. `silent-payments` is available only in the multi-chain edition. Use `--output path/file.html` to choose a custom output path.

## The executable version

A browser runs MHFE's four Argon2 lanes in parallel only on a cross-origin isolated page, and a page opened as a file never is, so there MHFE uses one thread. The executable version is one program per platform (`Wallet_Key_Derivation_Tool-linux-x86_64`, `-linux-aarch64`, `-windows-x86_64.exe`, `-macos-aarch64`, `-macos-x86_64`) that carries the release's HTML page inside it. When it starts, it checks the page against the SHA-256 it was built with, serves it to this computer only (`127.0.0.1`, a port the system chooses) with the headers that make it isolated, and opens it in the default browser. MHFE then runs about two and a half to three times faster. Everything else works exactly as in the HTML file.

The program never receives what is typed into the page: it answers only `GET` and `HEAD` for `/`, checks the `Host` header, limits the size and duration of each request, and keeps no logs. Closing its window stops the server but not a tab that already shows the page; close the tab as well. A browser profile without extensions is the safest place to open it.

Its source is in [`launcher/`](launcher/). It needs no installation; its only dependency is RustCrypto's `sha2`, pinned in `Cargo.lock`. Build it for this computer after the HTML build with `node tooling/build-key-derivation-launchers.mjs` (add `--profile dash-community` for that edition, or `--platforms` for other platforms). A release build without the page fails. `pnpm build:reproducible:launchers` builds the Linux and Windows versions reproducibly in `Dockerfile.launchers`.
