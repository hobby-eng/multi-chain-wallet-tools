# Wallet Key Derivation Tool

The derivation form displays the fixed purpose, coin type and selected scheme from the same adapter that defines the standard path. The path is read-only: account, address branch controls, start index and result count remain editable where supported. Receive/change generation retains its existing checkbox. Identity has no account control; Orchard labels its diversifier index explicitly. Legacy mobile paths do not display nonexistent purpose/coin levels. There is no arbitrary-path mode in this tool.

Offline, standalone BIP39/BIP32/ZIP-32 derivation. The local Seed Diagnostic reports word count, English-wordlist membership, checksum validity, NFKD normalization, entropy/checksum sizes, and the passphrase-sensitive BIP32 master fingerprint; unknown English words receive bounded nearest-word suggestions. Its reveal-gated construction view lists every word position, BIP39 index in decimal/hex, the corresponding 11-bit group, canonical entropy in hex/binary, and checksum bits; validation and entropy recovery use the pinned `@scure/bip39` implementation. The input validator and secure phrase generator support every standard English BIP39 length: 12, 15, 18, 21, and 24 words. The extensible Multi-Chain edition includes Bitcoin, Dash (Core BIP44, legacy mobile Core, Platform payments, Platform Identity keys, Platform identity funding keys, DashPay addresses on which a contact pays, masternode owner, voting, BLS operator and Platform node keys, Purpose48 and Dash Core pkh multisig cosigner keys, and Orchard), Ethereum and the single-key coins below. Dash Community is Dash-only and compiles those Dash adapters. Build outputs: `dist/multi-chain-edition/key-derivation/Wallet_Key_Derivation_Tool.html` and `dist/dash-community-edition/key-derivation/Dash_Community_Key_Derivation_Tool.html`.

Coins of the Multi-Chain Edition: Bitcoin, Dash, Ethereum and every EVM network (the same 0x accounts on Arbitrum, Avalanche C-Chain, Base, BNB Chain, Gnosis, Hyperliquid's HyperEVM, Optimism and Polygon), and the single-key coins, mainnet only. The BIP44 coins are Bitcoin Cash (CashAddr, at coin type 145 or at Bitcoin's coin type 0 kept by wallets of the 2017 fork; Advanced mode also shows the legacy form), Cosmos (cosmos1…), Dogecoin (BIP44, dgub/dgpv account keys), Ethereum Classic (coin type 61), Injective (inj1…, at Ethereum's coin type 60), Litecoin (Legacy BIP44, Nested SegWit BIP49 and Native SegWit BIP84, at coin type 2), Tron (T… accounts), XRP (r… accounts) and Zcash's transparent t1 addresses (shielded addresses are not derived). The Ed25519 coins, derived by SLIP-10 with every level hardened, are Hedera (the Hedera SDK's standard Ed25519 keys at m/44'/3030'/0'/0'/i' with their HIP-32 alias, and its ECDSA keys at m/44'/3030'/0'/0/i with their EVM address; an account number 0.0.N comes only from the network), NEAR (m/44'/397'/i', the implicit account and the ed25519: key strings), Solana (Phantom and Solflare at m/44'/501'/i'/0', Ledger at m/44'/501'/i'; the private key in the base58 keypair form Phantom imports) and Stellar (SEP-0005, m/44'/148'/i', G… account ID and S… secret seed). TON has three tabs: Telegram wallet derives the one key of a TON phrase, 24 words of the English list without BIP39's checksum that pass TON's own check, from the phrase's entropy (ton-crypto: HMAC-SHA512 of the words, then PBKDF2-SHA512 “TON default seed”, 100,000 rounds; a BIP39 passphrase is not part of it, so the tab refuses one rather than ignore it), and shows its W5 address, which the Telegram wallet uses, with its v4R2 and v3R2 addresses; Trust Wallet (m/44'/607'/i', v4R2 first) and Ledger (m/44'/607'/0'/0'/i'/0') derive TON keys from any BIP39 phrase by SLIP-10. A pasted TON phrase that is not a BIP39 phrase opens the Telegram wallet tab, the other coins refuse it, and “Generate a phrase the Telegram wallet accepts” draws 24-word BIP39 phrases until one also passes TON's check (about 256 draws), with a chosen word and with the MHFE wallet check too (see below). The wallet contracts' addresses use their published code hashes (Ledger's app-ton, ton-blockchain's W5 build); `test/oracles/ton_oracle.py` reproduces the W5 and v4R2 hashes from wallet-core's state inits, the v3R2 hash from the code ton-org/ton publishes, ton-crypto's phrase vector and the startup addresses; no v3R2 address of a known key is published, so v3R2 addresses rest on ton-org/ton's data layout. The startup self-test checks TON's phrase check and the contracts' addresses of ton-crypto's key; the phrase's key, 100,000 PBKDF2 rounds, is checked in the full self-test. Their version bytes come from each coin's own chain parameters, read on 2026-11-10 (Litecoin Core, Dogecoin Core, zcashd) and from the CashAddr specification 1.0. The BIP44 coins share one derivation (`packages/coin-protocols/src/coins/bip44-coin.ts`); their startup vectors are the first addresses of the public "abandon … about" phrase, which MnemoCode's own Rust derivation finds at the same paths, and their encodings reproduce Trust Wallet wallet-core's addresses of the private key 0x46…46 (`packages/coin-protocols/tests/bip44-coins.test.ts`). The Ed25519 coins reproduce Stellar's SEP-0005 vectors, near-seed-phrase's and the Hiero (Hedera) SDK's published keys and wallet-core's addresses; Solana publishes no phrase vector, so its startup values, like NEAR's and Hedera's Ed25519 key for the public "abandon … about" phrase, come from `test/oracles/ed25519_oracle.py`, an independent standard-library reimplementation that first reproduces those published vectors (`packages/coin-protocols/tests/ed25519-coins.test.ts`); `test/oracles/bip32_oracle.py` recomputes every account key, WIF private key and old address form of the BIP44 coins. `node tooling/verify-oracles.mjs`, part of `pnpm test:vectors`, runs every oracle. Wallet Matcher reads each coin's addresses and refuses a broken checksum where the form has one; a 0x address is searched under Ethereum, Ethereum Classic and Hedera's ECDSA keys alike, a legacy 1… address under Bitcoin and Bitcoin Cash, and a 3… address under Bitcoin and Litecoin's nested SegWit, whose rows show that old form. Cardano has three tabs, CIP-3's master keys of a BIP39 phrase: Icarus, the key of Yoroi, Lace, Daedalus (Shelley wallets), Trust Wallet and Trezor (PBKDF2-HMAC-SHA512 of the BIP39 passphrase, salted with the phrase's entropy, 4096 rounds); Ledger, the key of Ledger devices and BitBox02, made from BIP39's seed; and Icarus-Trezor, the key of Trezor wallets made from 24 words with older firmware, whose salt also holds the phrase's checksum byte, so that below 24 words it equals Icarus and only a 24-word phrase gives it addresses of its own; Ledger's addresses always differ from both. Each derives BIP32-Ed25519 keys (`packages/coin-protocols/src/bip32-ed25519.ts`) at CIP-1852's m/1852'/1815'/account'/role/index, mainnet only; Role chooses receive addresses (0), change addresses (1) or the stake key (2, whose index 0 is the one wallets use, CIP-11). A row shows the base address of its key with the account's stake key, the key's addr_vk and its addr_xsk, and in Advanced mode its enterprise address, the account's stake address, the key in hex, its addr_xvk and the 128-byte signing key that cardano-cli's .skey holds; a stake key's row shows its reward address (stake1…), which is not a payment address and has no QR. The summary gives the account's acct_xvk, and its acct_xsk and the root_xsk. Byron-era wallets are not derived, neither CIP-3's Byron master key of Daedalus's Byron wallets nor any Byron address (Ae2…, DdzFF…), and nor are Trezor's Shamir (SLIP-39) wallets, whose Cardano keys come from SLIP-23 (the page's SLIP-39 tab restores BIP39 words only). Yoroi, Lace and Trust Wallet use no BIP39 passphrase, so with one the Icarus tab's keys are Trezor's alone; Eternl and Typhon may use Icarus's keys too, but no source for it was checked, since their code is closed; each tab's notice says which wallets it matches. The startup self-test checks CIP-3's Icarus root with a passphrase, cardano-serialization-lib's root, base, enterprise and reward addresses, and Trezor's account keys of one 24-word phrase under all three master keys; the full self-test adds cardano-serialization-lib's 15- and 24-word addresses, Trezor's base addresses, CIP-19's and CIP-11's vectors and a cardano-addresses golden. `test/oracles/cardano_oracle.py`, a standard-library reimplementation, reproduces those published values before it checks the inputs and the few own values of the self-test and the unit tests. A BIP85 child wallet offers Cardano's Ledger tab only (see below); Wallet Matcher does not search Cardano addresses yet, and says so.

A new phrase is a new wallet: Generate empties the BIP39 passphrase field, and only the MHFE wallet check mode keeps the passphrase its phrase is drawn for. Whenever a passphrase is in use, a line right above the address table says so. **Generate with a chosen word**, a checkbox under the Generate buttons, is not recommended: a phrase from the ordinary Generate buttons is the strongest, and the panel says so first. It makes the new phrase hold one chosen word, at a chosen position (the last word included) or anywhere, and not hold one word never to use: one of each at most, at every length, as in MHFE (owner's decisions, 2026-10-08). Every word must be in the English BIP39 list; a word that is not is marked and refused. The phrase is still drawn with `crypto.getRandomValues()`, evenly among all phrases that meet the wishes: the bits of a word at a position are set directly, everything else is drawn again until it fits, and the checksum is always calculated. The panel shows the random bits left for every length: a word at a position takes 11 bits, a word anywhere about 7, so a 12-word phrase keeps at least about 117. These are the worst case, for someone who knows the word: if nobody knows or can guess it, the phrase stays as strong as a random one. A chosen word also gives a phrase away: as MHFE warns, someone who learns or guesses it can rule out almost every wrong MHFE password and tell the wallet from a decoy, so the panel says so whenever a word is chosen; choose no word for a wallet you would protect with a decoy. [A chosen word](SECURITY.md#a-chosen-word) in the security notes explains how. Used the other way round, with a hidden wallet behind an honest disclosure, a word you are known to like, placed in the wallet you would disclose, is one more sign that this is your real wallet, while the hidden wallets are random phrases anyway; the wallet's own history remains the main evidence. The chosen word is part of the phrase, so the fields are hidden and shown together with it. A new Generate or Clear all cancels a search that has not started, and a wish that cannot be met is reported, never replaced by an ordinary phrase. At every start, in about 10 ms, the page self-test checks the generator's own steps at every position of all five lengths against an independent oracle: where a chosen word's bits go and that no neighbouring bit changes, how each word is read back with its checksum, and that a word never to use is refused wherever it stands. It then lets the search draw six known phrases from a fixed byte stream (a chosen word first, in the middle, across three bytes, anywhere and last), each computed by an independent whole-integer implementation. Unit tests check every word index at every position through the public generator and that 20,000 phrases of each kind keep their other bits and words uniform. The generator is `packages/crypto-core/src/bip39-chosen-words.ts`. It is the Deriver's one generator of phrases: from MHFE 0.8.0, MHFE draws none.

**Generate with the MHFE wallet check** draws a 24-word phrase that passes the experimental `MHFE-WALLET-CHECK-SEED-1` tagged check with the BIP39 passphrase entered in the main field; it holds the chosen word of the panel below, if one is given. The Deriver draws it itself (`packages/crypto-core/src/bip39-wallet-check.ts`), since MHFE 0.8.0 left the generation of phrases to it: each phrase is fresh and uniformly random among those that meet the wishes, as above, its seed is stretched with PBKDF2-HMAC-SHA512 (2048 rounds), and the workers the person chooses draw at once (see **Threads** below). The first phrase that passes is taken. MHFE's proof of the check, Theorem 5 of its specification, covers this draw when every word comes from it; a chosen word, a word never to use or the Telegram condition takes the phrase outside it, and the time shown and several threads stay slightly outside its conditions: see [The wallet check and its proof](SECURITY.md#the-wallet-check-and-its-proof). The check needs a passphrase (an empty one is refused, since anyone who sees the phrase could test it), and the panel says before the draw what the check and the wishes keep of the phrase's 256 random bits (about 240 with the check alone, about 228 with a fixed word; below 240 not recommended). New generation preserves the main passphrase field verbatim; keep it for recovery and keep all funds under it. The check accepts `SHA-256(ASCII("MHFE-WALLET-CHECK-SEED-1") || BE32(256) || seed)` only when its first two bytes are zero; neither the entropy nor the seed is zeroed. A wrong password or passphrase passes about once in 65,536; an address or fingerprint still identifies the wallet. The check is not encryption. A phrase takes roughly 65,536 draws on average, about 1 minute in Chromium and 1.5 minutes in Firefox on two threads (see below); progress contains counts only. As the specification allows, each worker stops after `2^22` draws, 64 times the average, or after `2^30` with the Telegram condition, of which about `2^22` reach the wallet check; a working generator reaches that limit with odds of about `e^-64`. Only when every worker has stopped does the page say "No phrase passed the wallet check in time. Generate again." Before the draw the page checks its digest against the profile's published vector and refuses a random source that gives the same bytes twice; MHFE's wallet module checks the drawn phrase once more (`MhfeWallet.walletCheck`) before it is shown. Stop, Clear all and a change of the options, the chosen words, the phrase or the passphrase stop every worker and discard late results; a change of the derivation settings or the coin does not, and the phrase is then derived with the new ones. MHFE's quick check of its wallet module runs when the box is first ticked; a failure closes the mode and says why. A build without MHFE contains neither these controls nor their code.

**The generation options combine.** A chosen word, a phrase the Telegram wallet accepts and the MHFE wallet check can be ticked in any combination. Every draw is fresh and uniformly random among the phrases that meet the wishes, and each check only rejects, so the phrase taken is uniform among those that pass every condition, exactly so on one thread (see above); TON's check runs first, being the cheaper, and with the wallet check both run on its workers (`packages/crypto-core/src/ton-mnemonic.ts` gives TON's check there by the worker's engine, kept in step with the page's own check by tests and by known answers before every draw). Right under the Generate buttons a line appears as soon as a button is pressed: what is drawn and how many draws it takes on average, then the phrases tried, the time elapsed and the average time at the speed so far, and Stop for every draw that can last; at the end it says how many draws the phrase took. A refusal, such as a missing passphrase or a word that is not a BIP39 word, appears in the same place. Under the options the page states the random bits the phrase keeps: 16 for the wallet check and 8 for TON's check are taken anyway, and only a chosen word makes the phrase not recommended. While the wallet check is ticked it also says how long a phrase takes on this computer, measured by the real draw with a public passphrase and without the chosen words, for one second after a short warm-up, only after an option changes and never on page load, together with the time that 1 search in 20 exceeds. The wallet check and TON's check together take about 16.8 million draws: on two threads, about 50 minutes in Chromium and 1.5 to 2 hours in Firefox on the laptop it was tested on, against about 1 minute and 1.5 minutes for the wallet check alone. It can take hours, and the page says so before the start. **Threads** (1 up to what the browser reports, 2 at first, kept only until a reload or Clear) sets how many workers draw. The first two use the browser's WebCrypto, which Chromium runs on one thread of its own and Firefox on about two; further threads compute in JavaScript, about 6 times slower each, and on that laptop they made the draw slower under its power limit while adding heat. The time shown before the start is measured with the threads chosen, so the effect on each computer can be seen. With both checks the page keeps the BIP39 passphrase, but the Telegram wallet uses the phrase without it, so the passphrase does not protect the funds of that wallet: the page says so before and after the draw, and does not open the Telegram wallet's tab, which refuses a passphrase. MHFE's wallet module and the page's JavaScript check of TON's condition check the phrase once more before it is shown. Encrypted with MHFE, a phrase the Telegram wallet accepts can be tested without the BIP39 passphrase, by TON's check and, once the Telegram wallet has been used, by its address: see [A phrase the Telegram wallet accepts, protected with MHFE](SECURITY.md#a-phrase-the-telegram-wallet-accepts-protected-with-mhfe).

The Release passport contains the self-test result, deterministic build identity, the name of the release's one checksum file (`SHA256SUMS`), and embedded dependency versions/licenses. The former duplicate expandable dependency footer has been removed.

The startup self-test checks known answers before any control opens: the health of the Web Crypto randomness, BIP39, every backup codec of the build but MHFE (SSKR with the published grouped vector of BCR-2020-011), every coin's derivation, and the optional features built in (BIP85's published vectors, Silent Payments, compact message signatures). **Run the full self-test** in the Release passport repeats these with the slower vectors (BIP38, BIP-322) and runs the self-tests of the backup methods, such as MnemoCode's. MHFE checks its classes when its panel is first opened, before any of its fields opens, since its WebAssembly is compiled only for MHFE; the full self-test runs MHFE's full checks too (a few seconds, up to 256 MiB). MHFE's published vectors take minutes and 2 GiB, so they run only in its Self-test tab. A failed check, at startup or in the full self-test, closes every control that derives, signs or encrypts from the phrase, BIP85 and Silent Payments included. Every check uses public test data.

The shared **Recover & Back Up** workspace is present in both editions. The original phrase or current BIP85 child phrase can be passed to a selected recovery workflow through an expiring in-memory reference, without clipboard or storage. The reveal-gated Mnemonic construction details also show BIP39 entropy; it never treats the separate passphrase as entropy. Wallet Matcher numbers seed phrases, their aligned passphrases, and known addresses as separate records; pasted line breaks inside a valid phrase are normalized only when its BIP39 checksum proves the boundary. Wallet Matcher accepts at most 100 phrases and refuses oversized pasted text before parsing, without truncating the input. It accepts aligned lists of BIP39 phrases and passphrases plus one or more known addresses, checks the selected coin’s supported profiles, optionally including change addresses; the all-coins option also includes change branches, and reports the matching seed number and full derivation path within explicit account/index bounds. SeedQR supports Standard numeric and Compact binary formats for every standard 12/15/18/21/24-word English BIP39 phrase. SeedSigner documents 12/24-word payloads; intermediate lengths round-trip inside this tool but may not be accepted by every external SeedQR implementation. With MnemoCode in the build, as in both editions, Encode can also hide a Standard SeedQR in a decoy QR (MnemoCode's hidden QR): ordinary scanners show only the decoy, SeedSigner and other wallets cannot read the SeedQR (they show the decoy or reject the code), and the SeedQR's digits are the QR's hidden record. The decoy is a contact card (vCard 3.0: name, organisation, job title, phone, email, website), a website, a plain text, a Wi-Fi network, an email (`mailto:`), a phone number (`tel:`) or a location (`geo:`), each with its own fields and written with its format's escaping; control characters other than line breaks, and broken characters, are refused. CompactSeedQR is raw bytes, not text, so it is never hidden. It is camouflage, not encryption: protect the phrase first, for example by encoding the container phrase of an MHFE backup instead of the seed phrase. Some scanners reject the nonstandard padding; save MnemoCode's original PNG and print it at actual size, since a QR made again from its visible text loses the record, and never put private information in the decoy. Decode's image import reads a PNG's hidden record before its visible text: a hidden Standard SeedQR is restored, and any other hidden record is refused. MnemoCode reads a hidden record from a PNG of at most 4096 pixels a side and 2 megapixels; a larger image, such as a phone screenshot of an ordinary SeedQR, is read as an ordinary QR. Whenever a hidden record goes unread, because the PNG is larger or MnemoCode is still loading or stopped, the page says why: in the refusal if the image gives no SeedQR, and in a note under the field if it does, so that a decoy that is itself a SeedQR is never taken silently. The same note appears on MnemoCode's own QR imports. Only this Deriver, or MnemoCode's `qr-open` followed by SeedQR decoding, reads the record. MnemoCode 0.2.0, which runs as MnemoCode's own WebAssembly, supports all five text representations plus Direct, checksum-valid Seedshift, exact legacy Seedshift, and legacy valid-final-word recovery; dates remain external to MNC1 records. Codes that a representation writes joined, such as Unicode code points, are also shown apart above the joined text in results, shares and restored backups, so that a person sees which code to mark with ?. Below its fields of words (the seed phrase, a phrase with a forgotten word, a word looked up in the word table, encoded codes or a record, and a written backup checked again), word hints appear while the text is shown, by the same rule as MHFE's: English words get them, Unicode codes, numbers and colors do not. Its Forgotten tab searches forgotten words, a missing word and forgotten dates (a ? for a digit, a whole day, month or year, or a whole date, and values joined by |), and sends unreadable codes of an encoded seed phrase, and codes typed in place of words, to Decode, which finds the codes marked with ?; with SSKR in the build it also splits, restores and repairs Shamir shares, and a share typed or read into Decode goes to Restore as its first share. Wherever MnemoCode asks for the wallet, it takes the master fingerprint, an address of any of its twelve coins, which it reads the coin from and names (an address of two coins' form, such as 1… of Bitcoin and Bitcoin Cash, is looked for on both coins' paths), or a Bitcoin key, whose address types follow from its form (the Dash Community Edition: the fingerprint or a Dash address), compared at its place among as many addresses as the person says, 20 by default. Printable share cards print shares written in colours or Unicode codes, one code to a card followed by random codes that belong to nothing, or one QR card per share; shares in word numbers, Bytewords or UR have no cards; a QR code printed on a sheet is offered as an image too. Encode's cross-stitch pattern (MnemoCode's SeedStitch) hides the phrase, masked with MnemoCode Seedshift and its dates, or with Direct the phrase itself, in the legend of a pattern in DMC threads made from a PNG, JPEG or WebP picture of the person's own, on the fabric chosen (Aida 11, 14, 16 or 18, or linen 28 over one) and at the size MnemoCode offers (a sheet from A6 to A2 that holds the picture, with its stitches and centimetres, or a width typed in centimetres or stitches), saved as a PDF that looks like a bought pattern; Decode and Re-encode read the legend line from that PDF or as typed, and they and Forgotten's date search correct one mistyped row and name it. The **Photo or MP3** tab (MnemoCode's steganography) hides a message, a small file or a MnemoCode backup record in a JPEG photograph or an MP3 file under a container password, optionally with a decoy under a second password, or divides it across 2 to 16 files of which a quorum recovers it. It first shows the guaranteed space at every density for those files and passwords and offers only the densities that take the contents; MnemoCode writes a new file, and the page reads back the Blob it saves and has MnemoCode open it with every password before offering it. Once a new file is saved, the page asks, as MnemoCode does, that each source be kept private (encrypted if it is used again, or else deleted with its copies in cloud backups and synced photo libraries), since a source and its saved file compared show the hidden changes. A password opens its own record and never says whether it is the original message or the decoy; nothing found does not prove a file empty. It is not statistical invisibility, and recompression, resizing or conversion destroys the record. Encode's records and a pattern's legend line are handed to it, as MnemoCode's menu offers a photo or MP3 among their destinations, and what it opens goes on to Decode or Re-encode. A sheet's QR code can keep the record hidden behind the printed contact (MnemoCode's hidden QR, camouflage rather than encryption), and every MnemoCode QR image import, and SeedQR's, reads such a record before the visible text. SLIP-39 uses the current Trezor-compatible mnemonic format. Codex32 follows draft BIP93 and its native GF(32) sharing scheme. Blockchain Commons SSKR adds interoperable grouped thresholds with standard `ur:sskr` records. Gordian Seed Envelope is the typed Seed profile inside Gordian Envelope; its encrypted form may carry password, X25519 recipient, and SSKR quorum permits over one content key. Each generated SeedQR, MnemoCode record, SLIP-39 share, Codex32 record, SSKR share, or Seed Envelope record is rendered as its own offline QR code with local PNG export. Every restore mode accepts local QR image files; CompactSeedQR import preserves raw bytes including NUL and line-break values.

SLIP-39 backs up the entropy of a valid English BIP39 phrase and restores those words. Codex32 can store either BIP39 entropy, which reconstructs the original English words, or the 64-byte BIP32 master seed produced from the phrase and its exact Unicode passphrase. Master-seed mode restores those seed bytes, but the PBKDF2 conversion is one-way and cannot recover the original words or passphrase. All share creation uses `crypto.getRandomValues`; Codex32 receives independent browser-generated random field-point payloads. No recovery method uses `Math.random`, network access, or browser storage.

MHFE embeds the MHFE 0.8.0 browser package (suites `MHFE-BIP39-256-EXPERIMENTAL-3` and `MHFE-BIP39-LP-EXPERIMENTAL-4`) and runs every operation in a disposable Worker. It provides 12/15/18/21/24-word encryption into a 24-word container, or on the user's choice into one as long as a 12- to 21-word phrase, which has no built-in check, with a check of every new container, automatic length detection with every candidate shown on the rare ambiguity, an explicit length override, PIM 0–1023, memory level 0 (2 GiB) in the browser and the mhfe command for any other, stop/status controls, QR transfer, and recovery-verifier reporting. A new phrase, with or without the wallet check, is drawn in Generate & Derive and handed to Encode; MHFE 0.8.0 draws none. Its tabs offer every operation of the mhfe program: Encode, Decode (with one password or several, each with its own PIM, recovered in turn and shown together, each phrase under its password; a stated length with a built-in check takes one password, and for a 24-word container the original seed phrase's BIP39 passphrase is asked first for the 16-bit check), Check (a rehearsal that shows no phrase), Change password, Hidden wallets (a session that lists and counts nothing and closes itself after 10 minutes without use), Repair (repair words and the repair of a container phrase), Password (dice words, a check word or random characters) and Self-test (only on request). Where a container password is set (Encode, Change password), it is the person's own, typed twice, or one MHFE makes: five dice words, five words and a check word, or sixteen random characters, shown once and typed back from the written copy; the result says how it was made, never the words. Every password is reviewed for a check word before long work, and the package's own list says what to keep. Where a container phrase is decrypted, checked, rekeyed or opened, a word typed as ? asks for its repair words at once; without them, MHFE asks what you know and searches for up to two missing words: by an address or fingerprint of the container's own wallet, with exactly the BIP39 passphrase you say is used with the container phrase and without the password (for two words by an address, among its first 20, 100, 500 or any number of receiving and change addresses, which takes minutes in a browser); or, for one missing word, by an address or fingerprint of your wallet, or in a 24-word container by the original seed phrase's passphrase or its built-in check, one full recovery a candidate, after saying how long that takes. A repaired or found container phrase is used only after Use it. Below every field of words (seed phrase, container phrase, repair words) and every password field, MHFE's word hints appear as in the mhfe program while the text is shown: after one letter how many words begin with it, from two letters those words, and in a line of BIP39 words a warning when none fits; Tab completes the word in a line of BIP39 words. A hidden field shows no hint, and Ctrl+W, which deletes a word in the mhfe program, stays the browser's. Check lists every check a match passed, the original seed phrase's own checks included. Change password warns every user that funds at the old addresses of wallets other passwords open stay there until moved, and asks nothing about them. Encode asks nothing about a BIP39 passphrase, as the mhfe program asks nothing, and its list then names any BIP39 passphrase of the wallet. Change password asks, with no answer chosen in advance and saying why, whether the wallet has one, so that this list is complete; MHFE stores no passphrase. Encode also offers memory levels 1 to 21 (3 GiB to 3 TiB), which no browser runs: a browser gives WebAssembly at most 4 GiB, and the Argon2 code allows at most 2 GiB there, so above level 0 Encrypt is off. For a memory level or a PIM other than 0, Encode shows the `mhfe encrypt` command with the same settings and a Copy button, such as `mhfe encrypt --pim 3 --mem 2 --same-length --new-password check-word --repair-words 4`; a custom PIM at level 0 still encrypts in the page as well. The command states `--pim` and `--mem`, `--same-length` for a container of the phrase's own length (24 words has no option: for a 12- to 21-word phrase mhfe asks, and Enter keeps 24 words), `--new-password own`, `words`, `check-word` or `chars`, and `--repair-words` with 0 for none. In every tab, a ticked PIM field without a whole number from 1 to 1023 is refused before any work, never read as PIM 0, and with several passwords Decode names the one it belongs to. Above level 0 the page makes and shows no password, since mhfe makes and shows its own: a kind that MHFE makes is then only a setting of the command. A password the page made at level 0 is kept out of sight meanwhile, and back at level 0 the page asks for it again as written down. Decode, Check, Change password (the old and the new container) and Hidden wallets offer the same memory levels and show their command the same way: `mhfe decrypt` with `--words` for a stated length (detection is its default; with 12 to 21 words stated, mhfe takes one password and asks nothing about a BIP39 passphrase, which the page says); `mhfe check` with `--address` and, where chosen, `--coin` and `--path`, or `--fingerprint`, or `--words` for the built-in check, and no option for the phrase + passphrase check, which mhfe offers in its list; `mhfe rekey` with `--words` and `--confirm address`, `fingerprint` or `show` where chosen, then `--new-pim`, `--new-mem`, `--new-password` and `--repair-words`; mhfe rekey has no option for one derivation path, which the page says. Hidden wallets shows Decode's `mhfe decrypt` command: mhfe 0.8.0 opens hidden wallets there, and a command of their own would mark the shell history. Above level 0 each tab's button and its missing-word search are off, and the work refuses such a level before the container is read, since the page passes no level to the package and would open the container at level 0. The commands carry the settings only: no seed phrase, container phrase, password, BIP39 passphrase, address or fingerprint is copied, and mhfe asks for each at its own prompts as soon as the command runs, so none of them enters a command, the clipboard or the terminal history. No command answers whether a wallet has a BIP39 passphrase (`--passphrase-used`) or adds `--repair` or `--scan-gap`: mhfe asks those questions when they arise. The command itself, with its PIM, memory level, word count, coin and path, stays in the shell history. Run it as mhfe recommends, on a trusted, non-persistent live system with the network disconnected. The panel says whether it runs in slow mode (a page opened as a file, one Argon2 thread) or fast mode. For fast mode, run the executable version of this tool, which carries the same page and serves it only to this computer (see [the executable version](#the-executable-version) below). See the [MHFE specification](https://github.com/hobby-eng/mhfe-spec) and [reference implementation](https://github.com/hobby-eng/mhfe).

Recovery-source visibility and derived-secret visibility use independent controls: revealing the mnemonic/passphrase does not reveal private result fields, and revealing result keys does not expose the recovery source. The BIP39 passphrase field accepts Unicode and preserves the entered case, spaces, line breaks, symbols, and other characters verbatim before BIP39's required NFKD normalization. The Deriver normalizes with its own tables of Unicode 18.0.0 (`packages/crypto-core/src/unicode-nfkd.ts`, generated by `tooling/generate-unicode-nfkd.mjs` from `UnicodeData.txt` and checked against every line of Unicode's `NormalizationTest.txt` and every code point), the version MHFE's specification pins, never with the browser's `String.prototype.normalize`, whose Unicode version varies: a passphrase with a newly assigned character, such as U+209D, which Unicode 18.0.0 normalizes to `w`, gives the same seed in every browser, in MHFE and in MnemoCode. The startup self-test checks it. The mnemonic itself remains restricted to the English BIP39 wordlist.

The main UI loads protocol metadata only. All runtime key derivation and the Orchard WASM instance execute in a disposable Blob worker. The offline Recover & Back Up workspace uses separate embedded Codex32, SSKR, and Gordian Envelope WASM modules on the main thread because it does not share derivation-worker state. Message signing, BIP38 encryption, BIP85 child-secret derivation, and BIP352 scan/spend-key derivation use the same disposable-worker boundary. The final HTML has `connect-src 'none'`, no external assets, no storage APIs and no runtime install requirement.

The coins and address types that sign messages, and their formats, are listed under [Message signing](#message-signing). BIP38 encryption is offered only for compressed Bitcoin and Dash P2PKH keys because BIP38 carries neither a script type nor a descriptor. It runs the standard scrypt and AES-256-ECB compatibility construction in the worker.

Both editions include coin-independent BIP85 child BIP39 derivation for all standard 12/15/18/21/24-word lengths. A child mnemonic opens as an in-memory wallet workspace with the edition’s supported coins, the normal result table, private-key reveal, clipboard controls, and account descriptor export; no URL, storage, popup, or network transport is used. The child workspace derives from the child phrase's BIP39 seed, so it offers the tabs that read that seed: not TON's Telegram wallet, and of Cardano only the Ledger tab, as its note says while Cardano is chosen (Yoroi, Lace, Daedalus (Shelley wallets) and Trezor read a child phrase with Icarus, whose addresses appear when the child phrase is entered as the recovery phrase). Both editions additionally expose XPRV and hexadecimal BIP85 applications; WIF choices follow the edition (Dash only in Dash Community, Bitcoin and Dash in Multi-Chain). Multi-Chain also includes BIP352 Silent Payment address derivation. Silent Payments show the canonical scan and spend paths, base address, and reserved `m=0` change label. This offline utility does not scan chain history: detecting payments still requires eligible transaction input data and ordered outputs.

Bitcoin Legacy, Nested SegWit, Native SegWit and Taproot plus Dash Core can optionally derive the standard internal/change branch `/1` alongside the receive branch `/0`. Dash legacy mobile exposes the historical `m/account'/0/i` receive and `m/account'/1/i` change paths through the same two result tabs. Receive and Change have independent row selection, paging, copy/download state and branch-specific Bitcoin watch-only descriptors. Ethereum keeps its explicit address-branch selector; arbitrary custom paths are not offered by this Deriver; Dash Platform uses the same Receive/Change result tabs for DIP17's hardened receive class `0'` and optional internal/change class `1'`; Orchard diversifiers retain their own controls.

Every derived public payment address has an on-demand offline QR preview beside its copy action. Bitcoin, Dash Core, Dogecoin, Ethereum, Litecoin, Solana and Zcash use their canonical address-only URI schemes, and a Bitcoin Cash CashAddr already carries its `bitcoincash:` prefix; Cosmos, Ethereum Classic, Hedera, Injective, NEAR, Stellar, Tron and XRP addresses are encoded as they are, since their wallets share no such payment URI; TON addresses are encoded as they are too, without a `ton://transfer/` link; Cardano's base and enterprise addresses are encoded as they are, without CIP-13's `web+cardano:` link; Platform and Orchard encode the exact address because no broader payment-URI mapping is assumed. Derivation rows do not offer QR actions for private/public keys, descriptors, viewing keys, Identity keys, paths, fingerprints, or metadata. Recover & Back Up separately offers explicitly labeled secret-record QR actions.

The **Also generate change addresses** checkbox appears only for adapters that explicitly declare receive/internal address selectors. It is off by default. When enabled, the same account, network, start index and result count are derived once for each selector: `/0` and `/1` for Core/BIP44, or hardened `0'` and `1'` classes for Dash Platform; the first tab remains **Receive addresses** and the second tab contains **Change addresses**. Automatic derivation, manual derivation, cancellation, known-address search, Basic/Advanced display, secret reveal, selection, copy and download all respect the active branch. Disabling the checkbox discards the change result rather than silently mixing it with receive rows.

Build only this artifact after generated WASM is already verified:

```bash
pnpm build:quick
node apps/key-derivation/scripts/verify-key-derivation-artifact.mjs
```

For a release, use the root `pnpm verify` command instead. Read [SECURITY.md](SECURITY.md) before handling valuable material and the root [extension guide](../../EXTENDING.md) before adding a coin.

For Dash Platform, leave **Also generate change addresses** off to derive receive addresses, or enable it for both receive and internal/change addresses. The advanced numeric Key class input is replaced by this standard choice; the underlying derivation library still accepts explicit classes. A receive-class xpub cannot derive the separate hardened internal class, so each result tab exposes its own xpub.

Legacy mobile Account selects the hardened root `m/account'`; zero remains the historical default. This matches [DashSync’s BIP32 account implementation](https://github.com/dashevo/dashsync-iOS/blob/master/DashSync/shared/Models/Derivation%20Paths/DSFundsDerivationPath.m). Discovery uses the selected account for both receive and change chains, on mainnet and testnet.

Legacy mobile results include **Copy public scan key** and a text-file export for the active branch. Paste the `dash-legacy-xpub:` export into Discovery Scanner; it covers that branch without revealing private keys.

### Message signing

The sign icon next to an address opens a dialog that signs a message with that row's key, in the disposable worker, and checks the signature locally before showing it. The same dialog verifies a signature someone pasted, for that address and in the selected format: it sends the worker only the address, the network, the format, the message and the signature, never the seed. The dialog names the format of each address and shows notes about it.

Every coin of the Deriver whose wallets share a message-signing standard signs and verifies messages, as the table lists. XRP is the only coin without one: its wallets sign messages in formats that do not match, and none is a common standard.

Litecoin Core verifies only L… addresses; Trezor and Electrum-LTC verify the SegWit signatures, and Electrum-LTC's own SegWit signatures, without the typed header, verify in the dialog too. A Bitcoin Cash signature is also a valid Bitcoin signature for the legacy 1… address of the same key, and a Bitcoin compact signature is valid for Bitcoin Cash: put the chain's name in the message if that matters. Shielded Zcash addresses have no message-signing standard. Ethereum, Ethereum Classic and every EVM network sign messages with the same bytes and no chain ID, so one signature is valid for the same 0x address on all of them; the dialog signs the message as UTF-8 text, as eth-account and viem sign a string, while MetaMask reads a message that starts with 0x as bytes. NEAR's response names the key's implicit account: a named account (name.near) that holds the key is checked only on the network. For NEAR, TON, Cosmos and Injective the dialog reads the signature from a pasted response, or the bare Base64 signature, and for Hedera from the SignatureMap or the bare signature; the message, the fields and the row are what it checks, the row's own public key included where the signature names none (ADR-036 and Hedera's ECDSA rows). An Injective EIP-191 signature is Ethereum's for the 0x form of the same address. Hedera wallets count the length of non-ASCII text differently, so the dialog signs ASCII text only.

### Dash multisig cosigner export

The Dash multisig section has two explicit cosigner derivation variants. Purpose48 derives wallet-specific legacy P2SH material at `m/48'/5'/account'/0'` on mainnet and `m/48'/1'/account'/0'` on testnet. Dash Core pkh signer uses the ordinary signer account at `m/44'/5'/account'` or testnet `m/44'/1'/account'`, matching Dash Core's default descriptor multisig workflow at account 0. Other accounts are explicitly custom BIP44 accounts and require the matching private signer descriptor/keys; an ordinary account-0 Core wallet will not infer them merely from the PSBT origin. Both variants show origin-tagged account xpubs and child compressed public keys; the Core variant also shows checksummed public `pkh(.../0/*)` and `pkh(.../1/*)` descriptors. It deliberately does not present the signer's P2PKH addresses as shared multisig addresses.

BIP48 itself specifies script types `1'` and `2'` for SegWit multisig; this tool’s Dash legacy `0'` convention must be checked against the intended wallet. A matching path does not prove import or signing compatibility.

Use the origin-tagged account xpub from the selected variant as one cosigner input in the PSBT & Multisig Inspector utility. The inspector also accepts the complete checksummed public Dash Core `pkh` signer descriptor and extracts its account xpub. It combines all cosigner xpubs to build the shared M-of-N P2SH address range. The signer's ordinary P2PKH addresses are not part of that shared wallet.

### Multisig wallet

**Recover & Back Up → Multisig wallet** builds a shared m-of-n wallet in the Deriver itself. Each numbered cosigner line is a BIP39 recovery phrase, with the passphrase on the same numbered line, or an account `xpub`/`tpub`, optionally written `[fingerprint/path]xpub…`. A phrase is taken to its account at the chosen cosigner path; Dash offers the Dash Core signer path `m/44'/coin'/account'` and Purpose48 `m/48'/coin'/account'/0'`. Each address of the chosen branch and index range shows the Dash Core P2SH address (`7…`, testnet `8…`) and the Platform P2SH address of the same script (`dash1s…`, testnet `tdash1s…`); Advanced mode adds the script and the keys in script order. Every cosigner's child public key is shown, and for a phrase its child private key, hidden until private keys are revealed. The summary gives the checksummed watch-only descriptor `sh(sortedmulti(…))` or `sh(multi(…))` for Dash Core's `importdescriptors`. The Multi-Chain Edition also builds Bitcoin P2WSH (BIP48 `2'`), P2SH-P2WSH (BIP48 `1'`), legacy P2SH (Trezor `m/48'/0'/account'/0'` or Electrum `m/45'/0`), and two Taproot forms at the proposed BIP48 `3'` or BIP87 `m/87'/0'/account'` path, since BIP48 itself defines no Taproot type:

- **Taproot `multi_a`**: a true m-of-n, `tr(H, sortedmulti_a(…))` (BIP386/BIP387), one Tapscript leaf `<k1> OP_CHECKSIG <k2> OP_CHECKSIGADD … <m> OP_NUMEQUAL` under BIP341's provably unspendable internal key H, so the script is the only way to spend. Bitcoin Core's descriptor wallets and Coldcard support it.
- **Taproot MuSig2**: n-of-n only, `tr(musig(…)/branch/*)`. The cosigners' account keys, sorted, aggregate into one key (BIP327); its BIP328 node derives the addresses, which look like single-key Taproot addresses. The descriptor standard (BIP390) is a draft and few wallets sign with it yet. Each cosigner shows its participant key; there is no per-address child key to sign with.

Key order changes the address: sorted (BIP67, `sortedmulti`) is what descriptor wallets use; Dash Core's `createmultisig` and `addmultisigaddress` keep the given order, which **As entered** reproduces. A repeated cosigner is refused, as it silently lowers the real threshold. P2SH admits 15 compressed keys (a 520-byte redeem script), P2WSH 20. Holding every cosigner's phrase in one place undoes what multisig protects against, so the tab is meant for offline recovery and checking.

### Account descriptor export

Enter `0` explicitly for account or start index zero. An empty field is refused. Numeric controls accept decimal notation, including an exponent when its value is a whole number; hexadecimal, binary and octal prefixes are refused.

Selected-row exports require sensitive values to be shown before their text is assembled. Clear all, replacing a result, concealing sensitive values, or leaving the page cancels pending selected-row exports. Text already handed to the operating-system clipboard or a completed file download cannot be recalled; clear the clipboard when finished. Browser memory cleanup is best effort.

The Key Derivation Tool exports public and **unencrypted private** account descriptors for all four Bitcoin address profiles and Dash Core P2PKH families (BIP44, legacy mobile and mobile DIP9 CoinJoin). The default export is a ready-to-paste Core console import command covering receive and change, with active account branches, Core-managed address pools and a full historical rescan. Raw checksummed descriptor lines remain available for Scanner and other wallets. Public export cannot spend; private export grants account spending access. Public export is available without revealing sensitive values; private export requires revealing them. The **Account export** button opens a dialog with public and private copy/download actions. Other accounts, other Bitcoin address profiles, Dash Platform, Identity and Orchard are not included. See [account descriptor instructions](../../docs/ACCOUNT_DESCRIPTORS.md) for scope and Core import requirements.

Only change the default scheme or account when you know the source wallet’s derivation path. A different account produces different keys and addresses; other wallets may not discover its funds automatically. Exports preserve the selected account, including a nonzero account number. The deriver supports the selected scheme’s account controls, not arbitrary custom path templates.

MHFE checks raw phrase, container and repair-word input against its own UTF-8 byte limit, including whitespace, before interpreting the words. Repair-word choices come from the loaded MHFE package; a missing or unsupported choice is refused. Browser memory cannot be guaranteed to be erased.

## Feature-selective standalone builds

Canonical builds include every feature allowed by their edition profile. Custom builds are written under `dist/custom-builds/<profile>/` and never replace release artifacts.

```bash
pnpm build:key-derivation -- --profile multi-chain --features derive,bip85,seedqr
pnpm build:key-derivation -- --profile dash-community --exclude mnemocode,slip39,codex32,sskr,gordian-envelope
pnpm build:key-derivation -- --profile multi-chain --features derive,bip85,seedqr,slip39 --exclude slip39
```

`--features` starts from the named allowlist; `--exclude` starts from the edition's complete set and removes names. When both are present, exclusions are applied after the allowlist. The base `derive` feature is required. Available names are `derive`, `bip85`, `silent-payments`, `bip38-encrypt`, `message-signing`, `wallet-matcher`, `multisig`, `seedqr`, `mnemocode`, `mnemocode-cards`, `mhfe`, `slip39`, `codex32`, `sskr`, and `gordian-envelope`. `silent-payments` is available only in the multi-chain edition. Use `--output path/file.html` to choose a custom output path.

## The executable version

A browser runs MHFE's four Argon2 lanes in parallel only on a cross-origin isolated page, and a page opened as a file never is, so there MHFE uses one thread. The executable version is one program per platform, the Desktop file of a release (`Wallet_Key_Derivation_Tool_Desktop-linux-x86_64`, `-linux-aarch64`, `-windows-x86_64.exe`, `-macos-aarch64`, `-macos-x86_64`, and `Dash_Community_Key_Derivation_Tool_Desktop-<platform>` in the Dash Community edition): the whole Deriver, with the release's HTML page inside it. When it starts, it checks the page against the SHA-256 it was built with, serves it to this computer only (`127.0.0.1`, a port the system chooses) with the headers that make it isolated, and opens it in the default browser. MHFE then runs about two and a half to three times faster. Everything else works exactly as in the HTML file.

The program never receives what is typed into the page: it answers only `GET` and `HEAD` for `/`, checks the `Host` header, limits the size and duration of each request, and keeps no logs. Closing its window stops the server but not a tab that already shows the page; close the tab as well. A browser profile without extensions is the safest place to open it.

Its source is in [`launcher/`](launcher/). It needs no installation; its only dependency is RustCrypto's `sha2`, pinned in `Cargo.lock`. Build it for this computer after the HTML build with `node tooling/build-key-derivation-launchers.mjs` (add `--profile dash-community` for that edition, or `--platforms` for other platforms). A release build without the page fails. `pnpm build:reproducible:launchers` builds the Linux and Windows versions reproducibly in `Dockerfile.launchers`.
