## Confirmed findings

<a id="b-01--p1--legacy-sighash_single-incorrectly-labels-inputs-as-committed"></a>

### AUD-016-FUN001 — Not recorded — Legacy SIGHASH_SINGLE incorrectly labels inputs as committed

[signing-commitments.ts:108](../../apps/psbt-inspector/src/signing-commitments.ts).

With two inputs and one output, the UI reports `Current input: Committed` and `Other inputs: Committed` for the second Legacy input using `SIGHASH_SINGLE`. An unusual-policy warning is present, but these two claims are incorrect. In this historical case, the Legacy signature hash is the constant ONE, independent of transaction fields. SegWit v0 behaves differently; Taproot rejects a signature without the corresponding output.

Reference: [SignatureHash](https://github.com/bitcoin/bitcoin/blob/a604a7647588500354d4772e60620ea36b129d05/src/script/interpreter.cpp#L1615). Probe: `additional-results.json`, `legacy_single_missing_output`; browsers confirmed the text.

Fix: separate branches for the three protocols; do not claim input commitments for Legacy and explicitly describe the constant digest. Add tests for SINGLE/ANYONECANPAY and a missing output.

<a id="b-02--p1--optional-metadata-overrides-signing-protocol-detection"></a>

### AUD-016-FUN002 — Not recorded — Optional metadata overrides signing-protocol detection

[signing-commitments.ts:35](../../apps/psbt-inspector/src/signing-commitments.ts).

Adding a valid `PSBT_IN_TAP_INTERNAL_KEY` to a genuine P2PKH input with a verified non-witness UTXO is sufficient to trigger this issue. Metadata taking precedence over scriptPubKey makes the UI report `Taproot / BIP341` and `Current input amount: Committed`; Legacy does not include the amount in its signature hash. Core decodes the additional metadata, but it does not turn P2PKH into Taproot.

Reference: SigVersion selection from the spending script and [SignatureHash](https://github.com/bitcoin/bitcoin/blob/a604a7647588500354d4772e60620ea36b129d05/src/script/interpreter.cpp). Probe: `legacy_input_with_taproot_metadata` in `additional-results.json`, both browsers.

Fix: determine the protocol from the bound UTXO and verified redeem/witness script chain. Flag conflicting metadata separately. When data is insufficient, report uncertainty rather than a confident claim. This is a shared module; also check Dash, where these fields may be unknown.

<a id="b-03--p2--proprietary-psbt-key-structure-is-not-validated"></a>

### AUD-016-FUN003 — Not recorded — Proprietary PSBT key structure is not validated

[psbt-validation.ts:54](../../apps/psbt-inspector/src/psbt-validation.ts).

Keys `fc`, `fc00`, `fc036162`, and a key with a noncanonical identifier length are accepted in global/input/output maps. Core rejects them because the identifier/subtype is missing or CompactSize is noncanonical. In total, 12 negative probes produced a mismatch; both implementations accepted 3 valid control examples. The UI nevertheless reports successful framing/field-schema verification.

Reference: [PSBT_IN_PROPRIETARY](https://github.com/bitcoin/bitcoin/blob/a604a7647588500354d4772e60620ea36b129d05/src/psbt.h#L900) and corresponding global/output branches. Evidence: `additional-results.json`.

Fix: parse the structural part of a proprietary key with a bounded Reader, validate canonical lengths and the presence of a subtype, and preserve the opaque remaining key data and value. Do not reject valid unknown fields: they differ from a malformed known proprietary envelope.

<a id="b-04--p2--incorrect-psbtv2-locktime-compatibility"></a>

### AUD-016-FUN004 — Not recorded — Incorrect PSBTv2 locktime compatibility

[psbt-validation.ts:179](../../apps/psbt-inspector/src/psbt-validation.ts), [signing-commitments.ts:152](../../apps/psbt-inspector/src/signing-commitments.ts).

An input with both `height=800000` and `time=1700000000` is marked FAILED as incompatible. BIP370 permits both types as alternatives. When both are allowed, height is selected; a combination is incompatible only when requirements exclude a common alternative. The UI also displays time instead of the effective height.

Reference: [ComputeTimeLock](https://github.com/bitcoin/bitcoin/blob/a604a7647588500354d4772e60620ea36b129d05/src/psbt.cpp#L86), [official test with two alternatives](https://github.com/bitcoin/bitcoin/blob/a604a7647588500354d4772e60620ea36b129d05/src/test/psbt_tests.cpp#L105), [BIP370](https://github.com/bitcoin/bips/blob/master/bip-0370.mediawiki#determining-lock-time). Evidence: `edge-results.json`, both browsers.

Fix: compute the effective nLockTime consistently across the transaction; add separate tests for dual/height-only/time-only requirements, the maximum, and fallback. Core 31.1 did not validate this probe: it does not support v2 at all.

<a id="b-05--p2--advanced-p2sh-presets-export-descriptors-unsupported-by-core"></a>

### AUD-016-API001 — Not recorded — Advanced P2SH presets export descriptors unsupported by Core

[policy.ts:406](../../apps/psbt-inspector/src/policy.ts).

All 9 tested advanced P2SH presets return `sh(Miniscript...)`, described in the UI as a portable descriptor. Core accepts conventional P2SH `multi()/sortedmulti()`, but does not support Miniscript inside sh. Live getdescriptorinfo rejected all 9 exports. This is an incompatibility of the exported format and wallet workflow; deriving scriptPubKey/a P2SH address from such a script does not itself demonstrate a consensus defect.

Reference: [ParseScript grammar](https://github.com/bitcoin/bitcoin/blob/a604a7647588500354d4772e60620ea36b129d05/src/script/descriptor.cpp#L2723). Evidence: `policy-matrix-results.json`.

Fix: offer P2WSH/P2TR for portable Core policies; for custom P2SH, distinguish the raw watch-only descriptor, required redeemScript, and need for a custom verified signer. Do not describe such an sh export as a Core-importable descriptor.

<a id="b-06--p2--decaying--expanding-presets-also-cannot-be-imported-into-core"></a>

### AUD-016-API002 — Not recorded — Decaying / expanding presets also cannot be imported into Core

[policy.ts:276](../../apps/psbt-inspector/src/policy.ts).

These presets repeat the same keys in different branches. For P2WSH and P2TR, Core rejects the Miniscript as `not sane: contains duplicate public keys`. The local compiler also reports `not sane`, but the builder still creates a funding address and portable descriptor. Simply switching from P2SH to P2WSH therefore does not fix these two presets.

Reference: [IsSane / CheckDuplicateKey](https://github.com/bitcoin/bitcoin/blob/a604a7647588500354d4772e60620ea36b129d05/src/script/descriptor.cpp#L2727). Four RPC confirmations: `policy-matrix-results.json`.

Fix: either use a Core-compatible policy form without prohibited repetitions, with a separate equivalence check, or provide an explicitly separate advanced custom mode without promising import compatibility. Disabling safety analysis alone does not restore compatibility. Repeated keys are not, by themselves, evidence that funds can be stolen in this case.

<a id="b-07--p2--bitcoin-ranged-import-does-not-create-a-working-active-multisig-wallet"></a>

### AUD-016-BLD001 — Not recorded — Bitcoin ranged import does not create a working active multisig wallet

[multisig-wallet.ts:370](../../apps/psbt-inspector/src/multisig-wallet.ts).

The export sets `active:false`, omits next_index, and does not create a separate blank watch-only wallet. Import succeeds in an empty wallet, but getnewaddress/getrawchangeaddress return `This wallet has no available keys`. A pre-existing wallet retains its old active descriptors. Consequently, the user may continue receiving addresses belonging to a different wallet type.

Passive watch-only import is valid by itself; the problem is failure to implement the complete ranged-multisig creation workflow. Reference: [Core multisig workflow](https://github.com/bitcoin/bitcoin/blob/9be056a8a72b624dae9623b2f7bded92c2a21c91/test/functional/wallet_multisig_descriptor_psbt.py). Evidence: `rpc-results.json`; successful workflow after correcting only the scratch import — `workflow-results.json`.

Fix: separate passive watch-only import from creation of a new multisig wallet. The latter needs a separate blank wallet, active receive/change descriptors, the correct next_index, and wrapper/change-type selection. For a specific non-ranged address, active:false remains correct.

<a id="b-08--p2--valid-taproot-pkh-leaves-are-rejected"></a>

### AUD-016-FUN005 — Not recorded — Valid Taproot pkh leaves are rejected

[musig-descriptor.ts:228](../../apps/psbt-inspector/src/musig-descriptor.ts).

Two official positive examples using `tr(...,pkh(...))` produce `P2TR: invalid leaf script=pkh`. Core 31.1 accepts both and returns addresses. The cause is a leaf-script classifier restriction in Scure; the existing allowUnknownOutputs does not help with the already recognized pkh type.

Reference: [descriptor_tests.cpp:1157](https://github.com/bitcoin/bitcoin/blob/a604a7647588500354d4772e60620ea36b129d05/src/test/descriptor_tests.cpp#L1157), also line 1159. Evidence: `descriptor-results.json`, `additional-results.json`, both browsers.

Fix: integrate correctly validated Tapscript leaves without conflating ordinary output-script classification with Tapscript consensus rules; check the tree/hash/address against these two vector results. Do not disable all script checks without a replacement.

<a id="b-09--p2--the-decoder-accepts-syntactically-invalid-descriptors"></a>

### AUD-016-FUN006 — Not recorded — The decoder accepts syntactically invalid descriptors

[descriptor.ts:74](../../apps/psbt-inspector/src/descriptor.ts), [descriptor-compiler.ts:110](../../apps/psbt-inspector/src/descriptor-compiler.ts).

Official negative examples `addr(asdf)`, `sh(<pubkey>)`, and `multi(+1,...)` are accepted. The first two finish without compiledOutput instead of a clear error; the third actually compiles because of numeric coercion. Core rejects all three. `addr(asdf)` was confirmed in both browsers.

Reference: [descriptor_tests.cpp](https://github.com/bitcoin/bitcoin/blob/a604a7647588500354d4772e60620ea36b129d05/src/test/descriptor_tests.cpp#L1018), lines 1018/1029/1053. Fix: strict grammar and address validation for the selected network; distinguish “known format with unimplemented presentation” from “syntactically invalid.” Evidence: `descriptor-results.json`, `rpc-results.json`.

<a id="b-10--p2--staged-recovery-p2tr-loses-ranged-xpub-expressions-during-export"></a>

### AUD-016-API003 — Not recorded — Staged recovery P2TR loses ranged xpub expressions during export

[policy.ts:371](../../apps/psbt-inspector/src/policy.ts), [policy.ts:407](../../apps/psbt-inspector/src/policy.ts).

For `xpub/<0;1>/*` inputs, portableDescriptorBody is constructed, but for P2TR it is replaced by the materialized, index-specific taprootDescriptor. Core reports `isrange:false`; changing the index changes the descriptor itself. For the same inputs, the P2WSH descriptor remains ranged. This contradicts the README claim that ranged exports are preserved.

Evidence: `final-results.json`, `staged`: P2WSH indices 0/1 → isrange=true; P2TR indices 0/1 → false. The address for the current specific index is nevertheless correct.

Fix: preserve the original key expressions and binary tree in Taproot exports, displaying the materialized current address separately; check receive/change branches and multiple indices through deriveaddresses.

<a id="b-11--p2--different-origin-paths-are-incorrectly-prohibited"></a>

### AUD-016-FUN007 — Not recorded — Different origin paths are incorrectly prohibited

[multisig-wallet.ts:314](../../apps/psbt-inspector/src/multisig-wallet.ts).

Two cosigner xpubs with origins `m/48h/1h/0h/2h` and `m/48h/1h/1h/2h` are rejected. Core accepts them together and derives the combined multisig. Origins describe each key's provenance; matching account paths for all participants are not a Bitcoin multisig rule. The error text additionally contains a Dash-only example for Bitcoin.

Evidence: `additional-results.json`, `mixed_account_origins`. Fix: validate each origin separately; warn about unusual combinations while retaining mandatory descriptor/address verification by all participants. Do not automatically reject a valid combination.

<a id="b-12--p2--advertised-p2wsh-support-for-1720-keys-does-not-work"></a>

### AUD-016-FUN008 — Not recorded — Advertised P2WSH support for 17–20 keys does not work

[policy.ts:67](../../apps/psbt-inspector/src/policy.ts).

The top level and README allow up to 20 keys, but the shared validatePublicKeys limits them to 16. Probes with 15/16 succeed; 17/20 fail. Core accepts P2WSH sortedmulti with 16, 17, and 20 keys.

Evidence: `edge-results.json`, `policy-matrix-results.json`. Fix: wrapper/context-specific limits and script-number encoding above OP_16; retain the P2SH limit of 520 bytes and 15 compressed keys. Changing only the validation number is insufficient without compiled-script vectors.

<a id="b-13--p3--cli-export-omits-the-selected-network"></a>

### AUD-016-BLD002 — Not recorded — CLI export omits the selected network

[multisig-wallet.ts:164](../../apps/psbt-inspector/src/multisig-wallet.ts), [multisig-wallet.ts:379](../../apps/psbt-inspector/src/multisig-wallet.ts).

For testnet/regtest, `bitcoin-cli importdescriptors ...` is generated without a network flag. The command uses the CLI configuration's network, usually mainnet. The network cannot be inferred from a literal pubkey descriptor, so such an import can successfully land on the wrong network. An xpub for the wrong network will more often produce an explicit error, but that does not make the export self-contained.

Evidence: `edge-results.json`, network_mainnet/testnet/regtest. Fix: correct network flags or an explicit requirement to select the CLI chain. Testnet and signet use the same address versions, so the current combined UI model cannot automatically infer the required flag; this must be resolved explicitly.

## Cases that should not be treated as discovered defects

- Accepting valid unknown PSBT fields is necessary for compatibility. AUD-016-FUN003 concerns only malformed proprietary-key structure.
- An unavailable UTXO amount or missing BIP32 origins does not make every PSBT syntactically invalid.
- Decoding a policy that fails sanity checks with an explicit warning is useful; creating a portable Core wallet from it is a separate requirement.
- Hardened child derivation from an xpub alone is impossible. The seven corresponding positive C++ vectors test a context with private keys available; our public-only tool does not have that context.
- `combo()` specifies multiple output scripts; the absence of a single compiledOutput does not imply an incorrectly computed address. This is a presentation limitation.
- The initial suspicion about transaction version `0xffffffff` was not confirmed as a mismatch with Core31.1: both implementations display 4294967295. It was not included in the defect list.

## Remediation order and regressions

1. AUD-016-FUN001/AUD-016-FUN002: remove false signature claims; test legacy/BIP143/BIP341 and conflicting metadata separately.
2. AUD-016-FUN003/AUD-016-FUN004: structural parser and BIP370 locktime. Valid unknown records must remain accepted.
3. AUD-016-API001/AUD-016-API002/AUD-016-BLD001/AUD-016-API003: accurate, reproducible Core workflow and policy exports; end-to-end test with a real regtest node.
4. AUD-016-FUN005/AUD-016-FUN006/AUD-016-FUN007/AUD-016-FUN008/AUD-016-BLD002: complete grammar/context handling, key limits, and network selection.
5. Retain official PSBT/BIP67/descriptor vectors with the upstream commit and checksum. Negative tests must check more than exceptions: AUD-016-FUN001/AUD-016-FUN002/AUD-016-FUN004 affect report content after successful parsing.

## Review limitations

The complete Bitcoin Core C++ test suite was not run, and no new HTML, Docker, or WASM build was performed. Spending branches for all complex Miniscript presets and interactive MuSig2 signing did not undergo complete signing workflows. The main live workflow was 2-of-3 P2SH/P2WSH. This audit does not prove the absence of all defects; it records checked coverage and reproducible discrepancies.
