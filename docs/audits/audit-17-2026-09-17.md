## Assessment

No incorrect address, key, recovery secret, threshold reconstruction, network-operation dispatch or secret-bearing export was found in the supported typed UI flows. All official/reference-vector suites and the complete browser matrices passed. Input seeds remained unchanged in the derivation probes, exact large integers survived JSON/XLSX and history exports, and the network boundary forwarded every field of all 14 operations to the intended fixed service method.

Four defects were reproduced. One is a cryptographic API contract problem: invalid runtime format values silently select a different backup encoding. Three affect less common API/export edges. None exposes a private key or changes an address generated through the normal UI, but all four should be fixed because the package APIs and multi-coin exports are intended to fail closed and remain extensible.

## Findings

<a id="m-01--medium--invalid-sskr-and-ckd-shamir-format-values-silently-select-another-format"></a>

### AUD-017-API001 — Medium — Invalid SSKR and CKD Shamir format values silently select another format

- **Files:** [packages/recovery-backup/src/sskr.ts:18](../../packages/recovery-backup/src/sskr.ts#L18), [packages/recovery-backup/src/shamir.ts:172](../../packages/recovery-backup/src/shamir.ts#L172).
- `SSKR_ENCODING[encoding]` is passed directly to wasm-bindgen. An unknown JavaScript value yields `undefined`, which is converted to numeric zero and therefore selects Compact UR. Both creation and recovery were reproduced with an invalid runtime encoding and completed without an error.
- CKD Shamir uses `format === 'raw' ? raw : words`; every value other than the exact string `raw` selects Words. Creation was reproduced; decoding has the same branch.
- The current UI is protected because `selectedEncoding()` and `selectedFormat()` validate the `<select>` value before calling these APIs. Direct JavaScript callers, generated compositions and future UI code do not receive the same protection.
- **Impact:** a caller can request one representation and receive or interpret another valid representation without being told. The cryptographic secret is not changed, but backup format is part of the recovery contract and must not be guessed.
- **Recommended fix:** validate the discriminant at the public API boundary before WASM initialization or decoding. Add runtime-negative tests for both create and recover paths.

<a id="l-01--low--discovery-csv-drops-the-display-balance-for-every-non-dash-coin"></a>

### AUD-017-API002 — Low — Discovery CSV drops the display balance for every non-Dash coin

- **File:** [apps/discovery-scanner/src/export.ts:161](../../apps/discovery-scanner/src/export.ts#L161), used at [line 291](../../apps/discovery-scanner/src/export.ts#L291).
- The supposedly generic `balance_display` column calls `numericDash()`, which recognizes only `... DASH`. Reproduced Bitcoin `0.12345678 BTC` and Ethereum `1.25 ETH` findings produced an empty `balance_display` cell.
- `balance_atomic`, `balance_asset`, `balance_atomic_unit` and `balance_decimals` remain correct, so the exact monetary value is not lost. JSON and XLSX also preserve `balanceLabel`.
- **Recommended fix:** derive the decimal display from the exact atomic value plus the declared decimals, or parse against the finding's declared asset instead of the Dash ticker. Retain a future-adapter regression in addition to Bitcoin/Ethereum cases.

<a id="l-02--low--empty-section-warnings-are-mislabeled-as-csv-metadata-and-then-repeated"></a>

### AUD-017-API003 — Low — Empty-section warnings are mislabeled as CSV metadata and then repeated

- **File:** [apps/discovery-scanner/src/export.ts:245](../../apps/discovery-scanner/src/export.ts#L245).
- In the no-findings row, `section.warning` occupies the `metadata` position and the next expression includes the same warning again in `warnings`.
- **Impact:** the CSV remains rectangular, but consumers see a provider/scan warning under the wrong schema field and then see it twice.
- **Recommended fix:** emit an empty metadata cell for section-only rows and retain the warning only in the warnings column.

<a id="l-03--low--the-injectable-slip-39-random-source-is-not-checked-for-the-requested-length"></a>

### AUD-017-API004 — Low — The injectable SLIP-39 random source is not checked for the requested length

- **File:** [packages/recovery-backup/src/slip39.ts:369](../../packages/recovery-backup/src/slip39.ts#L369).
- `Slip39GenerateOptions.randomBytes` is public and is used for deterministic integrations/tests. A probe returning a zero-length array for every request still generated a valid 1-group/1-member share. The two missing identifier bytes are coerced through bitwise operators and produce identifier zero.
- The shipped UI never injects this callback and uses `secureRandomBytes`, so normal production generation is unaffected. A caller supplying a broken custom source can silently lose the expected identifier entropy; higher thresholds usually fail later from inconsistent byte lengths, which is an inconsistent contract.
- **Recommended fix:** wrap the callback and require a `Uint8Array` of exactly the requested length on every call, wiping and rejecting mismatched results.

## Verified data paths

### Derivation and presentation

- Exercised 21 transparent adapter/network combinations: all four Bitcoin address families on mainnet/testnet; Ethereum; Dash Core, legacy mobile, Platform, Identity, Purpose48 cosigner and Core-pkh cosigner on mainnet/testnet. Each probe checked deterministic repeatability, non-mutation of the input seed, result id, sequential indices, unique paths, unique field keys, non-empty values and field-role exports.
- Dash Orchard mainnet/testnet remained covered by its official key-component vectors, compiled-WASM ciphertext recovery, key-capability tests, sequential output validation and startup self-tests. DIP9 mainnet/testnet vectors also passed.
- Independent derivation suites compare Bitcoin/Dash results to external implementations and Ethereum to `ethers`/EIP-55 vectors. No mismatched address, WIF, xpub/xprv, Platform payload, Identity key group or export role was observed.
- `TRANSPARENT_ROLES` is a shared superset rather than an exact per-adapter schema. The formatter intersects it with fields actually present, so the current design does not create empty or cross-protocol exports. Exact per-adapter roles would make future static checks stronger but are not required to fix a current failure.

### Network boundary and providers

- A temporary dispatch probe exercised all 14 operations (`ping`, five Core operations, four Platform/Identity operations, Orchard page, generic history, UTXO batch and EVM batch). Every payload field and the same `AbortSignal` reached the intended `RecoveryNetworkApi` method without reordering or loss.
- Worker-side validators reject unknown/extra fields, malformed networks/hashes/tokens, oversized batches and out-of-range pages. Scanner-side validators then bind structured responses back to the requested address/hash/order and exact integer limits before accounting.
- The generic MessagePort client validates its envelope and leaves operation-specific value validation to consumers. Every current scan consumer performs that validation. Central per-operation response schemas could reduce reliance on this convention, but no unvalidated accounting path was found.
- Live providers were not queried during this audit. Their fixed-endpoint parsers, pagination, duplicate, mismatch, precision and fallback tests passed locally.

### Recovery and backup formats

- A temporary matrix round-tripped 16-, 20-, 24-, 28- and 32-byte BIP39 entropy through Standard/Compact SeedQR, CKD Shamir Raw/Words, SSKR Compact UR/Bytewords, grouped SLIP-39, shared/unsplit Codex32 and password/recipient/SSKR Gordian Envelopes. Codex32's separate 64-byte BIP32-seed mode also passed at 9-of-31.
- SeedQR matches the five retained SeedSigner vectors and rejects invalid lengths, word indices and BIP39 checksums. Intermediate BIP39 sizes work locally and remain documented as potentially unsupported by external SeedQR tools.
- SLIP-39 passes all 45 retained Trezor recovery vectors, both original and extendable formats, grouped thresholds, printable-ASCII passphrase rules, invalid checksum/padding/set/threshold cases and wrong-passphrase behavior defined by the standard.
- SSKR reconstructs the official BCR-2020-011 grouped vector through distinct quorums in tagged Compact UR and Bytewords. Duplicate/incomplete/damaged shares fail; legacy untagged CKD Bytewords remain readable.
- Codex32 passes official BIP93 valid, threshold and invalid vectors; supported lengths, identifier alphabet, repeated indices, mismatched sets, checksums and threshold errors are enforced.
- Gordian Envelope passed unencrypted, Argon2id password, two independent X25519 recipients, SSKR permit and included BIP39-passphrase paths. Wrong passwords/keys and insufficient SSKR records fail. Rust validates entropy and serializes the wrapper JSON itself. The TypeScript wrapper currently trusts that pinned WASM JSON shape; adding a small runtime schema is reasonable defense in depth, but no external or network-controlled data reaches that JSON boundary.
- Secret-adjacent byte buffers are wiped on the reviewed success and exception paths. Existing lifecycle tests deliberately force Shamir/SLIP-39 failures and passed.

### Exports

- Deriver `plain`, `structured` and rectangular TSV exports included every displayed row field, grouped Identity key fields, all applicable address/public/private roles and the secret flag. Spreadsheet formulas and TSV separators are neutralized.
- Discovery JSON preserves exact decimal strings and declared units; XLSX writes them as strings to avoid precision loss. CSV is rectangular and spreadsheet-safe, subject to AUD-017-API002/AUD-017-API003 above.
- Activity Viewer CSV/JSON/XLSX tests passed for Core, Platform, Identity, Orchard, batch errors, mixed modes and a future generic adapter. Orchard input material and unresolved raw inputs remain redacted.
