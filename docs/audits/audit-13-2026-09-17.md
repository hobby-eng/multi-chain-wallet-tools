## 1. Findings

### H-01 — High — Deriver artifact verifier requires non-existent element ids; `pnpm verify` and Docker fail

- **File:** [apps/key-derivation/scripts/verify-key-derivation-artifact.mjs:134-135](../../apps/key-derivation/scripts/verify-key-derivation-artifact.mjs#L134) — the required-id list contains `'Mnemonic construction details'` and `'BIP39 entropy · hexadecimal'`. ### M-01 — Medium — Discovery Scanner builds without `custom-paths` crash at startup

## 5. Module decomposition — assessment and recommendations

**What is right.** Feature installers with a uniform `install*(context)` signature; build-time virtual modules (`ckd:selected-*`) that select coins/features so excluded code is absent from the graph; shared codecs in `recovery-backup` with a single `sskr-groups.ts` validator; the Inspector split into `psbt-{types,binary,validation,utxo,verification,presentation}` behind a facade; `network-boundary` primitives separated from providers.

**What still hurts, in priority order.**

1. **Optional-function bags with `!` (Scanner).** `DiscoveryFeatureRuntime` exposes 16 optional functions and the view dereferences them with non-null assertions. This is exactly how M-01 happened and it will happen again for any new feature. Convert the Scanner to the Deriver pattern: one installer per feature (`installSeedDiscovery`, `installWatchOnly`, `installCustomPaths`, `installWalletMatcher`) that receives the view and registers its own DOM/handlers; the composition imports only the selected installers. Then absence of a feature equals absence of code and of its DOM, with no runtime branches.
2. **Three 700–1 100-line closures.** `createKeyDerivationController` (1 080 lines in one function), `createDiscoveryScannerView` (858), `createActivityBatchController` (~700). They are already surrounded by extracted helpers, so the remaining work is mechanical: Deriver → `derivation-session.ts` (worker lease + revision + streamed run), `result-state.ts` (branches/selection/paging), `feature-wiring.ts` (the table of installers); Scanner view → `seed-input-panel.ts`, `watch-only-panel.ts`, `custom-path-panel.ts`, `scan-progress.ts`, `results-tabs.ts`; Viewer batch → one handler per query kind plus a shared scheduler. Line count is not the goal; the goal is that each feature flag maps to one module the composition can drop.
3. **Feature metadata is repeated in four places.** Feature ids, their source files, HTML fragment markers, installer symbols, self-test entries and verifier id lists are hand-maintained in `key-derivation-features.mjs`, `*-composition.mjs`, `verify-*-artifact.mjs` and `BUILD_MODULES.md`. H-01 is a symptom (a verifier list edited by hand). A single manifest per tool (`{ id, files, htmlMarkers, installer, selfTest, requiredIds, docs }`) consumed by the builder, the graph allow-list, the verifier, the smoke matrix and a doc generator would remove that class of drift.
4. **`network-boundary/protocol.ts` split has no consumers.** The six focused modules are imported by nobody; all 24 importers still use the facade. Either migrate importers (and drop the facade) or drop the split; keeping both is the worst option.
5. **Merge candidates.** `apps/activity-viewer/src/export-{csv,json,text,workbook,public,common,model}.ts` (7 files, ~1 300 lines) and `apps/discovery-scanner/src/report-workbook.ts` re-implement CSV/XLSX/JSON writers that `packages/export-core` was created for; one `export-core/writers` with per-tool schemas would shrink both apps. `discovery-scanner/network-validation.ts` duplicates the intent of `network-boundary/request-validation.ts` (address batch/hash asserts) with different rules; keep one.
6. **Split candidate.** `packages/dash-network/src/platform-identity-history.ts` (707 lines) and `platform-identity-source.ts` (545) mix DAPI transport, proof decoding and history reconstruction; a transport/decoder/reconstruction split would let the Viewer and Scanner share the decoder without the transport.
7. **Keep as is.** Wordlists, generated WASM glue, `slip39.ts` (469 lines, 24 small functions, complete primitive), `shamir.ts`, the bounded binary readers.
