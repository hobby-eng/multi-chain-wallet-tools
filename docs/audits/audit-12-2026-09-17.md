## Findings requiring correction

<a id="f-01--p2-large-witness-transaction-txid-calculation-throws"></a>

### AUD-012-FUN001 — Not recorded — large witness transaction txid calculation throws

Location: `apps/psbt-inspector/src/transaction.ts:108`.

`parsedTransactionId` constructs the non-witness serialization with `Uint8Array.of(...bytes)`. This expands the transaction into function arguments and hits the engine's argument limit well below the input-size ceiling.

Probe: parse a synthetic witness transaction with 4,000 distinct inputs, empty scriptSigs, one output and a one-byte witness item per input; parsing succeeds, then txid calculation throws `RangeError: Maximum call stack size exceeded`. This demonstrates a parser/txid robustness failure, not that the synthetic transaction has valid spend signatures.

Fix: preallocate and use `set`, use a byte-concatenation helper, or hash the three serialization segments incrementally. Test against an independently constructed non-witness serialization.

<a id="f-02--p2-decoded-psbt-size-ceiling-is-not-enforced-for-base64"></a>

### AUD-012-API001 — Not recorded — decoded PSBT size ceiling is not enforced for Base64

Location: `apps/psbt-inspector/src/psbt-binary.ts:88`.

The 32,000,000-character check approximates a hexadecimal limit but is also applied to Base64. Base64 can decode to almost 24 MB before this check rejects it. The message promises a 16 MiB decoded ceiling, and even the hexadecimal branch uses decimal MB instead of MiB.

Probe: Base64 encoding of 17 × 1024 × 1024 zero bytes is accepted by `decodeText`, returning **17,825,792 bytes**. This tests the decoder's limit; it does not claim the zero buffer is a valid PSBT.

Fix: define one explicit byte limit, check each encoding's maximum input length before allocation, and enforce the decoded byte length in both branches.

<a id="f-03--p2-witness-flags-are-accepted-without-interpreting-supported-bits"></a>

### AUD-012-FUN002 — Not recorded — witness flags are accepted without interpreting supported bits

Location: `apps/psbt-inspector/src/transaction.ts:39`.

Any nonzero flag after the marker is treated as the ordinary witness flag. A synthetic flag-`0x02` transaction is accepted with `hasWitness: true`. The parser should reject unknown optional-data bits. It also does not retain whether all witness stacks were empty, which is needed to reject a superfluous witness serialization.

Reference: [Bitcoin Core transaction deserializer](https://github.com/bitcoin/bitcoin/blob/master/src/primitives/transaction.h) rejects remaining unknown flags and superfluous witness records; [BIP144](https://github.com/bitcoin/bips/blob/master/bip-0144.mediawiki) describes the flag bitvector and the empty-witness rule. The flag-`0x02` path was probed; the all-empty-stack path was identified by source inspection.

Fix: parse supported bits explicitly, reject remaining bits, track whether a witness stack is nonempty, and add positive/negative serialization cases.

<a id="f-04--p2-clipboard-fallback-leaves-its-temporary-textarea-after-an-exception"></a>

### AUD-012-SEC001 — Not recorded — clipboard fallback leaves its temporary textarea after an exception

Location: `packages/export-core/src/clipboard.ts:15`.

Cleanup follows `temporary.select()` and `document.execCommand('copy')` without a `finally`. If either throws, the attached hidden textarea retains the copied text, potentially a mnemonic or private key.

Probe with a minimal fake DOM and throwing `execCommand`: `removed: false`, `retainedValue: true`. This is an exceptional-path lifecycle issue, not evidence of network exfiltration.

Fix: place selection/copy in `try/finally`, clear the textarea value and remove the element in the cleanup path. Do not claim clearing a DOM reference wipes immutable JavaScript strings.

<a id="f-05--p2-backup-cleanup-still-has-exceptional-path-gaps"></a>

### AUD-012-SEC002 — Not recorded — backup cleanup still has exceptional-path gaps

Locations:

- `packages/recovery-backup/src/shamir.ts:253`: decoding all shares with `map` happens before the cleanup scope. If a later share fails to decode, earlier decoded shares do not reach explicit wiping.
- `packages/recovery-backup/src/shamir.ts:274`: initialization occurs after allocating packed share bytes but before the packed-buffer `try/finally`.
- `packages/recovery-backup/src/slip39.ts:323`: a throwing PBKDF2 call bypasses cleanup of its password and round-input buffers.
- `packages/recovery-backup/src/slip39.ts:369`: a throwing `crypt` call bypasses the passphrase wipe.
- `packages/recovery-backup/src/slip39.ts:248`: partial splitting/allocation failures also need an ownership-aware cleanup scope.

The earlier Shamir split-randomness fix is present and its test passes. These are additional paths, not a claim that the earlier fix was absent.

Probe: replace only PBKDF2 at the in-memory bundling boundary with a throwing stub that retains its supplied password buffer. After `createSlip39Shares` fails, `passwordBufferWiped: false`. Other listed paths were confirmed by control-flow inspection.

Fix: begin cleanup scopes immediately after owning each allocation, decode incrementally inside the protected scope, and clean up partially created shares on failure. Preserve returned successful buffers and caller-owned inputs.

<a id="f-06--p3-linked-source-wording-overstates-isolation-in-key-deriver"></a>

### AUD-012-DOC001 — Not recorded — linked-source wording overstates isolation in Key Deriver

Location: `apps/key-derivation/src/ui/recovery-workspace.ts:119`.

The tooltip says the source remains inside an “isolated vault.” In this tool, `app-bootstrap.ts` installs Derive and Recovery into the same document and transfers a callable `RecoverySourceReference.read()`. The key-derivation build embeds an offline document plus a derivation worker; it does not construct Discovery Scanner's separate sandboxed iframe.

The no-clipboard handoff is real, and the offline CSP is a separate protection. The text should accurately describe an in-memory reference inside the offline workspace unless a separate compartment is deliberately implemented. This is a misleading security description, not a demonstrated leak.

## What should remain cohesive

Do not split wordlists, generated WASM bindings, bounded low-level binary readers, or a complete small cryptographic primitive merely to reduce line counts. Keep exception cleanup next to resource ownership. Coin-specific implementations should remain modular internally but be selected together by `--coins`, as requested. Keep one public adapter contract and avoid forcing every coin into Dash-specific modes.

Repository-wide source searches found no direct `eval`, `new Function`, `innerHTML`, localStorage/sessionStorage use or executable `Math.random` fallback in the searched TypeScript source. This is a limited search result, not a security guarantee about dependencies, generated code or all browser behavior.

## Recommended order

1. Correct AUD-012-FUN001 through AUD-012-SEC002 and add focused regression tests for those failure paths.
2. Correct AUD-012-DOC001 wording and remove the two confirmed unused helpers.
3. Split PSBT's remaining parse/validate/presentation responsibilities, preserving existing APIs.
4. Extract Deriver session/state and Discovery input/result modules.
5. Consolidate Activity query handlers, history models and format writers.
6. Run affected checks once per coherent change and rebuild HTML only when requested.

The current passing tests do not cover the reproduced edge cases. This report recommends specific boundaries and fixes; it does not claim the repository is fully optimal or free of other bugs.

## Remediation status

The findings above describe the audited snapshot. The following changes were subsequently applied in this working tree:

- **AUD-012-FUN001:** transaction identifiers now concatenate the serialized chunks before double-SHA256, avoiding spread-argument limits on large witness transactions.
- **AUD-012-API001:** hexadecimal and Base64 PSBT inputs enforce the same 16 MiB decoded-size ceiling before allocation/parsing.
- **AUD-012-FUN002:** transaction parsing rejects unknown witness flag bits and superfluous all-empty witness serialization; focused edge cases cover both paths.
- **AUD-012-SEC001:** clipboard fallback clears and removes its temporary field from a `finally` block, including selection/copy exceptions.
- **AUD-012-SEC002:** CKD Shamir and SLIP-39 cleanup scopes now own partially decoded/generated buffers and wipe them on exceptional paths; lifecycle regression tests cover the reproduced failures.
- **AUD-012-DOC001:** linked-source copy now describes a temporary in-memory reference within the offline workspace and no longer claims a separate isolated vault.

The modularization recommendations were also applied without changing the public build-feature model. PSBT parsing is split into type, binary, validation, UTXO, verification, and presentation modules behind the existing facade. Deriver settings, automatic scheduling, self-tests, streaming and exports have separate owners. Discovery uses separate Core and Platform network services plus progress, estimate, validated-export and result-view modules. Activity uses shared batch query handlers, separate result renderers and typed format writers. Common CSV encoding, byte comparison, compact-message primitives, SSKR group validation and bounded HTTP lifecycle moved to shared packages.

The two confirmed unused helpers were removed. The duplicate application-local Dash descriptor detector was also removed because the active implementation is `packages/wallet-recovery/src/watch-only/dash.ts`. The obsolete test-only `createVaultChannel` was removed in favor of the production `bootstrapIsolatedBoundary`; the tested Orchard transition primitive now drives the production stream loop; the QR test exercises the shared production matrix encoder and the payment payload ceiling is enforced by `createPaymentQrAction`.
