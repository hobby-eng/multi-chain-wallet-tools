## 1. Confirmed findings

### F-01 — High — Canonical reproducible build fails at HEAD (`pnpm verify` inside `Dockerfile.reproducible`)

- **Files:** [tooling/build-recovery-shamir-wasm.mjs:7-13](../../tooling/build-recovery-shamir-wasm.mjs#L7), [tooling/build-recovery-codex32-wasm.mjs:7-13](../../tooling/build-recovery-codex32-wasm.mjs#L7); compare [tooling/build-shielded-wasm.mjs:7-22](../../tooling/build-shielded-wasm.mjs#L7).
- **Observed:** `docker build --platform linux/amd64 --network host -f Dockerfile.reproducible --build-arg SOURCE_COMMIT=cdce70cb… --build-arg SOURCE_DIRTY=false --target artifacts .` fails at `Dockerfile.reproducible:68` (`RUN --network=none pnpm verify`) with `Error: spawnSync /.tools/cargo/bin/cargo ENOENT` raised by `build-recovery-shamir-wasm.mjs` right after "Generated pinned Dash Orchard browser WASM." (log `audit3/docker-full.log`, exit 1 after 62 s of the verify layer). Two attempts, same result.
- **Cause:** both new scripts compute `tools = <repo>/.tools` or `<repo>/../.tools` and then `cargo = resolve(tools, 'cargo/bin/cargo')` unconditionally. The Orchard script uses the same lookup but falls back to `CARGO_HOME`/`PATH` (`'cargo'`, `'wasm-bindgen'`) when the local toolchain directory is absent. In the container the toolchain lives at `/root/.cargo/bin` and `.tools` is excluded by `.dockerignore`, so `/.tools/cargo/bin/cargo` does not exist. Locally the same command succeeds only because `../.tools/cargo/bin/cargo` exists on this host (`pnpm verify` exit 0, 17:19 UTC).
- **Impact:** `.github/workflows/ci.yml`, `full-wasm.yml`, `release.yml` and `./tooling/build-reproducible.sh` all run this Dockerfile; none can succeed on this commit, so no canonical artifacts, `verification-record.json`, attestations or release can be produced. The `docs/ARCHITECTURE.md` and `SECURITY_AUDIT.md` statements that the Docker path defines release bytes are correct in design but not currently achievable.
- **Correction:** adopt the Orchard script's resolution (local `.tools` → `CARGO_HOME` → `PATH`), or factor one shared `resolveRustToolchain()` used by all three scripts. Add a unit test that runs the resolver with a fake root lacking `.tools` and asserts it yields `cargo`/`wasm-bindgen` from `PATH`. The bounded matrix smoke in the same Dockerfile never ran because the earlier layer failed.

### F-03 — Medium — `--output` overwrites canonical release artifacts with a selective build

- **Files:** [tooling/tool-feature-options.mjs:103-105](../../tooling/tool-feature-options.mjs#L103), [tooling/key-derivation-features.mjs:110-112](../../tooling/key-derivation-features.mjs#L110), [tooling/build-html-profiles.mjs:26-29](../../tooling/build-html-profiles.mjs#L26).
- **Observed:** `node tooling/build-html-profiles.mjs --profile multi-chain --tool key-derivation --coins dash --output dist/multi-chain-edition/key-derivation/Wallet_Key_Derivation_Tool.html` succeeded and replaced the canonical artifact (SHA-256 `c9194584…` → `d309be5e…`) while `dist/multi-chain-edition/SHA256SUMS` still listed the old digest. ### F-04 — Low — WASM bridge errors are strings, so the Recovery UI hides the real reason

- **Files:** [packages/recovery-codex32-wasm/rust/src/lib.rs](../../packages/recovery-codex32-wasm/rust/src/lib.rs) and [packages/recovery-shamir-wasm/rust/src/lib.rs](../../packages/recovery-shamir-wasm/rust/src/lib.rs) (`JsValue::from_str`), [apps/key-derivation/src/ui/recovery-codex32.ts:99-126](../../apps/key-derivation/src/ui/recovery-codex32.ts#L99), [apps/key-derivation/src/ui/recovery-shamir.ts:45-60](../../apps/key-derivation/src/ui/recovery-shamir.ts#L45).
- **Observed (probe R4):** recovering BIP93 vector 3 with two of three shares throws the primitive string `Codex32 interpolation failed: ThresholdNotPassed { threshold: 3, n_shares: 2 }`; mixing an upper-case and lower-case share throws `… MismatchedHrp("ms", "MS")`. The UI catch blocks use `cause instanceof Error ? cause.message : 'Codex32 restoration failed.'`, so users see only the generic sentence. The Rust `{error:?}` Debug formatting is also not user-facing text.
- **Correction:** wrap bridge failures in `Error` inside `codex32.ts`/`shamir.ts` (or use `describeUnknownError`, which already handles strings) and map the known variants to plain sentences ("2 of 3 required shares were entered"). Add tests for the three cases above.

### F-05 — Low — CKD Shamir format cannot detect a consistent-looking wrong share

- **File:** [packages/recovery-backup/src/shamir.ts](../../packages/recovery-backup/src/shamir.ts).
- **Observed (probe R7):** a raw share whose payload byte was flipped and whose 4-byte SHA-256 trailer was recomputed recovers a *different* 32-byte secret without any error, and that entropy always converts to a valid-looking BIP39 phrase. The per-share checksum protects against accidental corruption only; nothing binds the shares to the secret (SLIP-39 uses a digest share for this; BIP93 has the same limitation by design).
- **Assessment:** not a vulnerability (an adversary who can alter a share can also withhold it), but a recovery-safety gap for the stated audience: a wrong-but-consistent set silently produces a plausible phrase. The documentation calls the format "checksummed" without stating this.
- **Correction:** in a versioned format update include a truncated digest of the secret (SLIP-39 style) or an HMAC share; until then document the limitation next to the "verify with a standard wallet" advice. Keep the positive property found here: word shares are 27–39 words and never validate as BIP39 mnemonics (`validateMnemonic` false), so they cannot be confused with a seed phrase.
