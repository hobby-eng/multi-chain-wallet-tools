## Assessment

The repository is in materially better shape than the 2026-09-12 first-pass audit found: every repository check passes locally, the canonical Docker build is reproducible byte-for-byte across two independent builds (one with `--no-cache`), the container-regenerated Orchard WASM equals the committed bytes, the official-vector fixture is byte-identical to a fresh extraction from the pinned upstream revisions, and derivation output for Bitcoin, Ethereum and every Dash family matches an independent Go/btcd derivation plus hand-written encoders at boundary indices.

Two confirmed defects still block a release advertised as verified:

1. **IA-01 (High):** the Inspector compiles `multi()`/`sortedmulti()` descriptors with 21 or more keys under `wsh()` into a P2WSH address and labels the policy "sane · signature required". Consensus limits `OP_CHECKMULTISIG` to 20 keys, so funds sent to such an address are unspendable.
2. **IA-02 (Medium):** the Multi-Chain Key Derivation Tool crashes the Firefox page deterministically whenever an in-flight derivation worker is terminated by Clear, Cancel or a protocol-tab switch. This is not the "intermittent BIP85 reload crash" the documentation tracks; BIP85 and reload are irrelevant.

The remaining findings are Low or Informational: misleading multisig ordering rows for `sortedmulti`, PSBT relationships that are accepted without cross-checking, an artifact-verification gap for the Dash Community Inspector, and test-coverage claims that are broader than what the suites actually assert.

No secret-exfiltration path, storage persistence, unexpected network request, or CSP bypass was found in any artifact in either browser.

### IA-01 — High — Confirmed: `multi()`/`sortedmulti()` with more than 20 keys compiles to an unspendable P2WSH output labelled sane

- **Files/lines:** [apps/psbt-inspector/src/miniscript-engine.ts:452-481](../../apps/psbt-inspector/src/miniscript-engine.ts#L452) (`compilePolicyMiniscript` validates key encodings but not key counts), [apps/psbt-inspector/src/descriptor.ts:560-586](../../apps/psbt-inspector/src/descriptor.ts#L560) (`validateDescriptorMiniscript`), [apps/psbt-inspector/src/descriptor.ts:461-497](../../apps/psbt-inspector/src/descriptor.ts#L461) (`compiledDescriptorOutput` emits the address).
- **Affected:** Multi-Chain PSBT & Multisig Inspector, descriptor decoding path (`wsh`, `sh(wsh)`, bare). The Dash Community Inspector only compiles `sh()` where the 520-byte redeem-script limit already stops more than 15 compressed keys, so it is not affected by the unspendable case. The policy builder and ranged-wallet builder cap keys at 16 and are not affected.
- **Trigger (public):** `wsh(multi(1,K0,…,K20))` where `K_i` is the compressed child `i` of the BIP32 test-vector-1 master xpub `xpub661MyMwAqRbcFtXgS5sYJABqqG9YLmC4Q1Rdap9gSE8NqtwybGhePY2gZ29ESFjqJoCu1Rupje8YtGqsefD265TMg7usUDFdp6W1EGMcet8` (all keys distinct).
- **Observed:** address `bc1q9q67755plv5t8amhcx0ng26g2mqzz4jxtkpkaptzn8250m4drafq3g9ezy`, witness script 718 bytes, analysis "sane · non-malleable satisfactions available · signature required · compatible timelock units · no duplicate keys". The same happens with 25 keys (854 bytes) and with `sortedmulti`. `compilePolicyMiniscript` returns `sane=true` directly; `analyzeMiniscript` from `@bitcoinerlab/miniscript` reports `valid:true, issane:true`.
- **Independently expected:** rejection. Bitcoin Core `script/script.h:35` defines `MAX_PUBKEYS_PER_MULTISIG = 20`; `script/interpreter.cpp:1127` fails script execution with `SCRIPT_ERR_PUBKEY_COUNT` when `nKeysCount > 20`; `script/descriptor.cpp:2431-2432` rejects the descriptor ("Cannot have %u keys in multisig; must have between 1 and 20 keys, inclusive"); `script/miniscript.h:1901` marks the fragment invalid; BIP383 states "Otherwise the maximum number of keys is 20". The Go/btcd oracle (`btcutil-js` `descriptors.create`) also accepts 21 keys, so the existing Go differential cannot detect this class of error.
- **Impact:** a user who funds the displayed address cannot spend the output under consensus rules; the UI affirmatively states the policy is sane and needs a signature. This is the same failure class as the first-pass F01 (displayed analysis differs fundamentally from consensus).
- **Related Low sub-findings (same root cause: no key-count validation):** `tr(KEY,multi_a(1,<1000 keys>))` compiles although BIP387 and Core (`MAX_PUBKEYS_PER_MULTI_A`, `descriptor.cpp:2434`) allow at most 999; bare `multi(1,<4…20 keys>)` compiles as "Bare multisig" although Core (`descriptor.cpp:2446`) allows at most 3 keys at the top level and such outputs are non-standard.
- **Minimal correction:** enforce `1 ≤ k ≤ n ≤ 20` for `multi`/`sortedmulti`, `n ≤ 999` for `multi_a`/`sortedmulti_a`, and `n ≤ 3` for top-level bare `multi`, before compilation and before any "sane" label, in `compilePolicyMiniscript` (context-aware) and in `validateDescriptorMiniscript`.
- **Required regression test:** `decodeDescriptor('wsh(multi(1,<20 distinct keys>))')` compiles; 21 keys throws with a key-count message; `sortedmulti` identical; `multi_a` 999 compiles and 1000 throws; bare `multi` with 4 keys throws. Add a Core Miniscript-style invalid vector for 21 keys.
- **Why existing tests missed it:** the 97 Core Miniscript vectors contain no multisig above 15 keys; the Go oracle shares the omission; the builder tests only go to 16 keys; no test asserts key-count limits.

### IA-02 — Medium — Confirmed: Firefox page crash when an in-flight derivation worker is terminated (Multi-Chain Key Derivation Tool)

- **Files/lines:** [apps/key-derivation/src/ui/controller.ts:828-831](../../apps/key-derivation/src/ui/controller.ts#L828) (`stopActiveDerivation` → `terminate()`), [apps/key-derivation/src/ui/controller.ts:1544-1547](../../apps/key-derivation/src/ui/controller.ts#L1544) (Clear everything), [apps/key-derivation/src/ui/controller.ts:1970-1975](../../apps/key-derivation/src/ui/controller.ts#L1970) (Cancel), [apps/key-derivation/src/ui/controller.ts:1159-1164](../../apps/key-derivation/src/ui/controller.ts#L1159) (`resetForAdapter`), [apps/key-derivation/src/workers/derive-client.ts:158-164](../../apps/key-derivation/src/workers/derive-client.ts#L158) (`terminate` + `revokeObjectURL`).
- **Affected:** `dist/multi-chain-edition/key-derivation/Wallet_Key_Derivation_Tool.html` in Firefox 153.0 (Playwright build 1538). Not reproduced in Chromium 151 (0/9 attempts) nor in `Dash_Community_Key_Derivation_Tool.html` under the same Firefox (0/3).
- **Trigger (public):** open the artifact via `file://`, enter the Trezor phrase `abandon ×11 about`, count 1, wait about 400 ms for automatic derivation to start, then click **Clear everything** (3/3 crashes), or click **Cancel generation** during a 20-row derivation (3/3), or click a protocol tab and then Clear (3/3), or click another protocol tab while deriving (3/3). Waiting for the derivation to finish before Clear does not crash (0/3). Clearing before any derivation started does not crash (0/3). The repository's own extended browser suite reproduces it in `bip85-child-signer` (`page.reload: Page crashed`): the crash happens at `#protocol-tabs … click` followed immediately by `#clear-all`, and only becomes visible at the later reload.
- **Observed:** Playwright reports the `crash` page event within 1.5 s; the content process is gone (subsequent `page.reload` fails with "Page crashed"). No JavaScript `pageerror` precedes it.
- **Independently expected:** terminating a Web Worker must not crash the browser page. A synthetic test that creates a 12 MB Blob-URL worker and terminates it immediately (with and without `revokeObjectURL`) did not crash Firefox (0/8), so the trigger is specific to this worker's content (the Multi-Chain worker embeds the Orchard WASM and the ~10 MB Go/btcd BIP-322 WASM; the Dash Community worker embeds only Orchard and does not crash). The exact Firefox root cause was not established in this audit; a Firefox crash dump from a headed run is required to name it.
- **Impact:** loss of the working session and any displayed results; the crashed content process may be captured by Firefox's crash reporter together with seed material in memory (the security document already lists crash dumps as a residual risk). It is a reliability defect with a privacy consequence, not a cryptographic one.
- **Minimal correction:** do not terminate the worker while its script/WASM is still initialising — wait for the worker's `ready` message (already sent by `worker-runtime.ts`) before calling `terminate()`, or post a cancellation message and let the worker exit itself; keep `revokeObjectURL` after `ready` only. Validate the fix with a headed Firefox run and a crash dump.
- **Required regression test:** an extended-browser case in both engines and both editions: start a derivation, immediately click Clear, Cancel, and another protocol tab; assert no `crash` event and that the page still responds.
- **Why existing tests missed it:** the acceptance suite always waits for `#results` before clearing; the extended suite hit it only through the BIP85 case and attributed it to reload.

### IA-03 — Low — Confirmed: `sortedmulti` descriptors show a contradictory "supplied order preserved" row; `sortedmulti_a` is described as "key order preserved"

- **Files/lines:** [apps/psbt-inspector/src/descriptor.ts:371-382](../../apps/psbt-inspector/src/descriptor.ts#L371) (`calls()` uses `indexOf('multi(')`, which also matches inside `sortedmulti(`), [apps/psbt-inspector/src/descriptor.ts:678](../../apps/psbt-inspector/src/descriptor.ts#L678) and [:697-712](../../apps/psbt-inspector/src/descriptor.ts#L697).
- **Trigger:** `wsh(sortedmulti(2,K0,K1))` and `tr(K2,sortedmulti_a(2,K0,K1))` with the same public keys as IA-01.
- **Observed:** rows "Multisig 1 · key order = Supplied order preserved · multi()" and "Multisig 2 · key order = BIP67 lexicographic sort · sortedmulti()" for one `sortedmulti`; "Tapscript multisig 1 = 2-of-2 · key order preserved" for `sortedmulti_a`.
- **Expected:** exactly one multisig row stating BIP67 sorting; `sortedmulti_a` must state lexicographic x-only sorting. The compiled script itself is sorted correctly (Go-verified), so the defect is display-only, but it contradicts the security document's statement that supplied and sorted order are never conflated.
- **Correction:** derive these rows from the parsed expression tree (`ExpressionNode.name`) instead of substring scans.
- **Regression test:** assert the exact multisig row set for `multi`, `sortedmulti`, `multi_a`, `sortedmulti_a`.

### IA-04 — Low — Confirmed: PSBT cross-field relationships are accepted without verification

- **Files/lines:** [apps/psbt-inspector/src/psbt.ts:380-401](../../apps/psbt-inspector/src/psbt.ts#L380) (`validateMusigPsbtFields`), [:253-269](../../apps/psbt-inspector/src/psbt.ts#L253) (`inputValue`), [:282-349](../../apps/psbt-inspector/src/psbt.ts#L282) (`validateMap`), [:350-365](../../apps/psbt-inspector/src/psbt.ts#L350) (`validateVersionFields`).
- **Reproduced acceptances (synthetic PSBTs built from generator points, all "ACCEPTED"):** MuSig2 participant list whose aggregate key is not `KeyAgg(participants)`; a public nonce and a partial signature for a participant absent from the list; duplicate participants; a non-DER partial signature value `ff`; a redeem script under a witness UTXO whose scriptPubKey is not its hash; a witness script under a P2WPKH UTXO; a Taproot leaf whose control-block internal key differs from `PSBT_IN_TAP_INTERNAL_KEY`; a BIP32 derivation path of 300 levels (BIP32 depth is at most 255); output amounts of 2^63 (above `MAX_MONEY`, fee displayed as 9223372036854774908); PSBTv2 inputs requiring a height lock and a time lock respectively (unsatisfiable per BIP370); `PSBT_GLOBAL_TX_MODIFIABLE` with reserved bits set.
- **Assessment:** the UI labels amounts "not chain-verified" and the documentation states that structural acceptance is not signature validation, so this is a scope limitation rather than a false claim. However the MuSig2 aggregate/participant relationship, the redeem/witness-script commitments and `MAX_MONEY` are cheap, deterministic checks whose absence lets a malicious PSBT present a coherent-looking summary.
- **Correction:** add the four cheap checks (KeyAgg consistency, participant membership for nonce/partial-signature keys, script-hash commitments against witness UTXOs, `MAX_MONEY`), and render a visible "unverified relationships" list for the rest.
- **Regression tests:** one positive and one negative fixture per relationship, using public generator keys.

## 9. Maintainability findings (each tied to a defect or test risk)

1. Substring-based extraction in `descriptor.ts` (`calls()` for `multi`, `multi_a`, `older`, `after`, hashlocks, and the `xpubs` regex) produced IA-03 and can double-count; the parsed `ExpressionNode` tree already exists and should be the single source for rows, cards and summaries.
2. Three grammar layers — `expression()` in `descriptor.ts`, `musigExpressions()`/`fragment()` in `musig-descriptor.ts`, and the regexes in `descriptor-key.ts`/`compilePolicyMiniscript` — each re-validate keys; IA-01 shows a limit that none of them owns. One typed parse with per-context validation (key encoding, key count, wrapper limits) would close this class.
3. `import` statements at the end of `descriptor.ts` (lines 802–808) and a duplicated BIP380 checksum implementation (`descriptor.ts:55-80` vs `packages/export-core/src/descriptor.ts`) are known and tracked in the roadmap; the duplication is not a defect today because both implementations produced identical checksums in every probe.
4. `apps/key-derivation/src/ui/controller.ts` (2053 lines) mixes eight independently revisioned workflows; IA-02 shows that worker lifecycle rules (when a worker may be terminated) are implicit. A small `WorkerLease` abstraction with an explicit `ready` state would make the Firefox mitigation testable.
5. `apps/psbt-inspector/src/psbt.ts` mixes framing, per-field schema and cross-field relationships in `validateMap`; IA-04 relationships would fit a separate "relationship checks" table that also drives the UI's verified/unverified wording.
6. `tooling/verify-dash-community-artifacts.mjs` hard-codes the tool list instead of iterating `profileToolIds(profile)` (IA-05).
7. The PSBT invalid-corpus test should assert an expected error category per vector (IA-06); the Core Miniscript test should compile `"?"` vectors and compare the mode flags.

## 10. Residual limitations and static/unconfirmed observations

- Firefox root cause (IA-02) is characterised behaviourally but not at the engine level; a crash dump from a headed run is needed.
- Static/Unconfirmed: DashScan semantics for an address whose only transactions are unconfirmed (`txCount 0`, `pagination.total 1`) would make `queryDashScan` fail with "changed during pagination"; whether the live API reports pending rows in `total` was not observed.
- Static/Unconfirmed: whitespace inside a descriptor is removed before checksum verification (`pkh( KEY )` is accepted); Bitcoin Core treats spaces as significant, so a checksum computed by Core over a spaced descriptor would be reported as invalid here, and vice versa.
- `older(65536)` is displayed as "0 blocks" (BIP68 mask semantics) and analysed as valid; the UI does not warn that such a lock is effectively absent.
- `deriveDashPlatform` accepts any hardened key class at the API level (DIP17 defines `0'` and `1'`); the UI restricts the control, the library does not.
- MuSig2: no signer/coordinator exists; nonce lifecycle, reuse prevention and partial-signature verification are not implemented and are correctly not claimed.
- Live provider checks prove reachability and schema for public fixtures only; adversarial provider behaviour is covered by mocked probes.
- No independent libsecp256k1 or Bitcoin/Dash node was available as a third execution oracle; Go/btcd and Noble/Scure remain the two executed implementations.

## 13. General recommendations and feature suggestions

- **Release gating:** make the extended browser suite part of the release checklist with a required 34/34 result; today the documentation records a green matrix that the current build does not reproduce.
- **Consensus-limit table:** centralise script/policy limits (key counts, 520/10 000 byte limits, `MAX_MONEY`, BIP68/BIP65 thresholds, tree depth 128) in one module consumed by the descriptor decoder, the policy builder and the tests, so a limit missing in one path is visible.
- **Verified/unverified matrix in the Inspector UI:** show, per PSBT input, which relationships were checked (framing, field schema, UTXO binding, preimages) and which were not (signatures, script commitments, MuSig aggregation), rather than a single "not chain-verified" note.
- **Worker readiness contract:** await the worker `ready` message before allowing termination; expose a visible "initialising cryptography…" state so users understand the delay in the 12 MB Multi-Chain Deriver.
- **Useful features (in order of value for the stated audience):**
  1. Offline PSBT sanity checks that require no signing: fee-rate display in sat/vB with a warning threshold, change-output detection against imported public descriptors, and address-reuse warnings.
  2. Descriptor import validation against a wallet policy file (BIP388 wallet policies) so multisig users can confirm a PSBT's inputs belong to their known policy.
  3. A "compare two exports" mode in the Deriver that diffs two descriptor/xpub sets (useful when migrating between wallets).
  4. Optional Electrum seed mode already listed in the roadmap; keep it a separate explicit mode with vectors.
  5. Testnet-only "practice mode" banners and a one-click testnet faucet link list for users following the "test with valueless funds first" advice.
  6. A signed, machine-readable verification record (`verification-record.json`) emitted by `pnpm verify` with commit, toolchain, and artifact hashes, so audit reports can reference one canonical file instead of prose tables.
