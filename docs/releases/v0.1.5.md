# Multi-Chain Wallet Tools v0.1.5

**In preparation.** The release candidate v0.1.5-rc.1 is published; the release date is set when v0.1.5 itself is published. Both editions carry version 0.1.5. They are built from the same tagged source revision. This document lists changes made after v0.1.4.

- Added fourteen coins to the Multi-Chain Deriver, mainnet only: the coins of MHFE's wallet check, Bitcoin Cash (CashAddr, coin type 145 or 0), Cosmos, Dogecoin, Ethereum Classic, Injective, Litecoin (BIP44, BIP49, BIP84), Tron, XRP and Zcash's transparent addresses (startup addresses found at the same paths by MnemoCode's own derivation, encodings checked against Trust Wallet wallet-core's address vectors, account keys and WIF private keys recomputed by an independent reimplementation), and the Ed25519 coins Hedera (its SDK's Ed25519 and ECDSA keys), NEAR, Solana (Phantom and Ledger paths), Stellar (SEP-0005) and TON, checked against their published vectors and an independent reimplementation. TON has three tabs: Telegram wallet, the one key of a TON phrase (24 words of the BIP39 list that pass TON's own check, without BIP39's checksum) with its W5, v4R2 and v3R2 addresses; Trust Wallet (m/44'/607'/i'); and Ledger (m/44'/607'/0'/0'/i'/0'). A pasted TON phrase that is not a BIP39 phrase opens the Telegram wallet tab, and "Generate a phrase the Telegram wallet accepts" draws a 24-word BIP39 phrase that is also a TON phrase. Each coin has its selective-build option and its Wallet Matcher recognizer; the Matcher searches TON addresses under Trust Wallet's and Ledger's keys. The Ethereum tab names the EVM networks whose addresses it gives.
- Added Cardano to the Multi-Chain Deriver, mainnet only, with a tab for each of CIP-3's master keys of a BIP39 phrase: Icarus (Yoroi, Lace, Daedalus's Shelley wallets, Trust Wallet and Trezor), Ledger (Ledger devices and BitBox02, from BIP39's seed) and Icarus-Trezor (Trezor wallets made from 24 words with older firmware; below 24 words it equals Icarus). Each derives BIP32-Ed25519 keys at CIP-1852's m/1852'/1815'/account'/role/index, where Role chooses receive addresses, change addresses or the stake key, and shows each key's base and enterprise addresses, the account's stake address and the CIP-5 key texts; a QR code holds the address alone. Each tab's notice says which wallets it matches, and that Eternl and Typhon, whose code is closed, were not checked; Byron-era wallets and Trezor's Shamir (SLIP-39) wallets, which derive Cardano by SLIP-23, are not covered. The keys are checked against CIP-3's, CIP-11's and CIP-19's vectors, cardano-serialization-lib's, cardano-addresses' and Trezor's published values, and an independent standard-library reimplementation. A BIP85 child wallet offers the Ledger tab only, and says why; Wallet Matcher searches Cardano's base and enterprise addresses on the receive keys (and the change keys with change addresses) and its stake addresses on the stake keys in the index range, under all three variants, each from its own seed; a base address is matched whole, so one whose stake key is another wallet's is not found. Cardano is neither scanned nor looked up: Koios answers without an API key but sends no CORS header, so a page cannot read its answers, and Blockfrost and Cardanoscan ask for a key.
- Added MnemoCode cross-stitch patterns (SeedStitch): Encode hides the phrase, masked with MnemoCode Seedshift and its dates or with Direct the phrase itself, in the legend of a DMC cross-stitch pattern made from a PNG, JPEG or WebP picture, on Aida 11 to 18 or linen 28 over one, at a sheet size from A6 to A2 or a width typed in centimetres or stitches, and saved as a PDF that looks bought; Decode and Re-encode read the legend line from that PDF or as typed, and they and Forgotten's date search correct one mistyped row and name it.
- Added the Photo or MP3 tab, MnemoCode's steganography: a message, a small file or a MnemoCode backup record hidden in a JPEG photograph or an MP3 file under a container password, optionally with a decoy under a second password, or divided across 2 to 16 files of which a quorum recovers it. The guaranteed space at every density is shown first; every new file is read back from the Blob saved and opened with each password before it is offered. Encode's records and a pattern's legend line can be hidden there, and what it opens goes on to Decode or Re-encode. Once a new file is saved, the page asks, as MnemoCode does, that each source be kept private: encrypted if it is used again, or else deleted with its cloud copies, since a source and its saved file compared show the hidden changes. It is not statistical invisibility; recompression or resizing destroys the record.
- Added MnemoCode's QR codes with a hidden record: a card sheet's QR can show the printed contact to ordinary scanners and keep the record in its hidden bytes, and every MnemoCode QR image import reads such a record first. It is camouflage, not encryption.
- Added SeedQR hidden in a decoy QR: on the SeedQR tab, Encode offers an ordinary SeedQR or a Standard SeedQR kept as the hidden record of MnemoCode's hidden QR, behind a decoy that ordinary scanners show instead (SeedSigner and other wallets cannot read the SeedQR: they show the decoy or reject the code): a contact card (vCard 3.0), a website, a plain text, a Wi-Fi network, an email, a phone number or a location, each with its own fields and its format's escaping. CompactSeedQR, raw bytes rather than text, is not hidden. Save PNG gives MnemoCode's own image, to print at actual size; Decode's image import reads its hidden record first and restores the phrase, and refuses a hidden record that is no SeedQR. A PNG beyond MnemoCode's 4096 pixels a side or 2 megapixels, such as a phone screenshot of an ordinary SeedQR, is read as an ordinary QR again, on the SeedQR tab and on MnemoCode's tabs alike, and a note under the field says that its hidden record went unread. It is camouflage, not encryption: protect the phrase first, for example with the SeedQR of an MHFE container phrase.
- Added MHFE 0.8.0 (suites `MHFE-BIP39-256-EXPERIMENTAL-3` and `MHFE-BIP39-LP-EXPERIMENTAL-4`), an experimental encryption of a BIP39 phrase into a password-protected 24-word container, or on request into one as long as a 12- to 21-word phrase: twelve rounds of Argon2id with 2 GiB each, PIM 0–1023, and a check of every new container before it is marked verified.
- Added MHFE's decrypt with several passwords: Decode asks every password, with its own PIM and check-word repair, and for a 24-word container the original seed phrase's BIP39 passphrase for the 16-bit check, before any work, then recovers each password in turn and shows every seed phrase on one screen under its password.
- Added the memory level to MHFE's Encode: levels 0 to 21, each with its memory, of which a browser runs level 0 alone, so Encrypt is off above it. For a memory level or a PIM other than 0, Encode shows the `mhfe encrypt` command with the same settings and a Copy button, such as `mhfe encrypt --pim 3 --mem 2 --same-length --new-password check-word --repair-words 4`; a custom PIM at level 0 still encrypts in the page. Above level 0 the page makes no password, since mhfe makes its own. Decode, Check, Change password and Hidden wallets have the same memory level and show the matching command, built the same way, such as `mhfe decrypt --pim 3 --mem 2 --words 24`, `mhfe check --pim 3 --mem 2 --fingerprint` or `mhfe rekey --pim 1 --mem 1 --words 24 --confirm fingerprint --new-pim 0 --new-mem 2 --new-password check-word --repair-words 8`; their buttons are off above level 0 and their work refuses such a level before the container is read, since the page would otherwise open it at level 0. Hidden wallets shows Decode's `mhfe decrypt` command, since mhfe 0.8.0 opens hidden wallets there and a command of their own would mark the shell history. The commands hold no secret: mhfe asks for the seed phrase, the container phrase, every password and BIP39 passphrase, an address or a fingerprint at its own prompts, so none of them enters a command, the clipboard or the terminal history, and no command answers whether a wallet has a BIP39 passphrase.
- Added the Desktop Deriver, `Wallet_Key_Derivation_Tool_Desktop-<platform>`, one program per platform (Linux x86-64 and ARM64, Windows x86-64, macOS ARM64 and x86-64). It is the whole Deriver: it carries the release page, checks its SHA-256 when it starts and serves it to this computer only, so that MHFE runs in fast mode with four threads, about two and a half to three times faster than the page opened as a file.
- Added bounded generation with one chosen BIP39 word, or one excluded word, with the remaining random bits shown before generating.
- Added an optional exact derivation path when recovering missing MHFE container words against a known address. The address scope is shown before searching; an invalid path is refused.
- Normalized every BIP39 phrase and passphrase with the Deriver's own NFKD of Unicode 18.0.0, the version MHFE's specification pins, instead of the browser's: a passphrase with a newly assigned character, such as U+209D, now gives the same seed in every browser, in MHFE and in MnemoCode. The tables are generated from Unicode's `UnicodeData.txt` and checked against all of its `NormalizationTest.txt`.
- Added an explicit MHFE wallet-check checkbox: the Deriver's own generator samples phrases, on the workers you choose (Threads, 2 at first, on WebCrypto's PBKDF2; further threads in JavaScript), until the first two bytes of the check derived from the complete BIP39 seed are zero, and MHFE's wallet module checks the phrase once more before it is shown; it uses the phrase and the nonempty BIP39 passphrase of the one passphrase field, which asks you to check it with Show. The phrase and seed bytes are not overwritten. Hover or click the adjacent “?” to read the explanation.
- The generation options combine: a chosen word, a phrase the Telegram wallet accepts and the MHFE wallet check in any combination, each phrase drawn uniformly among those that meet every condition, TON's check first. With the wallet check, the page says before the start how long a phrase takes on this computer (a one-second measurement after an option changes) and that the wallet check with TON's check, about 16.8 million draws, can take hours; it keeps the BIP39 passphrase and says that the Telegram wallet uses the phrase without it.
- Documented the wallet check's limits from MHFE's specification (mhfe-spec 3d88078): its proof, Theorem 5, covers only a phrase whose every word comes from the draw, not one with a chosen word, a word never to use or the Telegram condition; each worker stops after `2^22` draws, `2^30` with the Telegram condition; the time a draw shows, and negligibly several threads, are outside the specification's conditions. A security note says what a phrase the Telegram wallet accepts costs once encrypted with MHFE, and the Telegram option's “?” links to it.
- Every Generate shows a line under its buttons from the click on: what is drawn, the draws tried, the time and the average time at the speed so far, Stop for a draw that can last, and how it ended. A refusal of generation appears there too, not at the derivation's messages.
- Added a “?” with an explanation beside the options whose meaning is not plain at once: the derivation types, Silent Payments, child seeds, legacy mobile Core and CoinJoin addresses in the Deriver, the custom PIM of every MHFE form, an unsplit Codex32 secret, and the PSBT Inspector's output wrapper, policy shape, key order, timelocks, hashlock, ranged keys and script kinds. A help stays inside the window at every width.
- Added seven EVM networks to the Discovery Scanner and the Activity Viewer, beside Ethereum: Arbitrum One, Avalanche C-Chain, Base, BNB Chain, Gnosis, OP Mainnet and Polygon, each a coin of its own with its own PublicNode endpoint, chain-id check, native asset and post-use gap. The Scanner checks the three standard EOA layouts on each chosen network (an "All EVM networks" box selects them in a multi-coin search); the Viewer shows an address's balance and nonce. These networks offer Mainnet only and no history; tokens and contract wallets are not scanned. Every chosen network receives the same derived addresses through PublicNode.
- Added Ethereum Classic to the Discovery Scanner and the Activity Viewer as one more EVM network, mainnet only, read from HebeBlock's public endpoint `etc.etcdesktop.com` after it reports chain id 61. The Scanner first checks Ethereum Classic's own wallets' layouts, derived as the Deriver's Ethereum Classic coin derives them: the BIP44 address index `m/44'/61'/a'/0/i` at its coin type 61 (Trezor's, and the Deriver's row: its first account of the public test phrase is the Deriver's `0xFA22…1420`), Ledger Live's account index `m/44'/61'/i'/0/0` and Ledger's legacy Ethereum Classic path `m/44'/60'/160720'/0'/i`; then Ethereum's three layouts at coin type 60, which find MetaMask and other EVM wallets used on Ethereum Classic; a custom path starts at `m/44'/61'/0'/0/{index}`. Both tools read its confirmed ETC history from Blockscout (`etc.blockscout.com`), as they read Ethereum's. Every other EVM network keeps its three layouts at coin type 60.
- Added NEAR, Solana, Stellar, Tron and XRP to the Discovery Scanner and the Activity Viewer as account coins, mainnet only, grouped under "Other networks". The Scanner checks a seed phrase's addresses on each coin's wallet paths, the addresses the Deriver derives (Solana's Phantom and Ledger paths, Stellar's SEP-0005 accounts, NEAR's implicit accounts, and for XRP and Tron the BIP44 address index and Ledger Live's account index), each through its own 20-address gap; the Viewer shows an address's balance, and its sequence for XRP and Stellar; NEAR's Viewer takes the account's public key (`ed25519:…`), since 64 hex digits cannot be told from a private key. Each coin is read from its own provider: PublicNode for Solana, XRPL Labs' cluster for XRP, the Stellar Development Foundation's Horizon, FastNEAR for NEAR and TronGrid for Tron. Tokens, staking and history are not read, and these coins have no custom paths or public-key scans. Bitcoin Cash, Dogecoin, Litecoin and Zcash are not scanned: no public provider found for them answers a browser at a usable rate. The public-input guard of the Viewer and of the Scanner's public-key input also refuses an Ed25519 secret key in base58 (a Solana keypair, a NEAR secret key) and a Stellar secret seed (S…) as private material.
- Added Cosmos, Hedera, Injective and TON to the Discovery Scanner and the Activity Viewer as account coins, mainnet only, under "Other networks". The Scanner checks Cosmos's and Injective's BIP44 address index and Ledger Live's account index, Hedera's Ed25519 and ECDSA keys, and TON's Trust Wallet and Ledger keys as v4R2 wallets. The Telegram wallet is not scanned, since its key comes from a TON phrase, which is not a BIP39 phrase. Hedera numbers its accounts (0.0.N): a key finds every account that holds it, an ECDSA key also the account of its EVM address alias, and both tools list those accounts by number with their balances, counting an account that two lookups reach once. The Viewer takes a Hedera account ID (with or without its mainnet HIP-15 checksum), an EVM address or a public key in DER (Ed25519 or ECDSA), Injective's EVM address as well as its inj1… form, and TON's user-friendly and raw address forms. Each coin is read from its own provider: PublicNode's Cosmos SDK gateways for Cosmos and Injective, Hedera's public mirror node, and TON Center, read from a liteserver and asked one request at a time, 1.1 seconds after its previous answer. Only each TON key's v4R2 wallet is read. The public-input guard also refuses a private key in DER written in hex (Hedera's PKCS#8 and SEC1 keys) and a 64-byte Ed25519 secret key in hex (TON's) as private material.

- Added Dash Platform identity funding keys (DIP13) to the Deriver: the Dash Core addresses and keys at `m/9'/5'/5'/1'…5'/index` that fund identity registration, identity top-ups (for any identity, and bound to one identity), invitations, and Platform address and shielded pool top-ups. - Added **Recover & Back Up → Multisig wallet**: the addresses of a shared m-of-n wallet from its cosigners' recovery phrases, with their passphrases, or account xpubs, with the watch-only descriptor, each cosigner's child keys and, for Dash, the Core `7…` and Platform `dash1s…` addresses of each script. The Multi-Chain Edition also builds Bitcoin P2WSH, P2SH-P2WSH, legacy P2SH, Taproot `multi_a` (m-of-n) and Taproot MuSig2 (n-of-n, draft BIP390).
- Added message signing and verification for the Cosmos Hub and Injective (ADR-036, as Keplr's signArbitrary writes it; Injective also EIP-191, as MetaMask signs) and Hedera's Ed25519 and ECDSA rows (HIP-820's hedera_signMessage, ASCII text only), with hedera-wallet-connect's and eth-account's published known answers at startup, and our own for ADR-036, made by independent code. With them, every coin of the Deriver that has a message-signing standard signs ([the Deriver's list](../../apps/key-derivation/README.md#message-signing)).
- Added message signing and verification for Cardano: CIP-30's signData, a COSE_Sign1 of CIP-8 and the COSE_Key, for a row's base, enterprise or stake address, each with its own key. A pasted signature is read only in CBOR's deterministic encoding and checked with the row's key, never with a pasted COSE_Key. cardano-signer's published signature is a startup known answer, byte for byte; Trezor's published signatures check the structures the Deriver builds, and `test/oracles/cardano_oracle.py` reproduces both before it gives the full self-test's values.
- Added message signing and verification for Solana (the wallets' signMessage and the Solana CLI's off-chain message), Stellar (SEP-53), NEAR (NEP-413, for the key's implicit account, with the recipient and a random nonce) and TON (TON Connect's signData for text and binary, for each wallet address of a row), each with SEP-53's published known answers or our own, made by an independent RFC 8032 implementation, at startup, and near/intents' published signatures in the full self-test.
- Added message signing and verification for Ethereum and every EVM network (EIP-191 personal_sign, one signature valid on all of them), Ethereum Classic (the same bytes) and Tron (TronWeb's signMessageV2, TIP-191), each with eth-account's, viem's or TronWeb's published known answers at startup.
- Added message signing and verification for Litecoin (Litecoin Core's format for L… addresses, BIP137's typed headers for its SegWit addresses), Dogecoin, Bitcoin Cash (CashAddr and its legacy form, one signature) and Zcash's transparent t1 addresses, each with its own startup known answer and published verify-only vectors in the full self-test.
- Added verification to the Deriver's message-signing dialog: paste a signature of the message for the selected address and format, and the dialog says whether it is valid, from public data alone; the worker that checks it receives no seed. The dialog now names each address's format with notes about it, and offers a choice of formats only where an address has several.

## Download and verify

Download the files you need into one folder together with `SHA256SUMS`, the release's one checksum file, and check them there. Every file you downloaded must be reported `OK`; `--ignore-missing` skips the release files you did not download:

```bash
sha256sum -c SHA256SUMS --ignore-missing        # Linux
shasum -a 256 -c SHA256SUMS --ignore-missing    # macOS
```

On Windows, run `Get-FileHash <file>` in PowerShell and compare the hash with the file's line in `SHA256SUMS`; `Get-FileHash` prints upper-case hex, so compare without regard to case. `Wallet_Key_Derivation_Tool_Desktop-<platform>` is the whole Deriver, served to this computer only so that MHFE runs in fast mode: take the one for your system and allow it to run with `chmod +x` on Linux and macOS. `gh attestation verify <file> --repo hobby-eng/multi-chain-wallet-tools` checks, with the network, that GitHub built a file from this repository.

## Safety notes

Use the Deriver and Inspector offline for secrets. Connected Viewer and Scanner requests disclose public identifiers and the source IP address to configured providers. Recovery shares, envelopes, private descriptors, private keys, and restored seed material all grant or contribute to spending access and must be protected according to their threshold design. None of the tools broadcasts a transaction or replaces independent verification in a maintained standard wallet. MHFE is experimental and not independently reviewed.
