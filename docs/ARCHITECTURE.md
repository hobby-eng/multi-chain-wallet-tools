# Repository architecture

This repository is a pnpm monorepo with four independently runnable browser applications and a shared package layer. A single root `package.json`, `pnpm-lock.yaml`, TypeScript configuration, Rust lockfile, and release pipeline prevent dependency copies from drifting between applications.

Original project code is MIT licensed. Third-party source, generated integration inputs and the Dash brand asset remain governed by the licenses and attribution recorded in the root notices.

## Applications and trust boundaries

| Application                | Source                   | Artifact                                                                   | Network                                                                            | Secret input                                                                                                                                                             |
| -------------------------- | ------------------------ | -------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Wallet Key Derivation Tool | `apps/key-derivation`    | `dist/multi-chain-edition/key-derivation/Wallet_Key_Derivation_Tool.html`  | CSP forbids all connections                                                        | BIP39 mnemonic/passphrase and optional BIP38 encryption password; derived private/spending/viewing keys are outputs                                                      |
| Wallet Activity Viewer     | `apps/activity-viewer`   | `dist/multi-chain-edition/activity-viewer/Wallet_Activity_Viewer.html`     | HTTPS enabled                                                                      | Dash Orchard viewing capability only; public addresses/Identity identifiers are non-secret; never mnemonic/spending key                                                  |
| Wallet Discovery Scanner   | `apps/discovery-scanner` | `dist/multi-chain-edition/discovery-scanner/Wallet_Discovery_Scanner.html` | HTTPS only in an outer Network Worker; inner Secret Vault has `connect-src 'none'` | Mnemonic/passphrase/seed/FVK confined to the opaque-origin vault; public-key material remains in the vault and only derived public lookup values cross fixed RPC         |
| PSBT & Multisig Inspector  | `apps/psbt-inspector`    | Multi-Chain and Dash Community artifacts under their profile directories   | CSP forbids all connections                                                        | Public PSBT/script/descriptor/policy/xpub material; optional local hashlock phrase/preimage and BIP38 encrypted keys/password with recovered WIF/hex outputs; no signing |

Each application owns its HTML template, UI controller, app-specific styles, build script, artifact verifier, tests, README, and security notes. Cross-application behavior lives in shared packages; applications do not import another application's source. Dash Community uses profile-specific entry points or dependency substitution while retaining shared application code. Its PSBT Inspector excludes the Bitcoin MuSig2 implementation at bundle time and exposes only Dash Core PSBT v0, legacy P2SH/Script, and reviewed hashlock/timelock policy surfaces. Custom Dash policies expose their redeemScript separately and export only a non-solvable `raw(scriptPubKey)` watch descriptor; Dash Core's descriptor grammar and standard wallet signer do not support Miniscript policy expressions.

## Compile-time edition profiles

`tooling/build-profiles.mjs` defines two allowlisted build profiles and their explicit entrypoints, names, metadata, and output paths. It does not delete source files or strip a completed bundle:

| Profile          | Key-derivation registry                                     | Output root                                                | Branding                                                                                                                 |
| ---------------- | ----------------------------------------------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `multi-chain`    | `coins/registry.ts` + `coins/runtime-registry.ts`           | `dist/multi-chain-edition/<tool>/Wallet_*.html`            | universal, extensible presentation; Bitcoin, Dash (Core, Platform, Identity, Orchard), Ethereum and the single-key coins |
| `dash-community` | `coins/dash-registry.ts` + `coins/dash-runtime-registry.ts` | `dist/dash-community-edition/<tool>/Dash_Community_*.html` | Dash-only copy, graph, branding, and theme                                                                               |

The metadata registry is split into protocol-specific adapter modules. The extensible Multi-Chain entrypoint composes Bitcoin, Dash, Ethereum and the single-key coins: the BIP44 coins (Bitcoin Cash, Cosmos, Dogecoin, Ethereum Classic, Injective, Litecoin, Tron, XRP, Zcash transparent), which share `coins/bip44-coin.ts`, and the Ed25519 coins (Hedera, NEAR, Solana, Stellar, TON), which share `coins/ed25519-coin.ts` and SLIP-10 (`slip10-ed25519.ts`, also Dash's Evonode key); TON's Telegram wallet variant derives instead from a TON phrase's own entropy (`seedSource: "ton-phrase"`), which the page computes from the words (`apps/key-derivation/src/ui/ton-phrase-feature.ts`, in TON builds only) in place of the BIP39 seed; Cardano has its own BIP32-Ed25519 (`bip32-ed25519.ts`), and its Icarus variants read CIP-3's root of the phrase's entropy (`seedSource: "cardano-icarus"` and `"cardano-icarus-trezor"`), which the page computes through its phrase seed readers (`apps/key-derivation/src/ui/cardano-seed-sources.ts`, in Cardano builds only), while its Ledger variant reads the BIP39 seed; Zcash's Sapling variant derives ZIP-32's Sapling keys (`zip32-sapling.ts`) from the BIP39 seed, writes ZIP-316's unified addresses and viewing keys (`coins/zcash/unified.ts`), takes each row's transparent receiver from the BIP44 account of the same coin type, and gives an index without a Sapling address a row with a note (`DerivedRow.note`) and no fields, while one rule (`fieldColumns`) builds the result table's and the TSV export's columns from every row; a BIP85 child wallet offers only the variants of the BIP39 seed, and the Wallet Matcher (`WalletMatcherPlan`) makes for each phrase one seed of each kind its variants read, through the same readers (`MatcherServices.phraseSeedReaders`): a search makes them one phrase per turn of the page's event loop, with progress, so that Cancel answers meanwhile, and a reveal makes only its matches' seeds; it searches a Cardano address only on the roles that show it (`WalletMatcherTarget.branches`); each brings its profiles, its key and address encodings, its startup vectors and its Wallet Matcher recognizer; more adapters can be added explicitly. The Dash entrypoint imports only Dash metadata, derivation implementations, and Dash-only startup vectors, including Dash Purpose48 P2SH multisig cosigner derivation. Activity Viewer and Discovery Scanner also use explicit edition entrypoints: their Multi-Chain builds register Bitcoin, Dash, Ethereum and the other EVM networks of the EVM network table (`apps/discovery-scanner/src/coins/evm/`, one EVM factory for every network, Ethereum's included), while their Dash Community builds register only Dash. This opt-in composition ensures that adding a future coin to Multi-Chain cannot silently add it to a Dash build.

Application bootstrap code, shared views, export implementations, network boundaries, Worker lifecycle, and most tests remain shared. Application controllers coordinate small feature runtimes rather than implementing optional workflows directly. In Activity Viewer the Dash Core, Platform address, Identity and Orchard single-query runtimes are separate internal modules, while selecting Dash includes all four as one application-level Dash suite. A build without Dash removes their controls, hidden placeholders and user-facing copy from the HTML template before bundling. The offline Deriver uses one browser-independent Worker readiness contract in both editions: sensitive requests queue until the embedded Blob Worker reports `ready`, while cancellation clears queued work without revoking a booting worker URL prematurely. Generated entrypoints select coin adapters, feature installers, worker operations and recovery codecs at compile time; disabled modules are rejected if they remain in the esbuild input graph.

## Shared packages

- `packages/crypto-core`: BIP39/BIP32 wrappers, network constants, byte-secret disposal and common types. `MnemonicEntries` owns pasted-list splitting: at most 65,536 raw UTF-16 code units, 100 explicit or inferred entries and 2,400 words. Raw size, explicit line count and word count are checked before checksum work; the bounded inferred result is checked before use. The old backup import is a compatibility re-export, so wallet search does not depend on backup codecs. `Bip39WordReader` owns English word/prefix lookup, coded refusals and lexical word counting; the diagnostic feature and the Deriver view share that count and the canonical BIP39 length predicate.
- `packages/coin-protocols`: offline derivation implementations. Profile metadata registries are main-thread-only; profile runtime registries import cryptographic implementations and are worker-only.
- `packages/dash-network`: public Dash data providers, Platform state/history, viewing-key parsing and Orchard activity reconstruction.
- `packages/dash-shielded-wasm`: pinned Rust source, Cargo lock and generated browser WASM for Dash Orchard/ZIP-32. There is one compiled WASM binary shared at source/build time; each standalone connected artifact embeds its own release copy because artifacts must run independently.
- `packages/export-core`: generic formatter, clipboard boundary and Bitcoin/Dash account descriptor exports. `ExportChoice` admits the shared result action, format and mode before field access; `ClipboardSelection` owns the clipboard assembly bound. `AccountExportChoice` owns account action/format admission, disclosure permission, Core console conversion and filename metadata; the main and child account panels share `AccountExportController`. Unknown choices are refused before descriptor access. `ClipboardWrite` owns mutable fallback text and accepts cancellation without starting a later legacy copy. BIP380 checksum logic has one implementation in `crypto-core`; the export package re-exports it for compatibility.
- `packages/shared-ui`: common visual system, the post-application `tool-shell.css` layout/state layer shared by both editions, and the explicit `dash-community.css` palette/brand override module. `ClipboardAction` owns pending source and result copies: source replacement, edits, concealment, Clear and leaving the page revoke later fallback writes and completion messages. A copy already delivered to the operating system cannot be recalled. The Deriver's `DeriverSource` owns the native source fields, disclosure and source-reference epochs. Publication revokes references acquired while generation was pending; page exit uses the same Clear operation to retire the source, results and active work.
- `packages/public-data-providers`: public address normalization, provider response validation, and Bitcoin and EVM network activity/balance services. The EVM networks are one EVM network table (`src/evm-networks.json`: label, asset, the operator of its JSON-RPC endpoints, for a network whose own wallets lay out their addresses otherwise the Deriver coin whose public address scheme derives them (`walletCoin`, Ethereum Classic's), and per network the EIP-155 chain id, name, JSON-RPC endpoint and, for Ethereum and Ethereum Classic, the Blockscout history root); `EvmAccountService` reads any of its rows, checking `eth_chainId` first, and `EvmHistoryService` reads the history of any row that names a Blockscout root, in the row's asset; the `evm.accounts` boundary payload is `{coin, network, addresses}`, `address.history` names Bitcoin or such a row in `coin`, and each build's Worker admits only its selected `coin` ids. The Scanner's EVM factory (`apps/discovery-scanner/src/coins/evm/`) checks Ethereum's three layouts at coin type 60 (`layouts.ts`), and before them, for a row that names a `walletCoin`, the layouts of that Deriver coin's public address scheme (`ETHEREUM_CLASSIC_ADDRESSES`: the BIP44 address index and Ledger Live's account index at coin type 61, and Ledger's legacy path `m/44'/60'/160720'/0'/i`), which derives them; the coin picker's privacy note names the operators that run several of the build's networks. Only development entry points import the table; composed builds inline their selected rows (`tooling/evm-networks.mjs`). The account coins (Cosmos, Hedera, Injective, NEAR, Solana, Stellar, TON, Tron, XRP) are one account coin table (`src/account-coins.json`: label, asset, atomic unit and decimals, the api of its provider, its endpoint, its batch, the addresses one provider request reads, and where needed the pace between two reads (TON Center) and whether the network numbers its accounts (Hedera), whose states then list each account found with its balance); each api has its provider in `src/account-coins/<api>.ts`, which checks the coin's address form and maps the provider's answers to account states (Cosmos's and Injective's share `cosmos-sdk.ts`), an `AccountStatesReader` holds a row with its api's provider and keeps the row's pace across all of its reads, and `AccountStatesService` admits a request only for its readers' coins, Mainnet only, with the coin's canonical addresses, and checks every answer (`assertAccountStatesView`). The `account.states` boundary payload is `{coin, network, addresses}` (`tooling/account-coins.mjs` composes the rows). The Scanner derives these coins' addresses with each coin's `<COIN>_ADDRESSES` of `coin-protocols` (`coins/address-scheme.ts`: the Deriver's profiles and address forms, public keys only; Hedera combines its Ed25519 and ECDSA schemes).
- `packages/wallet-recovery`: watch-only parsing/detection, checksum-aware address targets, bounded one-seed and multi-seed address search, and recovery search result types.
- `packages/recovery-backup`: shared SeedSigner SeedQR and MnemoCode codecs, SLIP-39, Blockchain Commons SSKR and Gordian Seed Envelope bridges, and Codex32 create/restore orchestration used unchanged by both Deriver editions. The MnemoCode wrappers translate between the page and MnemoCode's own WebAssembly, vendored for each page in `packages/recovery-mnemocode-wasm/` and pinned by commit and SHA-256; MnemoCode also draws the cards; see [MnemoCode source](MNEMOCODE_SOURCE.md).
- `packages/recovery-codex32-wasm`: pinned `rust-codex32` BIP93 reference bridge for seed encoding, checksum validation, GF(32) interpolation, and recovery.
- `packages/recovery-sskr-wasm`: pinned Blockchain Commons `sskr` bridge for grouped thresholds and standard Compact UR or full Bytewords representation. Browser WebCrypto supplies its explicit RNG seed.
- `packages/recovery-envelope-wasm`: pinned `bc-envelope`/`bc-components` bridge for typed Seed Envelopes, Argon2id password permits, X25519 recipient permits, SSKR permits, and the official recipient-key derivation from a 64-byte BIP39 seed.
- `packages/recovery-mhfe-wasm`: the MHFE 0.8.0 browser package from `hobby-eng/mhfe` (a verified development build of the unreleased 0.8.0 tree on v0.7.0, commit 8a15bed), unchanged: a shared runtime (one WebAssembly with every module, one worker script and the error and secret handling) and four module classes, the core (encryption, recovery, the rehearsal check, rekey, hidden wallets and the self-test, with two Emscripten builds of the reference Argon2 C code, threaded and single-threaded), repair words, passwords and wallet checks. MHFE 0.8.0 draws no new phrases; the Deriver's own generator (`packages/crypto-core/src/bip39-chosen-words.ts` and `bip39-wallet-check.ts`, on the workers of `apps/key-derivation/src/workers/wallet-check-draw-worker.ts`) draws them, and MHFE's wallet module checks a phrase drawn with its wallet check. With a phrase for the Telegram wallet, those workers try TON's check first (`workers/ton-draw-precheck.ts`, a TON module that a build without TON replaces with `no-ton-draw-precheck.ts`); `apps/key-derivation/src/ui/phrase-generation.ts` routes every combination of the generation options and shows the draw under the Generate buttons. The package's Python fast-mode launcher is not vendored; the executable Deriver replaces it. `modules.json` lists every file with its SHA-256 and the build pins `modules.json` itself. Its exact source fingerprint, manifest and build identity are described in [the package provenance](../packages/recovery-mhfe-wasm/README.md). Operations run in disposable Workers, so Stop discards the active 2 GiB Argon2 work area.
  Password permits use the upstream `bc-crypto` Argon2id defaults embedded in each Envelope: 19 MiB memory, 2 iterations, 1 lane, a random salt, and a 32-byte derived key. The SSKR and Envelope WASM builds explicitly select the browser `wasm_js` `getrandom` backend; randomness therefore comes from the browser CSPRNG and creation fails if it is unavailable.
- `packages/secret-boundary`: public-input rejection, the secret-egress tripwire, and byte-disposal helpers. It is reusable but does not open a network channel.
- `packages/network-boundary`: neutral transport DTOs, MessagePort client/cancellation/worker runtime, exact-envelope validation primitives, and the generic opaque iframe bootstrap used by both secret and public-input boundaries. Coin-specific operation allowlists and dispatchers are generated by the host application build.
- `packages/secret-vault`: seed-capable Vault protocol, delivery, lifecycle and disposal semantics layered on that transport.
- `packages/edition-profiles`: canonical edition capability metadata consumed by build/profile tooling; static code entrypoints remain authoritative for tree-shaking.
- `packages/build-security`: immutable build passport, including edition/profile identity, and ambient type declarations.
- `packages/verification`: fixed BIP39, full Multi-Chain, and Dash-only startup vectors.

## Internal application modules

Application files are split at state and trust boundaries rather than by page size:

The Deriver's range and result rules have shared owners. `DerivationBranches` selects ordered
worker branches; `DerivationRequest` snapshots their range and estimates work, and
`DerivationConsent` owns the second-start confirmation. `DerivationResults` retains each
branch's result, selection and page and releases data on replacement or Clear all. Its
`wipe()` clears result containers, including private account descriptor text; the view's
`clearResults()` clears only the DOM. `ResultSelection` supplies the original and BIP85 child
wallets with one all/none/invert rule, and `ResultWindow` supplies their common page policy.
Views borrow results only until replacement or cleanup. Clearing string references is best
effort because JavaScript strings cannot be erased in place.

`DerivationInput` admits native account, branch, network and range fields in the library and
provides the same profile bounds to `DerivationControlsView`. `IntegerInput` supplies bounded
decimal conversion to the Deriver and the existing Scanner/Viewer callers; empty text never
means index zero. `ResultRendering` owns result markup and binds supplied callback receivers.
The existing control and rendering function names remain compatibility entries.

`RenderedSecrets` owns each private result's presentation snapshot as mutable bytes. Concealed
nodes contain a placeholder and are hidden from accessibility text; revealing decodes a temporary
view. Hiding drops that native text, and replacing or clearing main/child results wipes the
presentation owners before detaching nodes. The derivation result containers have a separate
lifetime managed by `DerivationSecrets`: private fields, private descriptors and watch-only text
retain exact UTF-16 bytes through the existing `SecretValue` owner. Field reads decode temporary
views; retirement refuses later nonempty assignments through saved field references. A stream
releases only rows still in its batch container, preserving rows transferred to the destination.
Worker posting owns and releases the sender's result in `finally`, and the client takes private
text before resolving its request. Native structured cloning necessarily makes independent text
copies; late responses without a receiver are cleared, and erasure of immutable native copies is
not guaranteed. The package graph checks the shared owner's import without a copied text codec.
Property cleanup failures do not interrupt other fields or branches: independent releases finish
before one input-free refusal is reported, and a rejected replacement releases its incoming result.
Cleanup snapshots every field and container before invoking native setters. Branch admission is
closed during replacement and clearing; a reentrant transfer is refused after retiring its incoming
private text, so callbacks cannot strand a new branch outside the cleanup snapshot.
Planning attempts each available native field independently too: a failing graph getter is reported
with the cleanup code after available targets and healthy neighboring containers are released.
`DerivedPrivateKey` binds a derived secp256k1 key to the selected public address and retires the consumed
result before an awaited signing/BIP38 call. Only its owned key bytes and copied public script metadata
remain available to that call. Its hexadecimal property is a temporary view; disposal wipes the owned
bytes, and the worker does not retain a separate hexadecimal key string.
`DerivationErrorText` translates known codes after worker transport and uses a fixed fallback for
unknown failures. It does not display supplied exception text or coerce thrown objects to strings;
a foreign code getter that fails also receives that fallback.
`LiteralSecretField` uses the existing `SecretValue` owner for exact imported UTF-16 text and its
native presentation. Edits, Clear, disposal and page exit wipe that snapshot, preserving CRLF and
lone surrogates while an unedited imported factor is current. Immutable browser strings cannot
be guaranteed to be erased.

`Bip39Input` admits at most 8192 UTF-16 code units before and after phrase normalization, and at most
48 words for malformed-phrase diagnostics. Oversized input is refused without truncation; an
unavailable word count is never presented as zero. `MnemonicInspection` replaces the diagnostic DTO
with a disposable owner for normalized text, word indexes, suggestions and entropy. Its secret
getters create temporary views; hosts dispose the owner after synchronous rendering, and copied
native strings cannot be recalled. `SeedDiagnosticView` uses `RenderedSecrets` to revoke private
nodes before concealment, replacement or input refusal. Diagnostic fingerprint derivation waits for
self-test readiness and disclosure; revision/readiness checks prevent stale callbacks from restoring
a retired presentation. `MnemonicFingerprint` owns temporary seed/node cleanup for both diagnostics
and backup fingerprints. Existing `diagnoseMnemonic` callers must now dispose its returned owner.
Recovery result parents also retire those diagnostic owners before removing their descendants or
replacing them with a status. `RenderedSecrets.replace` preserves explicitly retained children,
locks the captured removed nodes against reentrant ownership and attempts each independent native
cleanup before reporting `ui.secret.cleanup`; reentrant transitions fail with `ui.secret.retired`.
Native properties that refuse writes and immutable copies cannot be guaranteed to be erased.
The MnemoCode share workspace composes separate split, restore and repair controllers with shared
action admission and result formatting. `LatestShares` owns the retained card-export records as
bytes: its stable view decodes records only when requested, and an old view refuses reads after
replacement or disposal. The split controller separately owns and wipes its save-file snapshot.

`RecoverySourceRoute` owns source/target admission and original BIP39 validation in the recovery
library. Unknown native choices fail before either source provider is called; an unavailable
child never selects the original phrase. `RecoverySourceController` translates native events and
stable refusal codes, then passes the admitted capability to the installed feature. The host's
existing source-reference types remain compatibility exports of the library's single contract.

`Bip85` owns the application paths and derivation. `Bip85Parameters` admits the public request
before the page allocates a seed; the worker uses the same admission and refuses unknown
applications. `Bip85Feature` retains the child phrase as mutable UTF-8 bytes, revokes child
references immediately when parameters change, and releases pending work on disposal. Worker
failures preserve the library's stable code; the BIP85 page supplies the display text. The page
builder reads the same word counts, HEX bounds and WIF versions as runtime admission. The
four application vectors remain the startup checks, with no additional expensive derivation.

`Bip85ChildWallet` owns the embedded workspace and its native bindings. It shares automatic
refresh scheduling with the main view and admits controls and startup readiness before reading
the child phrase. `CoinFamilyCatalog` supplies the same family/default selection rule to both
registries and embedded views. Single-field copies pass a deferred text source to
`ClipboardAction`, which checks disclosure before reading it and checks the current revision
again before the native write. Public copies do not request private fields.

`Bip85ChildDerivation` owns the child workspace's pending seed and worker. Cancellation wipes
its mutable seed before native teardown; the completed branch map crosses owner and view
revision checks before publication. `DerivationStream.discard` releases revoked branch maps
for the stream and its hosts. Native teardown failures do not leave the child operation busy.

- **Key Derivation:** the main controller coordinates feature installers; `adapter-settings` preserves user ranges across protocol switches, `automatic-derivation` owns debounce/cancellation scheduling, `startup-self-test` owns fail-closed readiness, `DerivationStream` in `coin-protocols` owns bounded worker batches over an admitted range, snapshots public settings, and clears uncommitted results; the browser supplies callbacks and event-loop turns, and the account/result export controllers own their respective disclosure rules. BIP85, Silent Payments, BIP38, signing, diagnostics, Wallet Matcher, and every backup codec have separate installers. Silent Payments has one library admission owner (`SilentPaymentParameters`) for network, account, label range and raw input bounds, and one derivation module (`SilentPaymentWallet`) in `coin-protocols`; the worker retains its existing callback name. Its page class owns active worker/seed cleanup and revokes old results on edits, Clear and page exit. Recover & Back Up is a host that knows no feature by name: each backup module exports a `recoveryFeature` that names its panel and phrase fields and installs itself, one job gate runs a single heavy job (such as a 2 GiB MHFE Argon2 run) at a time across all panels, and a panel with several operations, such as MHFE, has one class per operation tab.
- **Activity Viewer:** Core, Platform, Identity, and Orchard single-query services remain independent. `batch-public-query` supplies the shared Core/Platform/Identity batch handlers; `batch-controller` owns mixed/fixed scheduling, shared Orchard pages, cancellation, and result selection. Shared page controls and diagnostics remain in `view`, while `activity-results-view` and `activity-renderers` own result cards. CSV, JSON, workbook, text, and download-control exports are separate modules built from one typed export model.

The Dash Core adapter delegates whole-page pagination to `CoreAddressHistory` and transaction admission to `CoreTransaction`. Both pending and confirmed rows pass the same strict flow parser before display truncation. Missing input/output containers, malformed present amounts and missing amounts attributable to the queried address fail the query. Exact zero remains a value; absent unrelated amounts make the whole-transaction fee unknown without changing an otherwise exact address flow.

`PlatformIdentifier` admits bounded canonical Base58 text by decoded byte width. Identity lookup, indexed history and the Scanner network Worker share that rule, including identifiers with leading zero bytes. `PlatformIdentityHistory` owns one history request and its request count; separate methods load bounded collections and resolve registration metadata. Reusing that request owner fails before starting additional HTTP work. The function entry point remains available to existing callers.

- **Discovery Scanner:** `network-service` is a thin facade over separate Dash Core and Dash Platform/Identity/Orchard services; bounded HTTP lifecycle and strict Platform value parsing are independent modules. `wallet-progress`, `scan-estimate`, and `validated-exports` own progress, coverage estimates, and public export staging. Result navigation and resource cards are separate from form state, while coin adapters own their scan semantics. The controller coordinates seed, candidate, address-match, and watch-only workflows across the isolated boundary.
- **PSBT Inspector:** `psbt.ts` is a compatibility facade and parse orchestrator over types, binary framing, map/version validation, UTXO binding, verification summaries, and presentation metadata. Raw transaction parsing, descriptor policy analysis, descriptor compilation, balanced syntax, Bitcoin/Dash message verification, and optional workflow features are separate modules. Shared syntax helpers replace earlier per-feature delimiter parsers.
- **Build tooling:** profile definitions, HTML element replacement, profile template transformation, and per-application composition are separate modules. Capability metadata contains only fields that actively select build behavior; profile identity remains responsible for branding and profile-specific wording.

Public compatibility facades remain where existing imports form part of the repository API. Internal modules exchange narrow typed values and do not import another application.

Wallet Matcher uses `WalletMatcherPlan` and `MatcherScope` in `wallet-recovery` for input admission, profile/branch selection and worker operations. `MatcherSecrets` owns independently copied private fields in mutable byte storage and generates TSV only on demand; both export kinds share the identity columns, including “Known target”. The browser's `WalletMatcher` controller revokes pending search and reveal work on input, linked-source, Clear, page-lifetime or readiness changes. Its `MatcherResults` owner clears transient derived rows, conceals private DOM content on blur/hidden, refuses stale export callbacks and wipes retained private storage when the result is replaced. JavaScript cleanup is best effort, not guaranteed erasure.

The Inspector's `InspectorNetworkChoice` owns offered chain/network selections and the Bitcoin-regtest to Dash-testnet transition. Unsupported selections fail rather than defaulting to mainnet. `ScriptDecoder` bounds raw input before normalization, validates descriptor indexes and roles, and dispatches to the existing Script or descriptor decoder. `ScriptDecoderFeature` renders that result and retires previous output on input or network edits. Low-level `InspectorNetworkProfile` still supports Dash regtest encoding for direct callers; the page offers Dash mainnet/testnet.

Linked source cards belong to a unique association in `LinkedSources`. Replacement publishes one source-change notification after installing that association. Concealment works on its starting snapshot; an older callback can clear its own DOM but cannot retire a replacement. Removed controls lose authority, and expired source capabilities conceal the visible card. The DOM field is cleared on retirement; this does not promise erasure of browser memory.

## Offline derivation execution

`KeyDerivationView` owns native rendering fields and keeps its callbacks bound for feature hosts. It asks the shared export inspection for availability rather than deciding field roles again; raw action and format values reach `ResultExportController` for admission before any value is read. `CopyFeedback` owns one temporary copy label/title per button, cancels obsolete timers and restores the original state after repeated successes in the Deriver and Inspector.

`KeyDerivationController` composes native page bindings. `DerivationWorkspaceTabs` owns supplemental workspace selection and path presentation; pointer and keyboard protocol selection retire that workspace through one controller path. `DerivationResultPanel` owns main-result disclosure, navigation and export bindings over the library's `DerivationResults`. `MainDerivation` owns request revisions, streamed publication and each worker/seed lifetime: cancellation or source replacement wipes the owned mutable seed immediately, then worker settlement performs idempotent cleanup. Already admitted partial branches remain available after cancellation, including a first CoinJoin external batch before an internal reply. A manual BIP85 start cancels its pending edit timer before work starts, so it cannot later replace that child while its export is open. Export controls pass their raw format to the shared `ExportChoice` admission before reading rows. These are best-effort JavaScript lifetime controls; they do not guarantee erasure of immutable strings, runtime copies or worker-owned memory.

The main thread loads only adapter metadata, the BIP39 input layer and UI/export code. It validates the mnemonic and runs the BIP39 startup check. A disposable Blob Web Worker owns the runtime coin registry, cryptographic derivation, message signing, BIP38 encryption, BIP85 applications, BIP352 address derivation, the remaining fixed-vector startup checks, and the sole embedded Orchard WASM instance. These operations cross one discriminated typed worker protocol. BIP38 is restricted to compatible Bitcoin/Dash P2PKH rows. Coin-independent BIP85 child mnemonics are available in both editions and reuse the same result/export workspace; Bitcoin-specific BIP352 remains Multi-Chain only. The main-thread Recover & Back Up workspace shares Wallet Matcher and SeedQR/MnemoCode/SLIP-39/Codex32 code across editions; only address-profile detection has separate Multi-Chain and Dash-only entrypoints. Its Codex32, SSKR, and Gordian Envelope modules are synchronous embedded WASM with no loader or network path. The final artifact verifier requires exactly one byte-identical copy of each Orchard, Codex32, SSKR, and Gordian Envelope WASM payload and one English BIP39 wordlist. MnemoCode's long searches and share restores run in Blob workers of their own, which Cancel terminates; to keep those single copies, the page hands each worker its English wordlist when it starts and the share worker the SSKR WASM bytes with each job. SLIP-39 restoration also runs in a disposable Blob worker. The library admits the set before stretching, reports its public work count and requires confirmation above the default backup cost. The page transfers owned input bytes and the worker independently checks confirmation; Cancel, edits, Clear and readiness loss revoke pending results. Its public SLIP-39 dictionary is embedded once and supplied as a worker prelude. Startup also executes fixed encode/decode vectors for SeedQR, MnemoCode, SLIP-39, Codex32, SSKR, and Seed Envelope; all derivation and recovery controls remain disabled if any check fails.

Large requests are divided into bounded batches and only a bounded result window is rendered. For adapters declaring standard `addressBranches` metadata, the same worker derives receive `/0` and optional change `/1` batches into separate result, selection, paging, watch-only and export state. Branch support is adapter metadata rather than a Bitcoin/Dash conditional in the renderer. Both branches share the requested account/network/start/count, and total-row estimates include both. Requests of at least 10,000 total rows across enabled branches require an explicit second action, but no convenience maximum is imposed below the protocol index-space limit. Request generations and cancellation tokens prevent an obsolete worker response from committing UI state.

MHFE is the exception to the main-thread recovery WASM pattern described above: its 2 GiB, synchronous Argon2 work is embedded in and executed by a separate Blob Worker. The UI creates one Worker per operation through the package's classes, and quick operations (repair words, password tools, wallet checks) run in Workers of their own that never wait for a long one; terminating it is both the cancellation path and the memory-disposal boundary. On a cross-origin isolated page, as the executable Deriver serves it, the Worker uses the threaded Argon2 build and its four lane Workers, also started from Blobs; otherwise it uses the single-threaded build. The embedded scripts contain no network code: the MHFE build removes the unused file loaders of Emscripten and wasm-bindgen. MHFE is omitted entirely when the `mhfe` build feature is excluded.

BIP-322 signing is owned by `crypto-core`'s `Bip322Signing`, not the worker adapter. Its single-use key is cleared before public verification and on every refusal or explicit disposal. `Bip322Verifier` shares one initialized local backend: recognized script or full-message commitment mismatches return `valid: false`, text that is no BIP-322 signature (a compact one included) rejects as `UNREADABLE_SIGNATURE`, a simple signature for an address that needs a full one as `SIMPLE_FOR_ADDRESS`, and startup and other operational failures reject with an input-free code. A compact signature that names no public key (r = 0 or off the curve) rejects as `RECOVERY_FAILED`. Its adapters are pinned to the installed btcutil-js backend and exercised by published and generated negative controls. `SigningMessage` admits exact, well-formed text up to 64 KiB of UTF-8 for compact and BIP-322 operations, without trimming or normalization; verification also permits an empty message.

Each signing coin brings its standards as one `CoinMessageSigning` (`packages/coin-protocols/src/coins/<coin>/message-signing.ts`), or as a list of parts when its rows sign with different keys or standards (Hedera's Ed25519 and ECDSA rows, Injective's ADR-036 and EIP-191), and the worker's `MessageSigners` (`coins/message-signing.ts`) hands each request to the coin that owns its format and refuses any other. A build composes the signers, page policies and known answers of its own coins from `tooling/message-signing-coins.mjs`, so the Dash Community Edition holds Dash's alone. The compact signature of Bitcoin, Dash, Litecoin, Dogecoin, Bitcoin Cash and Zcash is one core (`crypto-core/src/compact-message-internal.ts`): each format gives its magic, the headers it reads (`compact-message-headers.ts`: Bitcoin Core's 27–34, BIP137's 27–42, or Zallet's compressed 31–34), the script type it signs, and the address forms a recovered key proves; Litecoin, Dogecoin, Bitcoin Cash and Zcash take those forms from their own row encoders through `coins/message-signing-compact.ts`: the row's address, and only the other forms a coin names (Bitcoin Cash's legacy address, never Litecoin's old 3… form). Ethereum, Ethereum Classic and Tron sign in EIP-191's envelope (`crypto-core/src/message-signing-envelope-191.ts`: 0x19, "Ethereum Signed Message:\n" or TIP-191's "TRON Signed Message:\n", the length in bytes in decimal, the message, Keccak-256) with a recoverable signature r‖s‖v (`message-signing-recoverable.ts`), through `coins/message-signing-envelope.ts`, which compares the recovered key's address with the row's: EVM hex without regard to case, Tron's base58 exactly. Tron's verification refuses a high S, as TronWeb's `verifyMessageV2` does; Ethereum's accepts it, as eth-account, viem and `ecrecover` do. Solana, Stellar, NEAR and TON sign with Ed25519 (RFC 8032, verified by its strict rule) through `coins/message-signing-ed25519.ts`, each with its standard in its own folder: `solana/message-signing-offchain.ts` (the CLI's off-chain message, version 0, beside the wallets' raw `signMessage`), `stellar/message-signing-sep53.ts`, `near/message-signing-nep413.ts` and `ton/message-signing-sign-data.ts`. NEAR's recipient, nonce and callback URL and TON's domain and timestamp are fields that the coin's page policy describes (`MessageFormatText.inputs`); the page admits them with the standard's own rule before a seed is copied, and the request carries them as `inputs`. A TON address is a contract's, so TON's verification takes the row's public key as an input and accepts it only for that key's own wallet addresses. The Cosmos Hub and Injective sign ADR-036's sign document as Keplr's `signArbitrary` writes it (`coins/message-signing-adr036.ts`: sorted, compact amino JSON with an empty chain id, account number and sequence "0", no fee or memo, and one `sign/MsgSignData` holding the Base64 message and the row's address), SHA-256 for Cosmos and Keccak-256 for Injective, as r‖s with low S; Hedera signs HIP-820's bytes (`hedera/message-signing-hip820.ts`: EIP-191's envelope with the name "Hedera", ASCII text only), Ed25519 over them or ECDSA over their Keccak-256, and returns a SignatureMap (`hedera/message-signing-signature-map.ts`). A signature without a recovery id names no key, so `coins/message-signing-secp256k1.ts` verifies ADR-036's and Hedera ECDSA's against the row's own compressed public key, which the request carries as an input, and only when that key owns the row's address; it refuses a high S, as the Cosmos SDK and the Hiero SDK do. Injective's EIP-191 is Ethereum's envelope signing (`coins/message-signing-envelope.ts`) for the inj1 form of the account. Cardano signs CIP-30's `signData` (`cardano/message-signing.ts`): a COSE_Sign1 of CIP-8 whose protected header names EdDSA and the address, over the message as UTF-8 text, with the COSE_Key (`cardano/message-signing-cose.ts`), in its own strict CBOR subset (`cardano/message-signing-cbor.ts`: RFC 8949's deterministic encoding only, the tag of COSE_Sign1 only around it, no floats, depth at most 8); the row's extended key signs (`Bip32Ed25519Signer`, which checks it as rust-ed25519-bip32 does), and verification takes the row's public key as an input, refuses any structure that is not CIP-8's in that encoding, and accepts the key only when its BLAKE2b-224 is the address's first credential: the payment key of a base or enterprise address, the stake key of a reward address. Before anything is derived or verified, the worker admits the request's format for the row's adapter (`MessageSigners.admit`): each coin's signer lists, per format, the adapters of the rows it signs, so no format is used on another coin's row or on another address type's (Litecoin Core's untyped format on a SegWit row), and no coin's signer reads another coin's key. Signing then lends the row's key as bytes the worker wipes afterwards. `DerivedPrivateKey` binds the key to the field the request names (`addressKey`): the row's address or another public payment-address field of the row. The coin's signer proves only the address forms it offers, so a request for another form, such as Litecoin's old 3… address, fails Litecoin's self-check, and Bitcoin's formats are refused on that row before it is derived. The key is read by the coin's own `DerivedKeySource`, the field and how the coin writes it there (Ethereum's hex `privateKey`, the Ed25519 seed in Solana's and NEAR's `privateKeyHex`, Stellar's S… seed, TON's 64-byte secret, Cardano's kL ‖ kR from its 128-byte `signingKey`), or else as a secp256k1 key from `privateKeyHex` or `childPrivateKey`; derivation output does not change. Verification is a `verify-message` request with no seed: the address, network, format, message, a format's inputs and the signature only; `MessageSignatureText` bounds a pasted signature before it is copied to the worker.

The Deriver's `MessageSigningFeature` owns dialog revisions and its disposable worker. Edits, closing, cancellation and page exit retire pending results. It calls message admission before deriving a seed or creating a worker, and clears the seed as soon as the worker client has copied it. Each coin's policy offers formats per address field of a row, its default first, and describes each one (label, signature label, notes); `MessageSigningFormatField` shows the choice and admits only an offered format, and `MessageSigningVerification` runs a pasted signature's check in a worker of its own. Native failures show an input-free message.

`MhfeInputText` admits borrowed phrase/container text with the producer's `requireInputText` and `parameters().maxInputTextBytes` before allocating retained host bytes. Encode uses scoped owners. `MhfeInputLifetime` owns pending repair inputs and wipes their managed bytes on edits, replacement, Clear and page departure, without waiting for a worker reply. Marked-container prompts retain separately disposable snapshots; an interrupted opening rolls back only its own snapshot. Temporary string views are passed through synchronous adapter frames. Strings already supplied to a caller and worker-owned copies cannot be recalled by these host owners, and browser memory cannot be guaranteed to be erased. `MhfeRepairChoices` reads the producer's repair counts and keeps explicit no-repair apart from an absent selection. Password and BIP39 passphrase policies remain with their own MHFE operations.

`MhfeContainerPreview` binds preliminary container readings in Decode, Check and Change password. It awaits the client and its parameters before reading the native field, then holds the admitted input in the same managed lifetime owner. Edits, Clear, page departure and an explicit operation revoke pending previews. Only a current preview may adapt the controls or display its refusal; invalid input is reported without repeating the concealed text. Preliminary views receive control metadata only, and Change password retains the confirmation choices without retaining the container phrase in its view state.

`DescriptorDecoder` owns admitted source and a snapshot of its network and derivation selection; `decodeDescriptor` remains the compatibility facade. `ScriptDecoder` uses that same selection admission and raw text limit. `DescriptorPolicy` owns symbolic descriptions, bounded alternatives and each Taproot leaf's spending description. A path card's `kind` distinguishes symbolic, impossible and concrete conditions. Its keys, locks and preimages are `null` when unknown and empty only when known absent. Nested MuSig keys keep their aggregate signature condition. An impossible script leaf never inherits the availability of Taproot's independent key path.

## Connected execution

The Multi-Chain Wallet Activity Viewer accepts Bitcoin, EVM network and account coin public addresses (Arbitrum One, Avalanche C-Chain, Base, BNB Chain, Ethereum, Ethereum Classic, Gnosis, OP Mainnet, Polygon, one adapter per network from the EVM network table; Cosmos, Hedera, Injective, NEAR, Solana, Stellar, TON, Tron, XRP, one adapter per coin from the account coin table; for NEAR, the account's public key `ed25519:…`, whose implicit account it reads; for Hedera, an account ID, an EVM address or a DER public key) plus Dash Core/Platform addresses, public Identity identifiers, names and keys, or an Orchard viewing capability. Dash Community exposes only those Dash inputs. The Wallet Discovery Scanner is structurally split inside one standalone HTML: an outer shell creates a network-capable Worker containing only the selected fixed provider operations, then loads the selected application as a sandboxed `srcdoc` iframe without `allow-same-origin` or `allow-downloads`. Seed-capable builds label this opaque-origin iframe the Secret Vault. Watch-only-only builds label the same transport the Public Input Boundary and omit BIP39, seed-worker and `secret-vault` modules. In both cases its CSP enforces `connect-src 'none'` and `worker-src 'none'`. The shell transfers one `MessagePort`; its discriminated protocol exposes fixed public read queries and never accepts a URL or secret-bearing generic payload. The build generates the Worker operation allowlist and dispatcher from the selected coins, so excluded provider branches are absent. Before dispatch, the Worker rejects unknown operations, extra envelope or payload fields, invalid networks, whitespace-bearing public tokens, malformed public hashes, oversized batches and out-of-range Orchard pages; provider adapters then perform coin-specific address and response validation. The shell cannot read the vault DOM, and the worker cannot access either DOM or vault memory. A separate fixed export message lets the shell save a local CSV/JSON Blob or convert the approved JSON projection into a local XLSX workbook without giving the vault navigation or download capability. Per-wallet secret-egress guards protect RPC messages. A second guard checks both fully serialized CSV and JSON exports at scan end, caches only approved public report strings, and then immediately discards its mnemonic/seed/FVK patterns. Both are defense in depth behind the structural CSP/sandbox boundary.

Discovery Scanner wallet tasks use isolated state slots and preserve input order. Seed phrases run sequentially by default, with explicit concurrency up to five available for users who accept greater DAPI tail latency. One abort-aware semaphore in the vault caps all concurrent RPC/DAPI work at five. The Network Worker maintains separate public Evo connection/quorum state per network and purpose. A batch Orchard coordinator streams each public encrypted page through all local FVK ledgers, wipes it, and only then advances by the required 2,048-action-aligned cursor. Two proof-verified empty terminal reads establish completion; a 4,096-page ceiling yields a partial result. No full-pool cache exists. Results are public projections; exports intentionally exclude the mnemonic, passphrase, seed and private/spending/viewing keys.

## Release ownership

`tooling/` compiles the pinned Rust packages, builds the standalone HTML files, creates and verifies per-profile manifests and flat release bundles, checks reproducibility, and enforces application-specific CSP/network/storage rules. `BundledAssets` shares the Deriver resource-loader catalog with module-boundary verification; resource edges require existing files inside the analyzed root, including real paths behind symbolic links. Exact aliases precede wildcard aliases, whose longest matching prefix wins; tied wildcard prefixes are refused explicitly instead of choosing a file by table insertion order. Original producer recipes are verified against their imported pins as provenance, and executable host imports of those snapshots are refused. `StartupSelfTestCatalog` maintains an independent expected inventory for each edition, while `SelfTestInventory` validates report shape and case multiplicity. Node commands execute the real self-test entries and print admitted reports. Discovery Scanner build metadata rejects network/Evo inputs in the Secret Vault, secret derivation inputs in the Network Worker, and every shell dependency except the reviewed shell plus typed shared `network-boundary`/`secret-vault` inputs. The Dash build additionally fails unless every bundled `coin-protocols` input is the shared registry contract, a Dash profile registry, the Dash adapter definition, or a module under `coins/dash/`; its Discovery Scanner graph has an equivalent Dash-only application allowlist. A future coin module therefore fails closed without updating the gate deliberately. Emitted HTML is then scanned for non-Dash adapter IDs and user-facing chain copy. The protocol-defined BIP32 HMAC domain string `"Bitcoin seed"` is an allowlisted lexical exception; it is required by Dash HD derivation and is not a Bitcoin adapter or registration. The Inspector has a separately bounded allowlist for unavoidable shared decoder vocabulary while its Dash artifact still rejects Bitcoin implementations and controls. The build passport hashes source, manifests, lockfiles, tests, the canonical Docker definition, generated pinned WASM and tooling, while excluding local dependency/build caches such as `node_modules`, `.pnpm-store` and Cargo `target`.

`Dockerfile.reproducible` is the byte-level release boundary. It fixes Linux/amd64, an Ubuntu 24.04-based image digest, and exact Node, pnpm, Rust and wasm-bindgen releases. Its final complete verification runs offline and rejects any difference between rebuilt and committed WASM/glue or their source/output integrity manifest. Local verification consumes those recorded bytes and fails if source changes or a host rebuild make the manifest stale. CI, tag releases and `./tooling/build-reproducible.sh` all use this same path, so the host distribution does not silently change release fingerprints or HTML checksums. Every supported build first enforces package-manager integrity pins for the complete pnpm and Cargo dependency closures, full commits for Cargo git sources, and stable SHA-256 records for the local recovery/QR codec sources. It additionally confirms that the exact reviewed GitHub commits remain available; loss of upstream access produces an explicit warning, while a returned mismatched commit fails. Successful verification emits a machine-readable record with the source revision, dirty state, toolchain, performed check groups, dependency provenance, and hashes for all artifacts and generated WASM integration files. The tag workflow adds GitHub OIDC provenance attestations over the release assets. Native builds remain supported for development and functional testing, but do not define canonical release bytes. Application build/verifier scripts remain beside their application so a future split into separate repositories does not require disentangling the build logic.

The applications should remain separate standalone HTML release assets rather than being merged into one page. The current `hobby-eng/multi-chain-wallet-tools` tag workflow publishes the stable Multi-Chain filenames, the Deriver's Desktop executables, the root MIT `LICENSE` with the other legal documents, and one flat `SHA256SUMS` that lists every other asset. The separately named Dash Community bundle is prepared deterministically but is not published by that workflow.

This repository is the canonical source for both editions. [dash-wallet-tools](https://github.com/hobby-eng/dash-wallet-tools) distributes Dash Community releases; Dash-specific source, fixes and shared security code remain here.

## Dash Community visual identity

The Dash Community theme is derived from the visual principles and palette in the official [Dash BrandBook](https://www.figma.com/design/cCpB1W2IAmoEGXBbGqGsfD/Dash-BrandBook?node-id=219-108&p=f), the [Dash Brand Guidelines](https://www.dash.org/brand-guidelines/), and the primary [Dash documentation marketing page](https://docs.dash.org/en/stable/docs/user/marketing.html). It applies controlled Dash blue, translucent navy surfaces, restrained ribbed geometry, and the official mark over the shared responsive shell. Expected privacy/security notices use calm caution styling; red is reserved for actual errors. Use of Dash branding identifies the target community and does not imply endorsement.

The Inspector's BIP38 input rules live in `Bip38Input`. `Bip38Batch` owns bounded request snapshots as mutable bytes; `Bip38Feature` checks both input revisions and literal fields before publication or password clearing. A single in-flight KDF slot and one deferred request prevent repeated Clear/start actions from multiplying active derivations. `Bip38Results` owns DOM fields and abortable copy listeners: retirement clears still-referenced secret fields before detaching them. Cancellation revokes publication; an existing cryptographic operation finishes under its own cleanup. The single-key compatibility function delegates to `Bip38KeyRecovery`; a host can await `Bip38Feature.whenIdle()` for KDF cleanup after cancellation.
